# Token 紀律

`implement-stepwise` 與 `implement-oneshot` 共用。修改本檔會同時影響兩者。

以下每一條都對應實測中確認過的浪費。共同前提：**留進 context 的內容無法移除，之後每一個回合都會重送**——所以錯誤的讀取方式不是付一次錢，是付到 session 結束。

## 探索優先序

**若本專案已建立程式碼知識圖譜或等效的索引式導覽工具，一律優先使用它定位，再針對性讀取檔案片段。**

如何得知專案有沒有：讀 `CLAUDE.md` / `AGENTS.md` 是否宣告了可用的索引與其工具，或檢查是否有對應的 MCP 工具可用。**不指定使用哪一套**——依專案當下實際可用的工具自行評估選擇。

1. **圖譜 / 索引查詢** —— 定位符號定義與引用、找出呼叫關係、評估變更影響範圍、追執行流程。
2. **針對性讀取** —— 依前一步得到的精確位置，只讀需要的區段。
3. **grep** —— 前兩者不適用時才用（例如找字串常數、設定值）。
4. **整檔閱讀** —— 只在該檔案本身就是變更目標、且篇幅不大時。

理由是成本：在大型 codebase 裡靠 grep 加整檔閱讀去理解結構，會把大量無關內容永久留在 context；圖譜查詢回傳的是定位結果，量級小上一到兩個數量級。

**但圖譜只對既有程式碼可信。** 索引反映的是上次建立索引時的狀態，**不包含本輪剛寫出的程式碼**，也可能因為專案已變動而過期。涉及本輪已完成 commit 所產生的新程式碼時，直接讀檔，不要查圖譜。索引明顯過期時，回報使用者，不要自行重建。

## 三條防呆

- **改檔一律用 Edit 做定點替換，不要用 `sed -i` 之類的整檔改寫工具。** 整檔改寫會觸發 harness 把修改後的完整檔案回吐進 context。實測：對一個 1200 行的 Service 檔做機械修改，換來六次整檔回吐，約 15–25k token，而那些內容當時早已知道。
- **grep 前先確認圖譜是否更適合**；確定要 grep 時先限定範圍，排除產生物與壓縮檔。掃 `wwwroot/`、`dist/`、`node_modules/`、`*.min.js`、`*.min.css` 這類路徑，會把整份壓縮過的單行 JS 倒進 context，且無法再移除。實測有發生過。
- **為了抄版型或慣例而讀既有檔案時，只讀需要的區段。** 用 offset / limit 讀目標區域。實測：為了其中約 40 行的 select2 版型，整份讀了 389 行的 `.cshtml`。

## 回合數也是成本

每一次 build / test 都是一個回合，會把當下的完整 context 重送一次。輸出本身很小，但回合數乘上 context 大小才是實際帳單。

- 不要為了確認而重複跑同一個測試。
- 相關的檢查合併成一次執行，不要拆成數次。
- 測試失敗時，先讀懂錯誤再改，不要「改一點跑一次」試探。
