# 實作規範

`implement-stepwise` 與 `implement-oneshot` 共用。修改本檔會同時影響兩者。

## TDD

調用 Matt 的 **`/tdd`** skill，取得測試品質判準：好測試的定義、seam 概念、以及三個 anti-pattern（implementation-coupled、tautological、horizontal slicing）與 `tests.md`、`mocking.md` 的具體規則。這些內容不在此重複，一律以 `/tdd` 為準。

在其之上套用三條覆寫：

**覆寫 1 — seam 只確認一次。** `/tdd` 要求「寫任何測試前先寫下 seam 並與使用者確認，未確認的 seam 不得寫測試」。照字面執行會在每個 commit 前多一道詢問，與逐 commit 的節奏疊在一起造成雙重關卡。改為在流程的規劃／開場階段一次列出全部 seam 並取得確認，之後不再逐一重問。**調用端 skill 負責指定該確認發生在哪一步**；未經確認的 seam 仍然不得寫測試。

**覆寫 2 — 先看它失敗，且必須因為對的理由失敗。** `/tdd` 只說 "Red before green"。本規範要求：執行測試，確認它**因「功能尚未實作」而失敗**，而非因語法錯誤或環境問題而失敗。**此步驟不得跳過**——沒看過它失敗，就不知道它測的是不是對的東西。

**覆寫 3 — 重構就地處理，不推給 review 階段。** `/tdd` 寫著「Refactoring is not part of the loop. It belongs to the review stage (see the `code-review` skill)」。但本套流程的 `code-review` 是選用的、可能不執行，照抄會讓重構無處可去。改為：在**剛寫出的程式碼**內、且測試保持綠燈時做最小整理。

- **不得改動本次以外的既有程式碼**（不順手重構、不改周邊命名、不調整格式或註解）。
- **預設不整理**，可直接省略此步。
- 若判斷需要較大範圍的重構，**不要就地進行**，依「暫停與回報」提出，由使用者決定。

### 例外

純設定檔、無邏輯的樣板或產生碼、純文件、一次性拋棄式變更，可不適用測試先行，但**須在回報中說明原因**。

## Test Consolidation

TDD 過程本來就會生出比最終該留的更多的測試——為了逼出 RED、為了確認某條分支走得到、為了在寫實作時有立即回饋。那些測試的價值在**當下**，不等於它有長期保存價值。全部留下來，測試套件會隨每張票膨脹，而膨脹的代價是日後每次改動都要一併修一堆對不上任何風險的測試。

**時機：GREEN 與重構完成後、驗證與 commit 之前**，檢視**本次新增或修改的**自動化測試，決定哪些留、哪些併、哪些刪。

**適用於全部層級的自動化測試**——單元測試、整合測試、UI／E2E 測試，以及日後新增的任何自動化測試型別。不要把規則綁死在特定層級。

### 唯一判準

> **這支測試是不是保護了一個獨立且有長期價值的行為或風險？**

是 → 留。否 → 才考慮合併或刪除。其餘一切（測試數量、層級分佈、驗收條件條數）都不是判準。

### 可以合併或刪除的

- **重複的 observable behavior 覆蓋** —— 兩支測試驗的是同一件對外可觀察的事，只是寫法不同。
- **同質、可參數化的 cases** —— 只有輸入值不同、斷言結構相同，併成一支參數化測試。
- **純 implementation detail／mock 互動的測試** —— 驗的是「有沒有呼叫某方法幾次」而非行為結果；對應 `/tdd` 的 implementation-coupled anti-pattern。
- **只為驅動 TDD 而存在的鷹架測試** —— 當時用來逼出 RED 或確認方向，行為已被更完整的測試涵蓋。
- **跨測試層級的重複覆蓋，且各層並未保護不同的風險。**

### 跨測試層級的重複怎麼判

同一個 observable behavior 同時被不同層級測到時，**不因為層級不同就自動全部永久保留**。逐層問它保護的是哪一種風險：

| 層級 | 它獨有的風險 |
| --- | --- |
| 單元 | 複雜的商業規則、分支與邊界 |
| 整合 | API／DB／framework 契約真的成立 |
| UI／E2E | 真實使用者流程與 wiring 接得起來 |

**各層說得出自己獨有的風險 → 全部保留**（規則本身在單元測、查詢真的下到 DB 在整合測、畫面真的接上那條路徑在 UI 測）。**說不出來、只是把同一件事再驗一次 → 留離該風險最近、回饋最可靠的那一層。**

### 護欄（防止刪過頭）

刪測試比留測試危險：多餘的測試只是慢，刪掉唯一的守門員是靜默的回歸缺口。因此：

- **驗收條件與重要的 regression 覆蓋不得因 consolidation 而遺失。** 刪或併之前先確認該行為仍有其他測試守著；**說不出是哪一支，就不准刪**。
- **只動本次新增或修改的測試。** 既有測試不在範圍內——不順手刪、不順手併。對既有測試有重複疑慮時只回報，不動手。
- **合併不得降低斷言強度。** 參數化後每個 case 驗到的東西不得比原本少；為了併得漂亮而放寬斷言，等於刪掉覆蓋。
- **判不準就留。** 留錯的成本遠低於刪錯的成本。
- **刪或併了什麼必須在該 commit 的回報中講出來**（刪了幾支、依據哪一條、該行為現在由誰守）。靜默刪測試不允許。
- consolidation 之後**必須重跑**受影響的測試確認仍是綠的，才進 commit。

### 不要留下 cleanup commit

consolidation 發生在 commit **之前**，是該 commit 的一部分。每個 implementation commit 直接包含這個行為最終值得永久保留的 production code 與自動化測試，**不要另外產生 `test: remove redundant tests` 這類收尾 commit**。TDD 中途為取得回饋而存在的暫時性測試，本來就不需要全部進 git history。

### 驗收條件與測試不是 1:1

每條驗收條件（以及規格的 `VC-xx`）都必須有**長期存在的自動化測試**守著，但：

- 一支測試可以覆蓋多條。
- 一條可以由多支測試共同保護。
- **不得為了追溯性而硬替每條驗收條件生一支專屬測試。**

要成立的是**覆蓋的可追溯性**——說得出每條由哪些測試守著；不是測試數量。下方「邊做邊記」記的就是這個對應關係，允許多對多。

### branch 層 cleanup 是例外，不是固定關卡

有些重複只有在整條 branch 收斂後才看得出來：跨多張 ticket、需求後續演進、驗收條件最終定稿、後面的實作取代了前面較細粒度的保護。這些情況才在 feature／branch 完成後另外做一輪 cleanup。

- **它是例外，不是每條 branch 必經的階段**，也不該固定產出一個 cleanup commit。沒東西可併就不要做。
- 觸發來源通常是 `to-acceptance-map` 回報的「潛在重複覆蓋」——那支 skill 只偵測、不動測試，實際修改由使用者決定怎麼進行：**只刪或併測試、不動 production code 時直接改即可，不需要為它跑任何 skill**；同時要動 production code、或範圍大到需要逐步把關時，才走 `implement-stepwise`（優先，刪測試需要 commit 關卡讓人看一眼）／`implement-oneshot`。無論哪一種都是「純實作」，**不需要跑 `to-change-request`，也不動任何規格文件**。
- **只要動了測試（刪、併、改），就必須重跑相關的驗證與覆蓋檢查**：受影響的測試專案全跑，並重跑 `to-acceptance-map` 確認沒有驗證條件因此失去覆蓋。

## 程式碼與註解

- **預設向既有程式碼看齊。** 動手前先看同目錄的既有檔案，沿用現行分層、命名慣例、錯誤處理方式與格式風格，不引入新風格、新抽象或新依賴。個人偏好一律讓位給專案現況。
  - 可偏離的情況僅限：既有寫法有明確缺陷（安全性、正確性、資源未釋放）、使用已棄用 API、既有風格本身不一致無單一慣例可循，或 ticket 已明訂不同做法。
  - **偏離時必須在回報中指出**「哪裡沒有沿用、依據哪一條理由、影響範圍」，讓使用者可當場否決。不得靜默偏離。
- **代碼層不寫需求文件編號**（`FR-xx`、`BR-xx`、`AC-xx`、`DC-xx` 等）。改為直接描述行為本身。ticket 與規格文件仍正常使用這些編號。
- **註解收斂到最少。** 只保留程式本身無法表達的約束或非顯而易見的推論，一個約束一行。刪除敘述性、提醒性、解釋本次改動理由的註解——那些屬於 commit message。測試斷言預設不加註解。

## Commit

使用 conventional commit 格式。

- 允許的 type 僅 `feat`、`fix`、`refactor`、`chore`、`test`。
- Commit type prefix 保持英文，描述以繁體中文撰寫。
- 若本次工作有已知的來源 issue 編號（例如經 `gitlab-issue-fetch` 取得的 GitLab issue），每則 commit message 都必須包含 `#<issue_number>`；純本地 ticket 無此編號時省略。
- 測試與其對應的實作屬於**同一個 commit**，不另拆。

## 收尾

一張 ticket 的全部 commit 完成後執行。**收尾是交接清單，不是稽核報告。**

### 步驟

1. **跑受影響範圍的測試** —— 本次變更所屬的測試專案／模組，不是完整測試套件。完整套件由 `to-acceptance-map` 在整條 branch 結束時跑一次，那裡才是它的位置；每張票都跑一次完整套件，在大型專案會耗掉大量時間而重複驗證同一批東西。

   **涉及多個測試專案時逐一執行，不要用 solution／workspace 層級的單一指令一次跑完。** 跨測試專案並行常因共用資料庫、連接埠、靜態狀態或測試替身而互相干擾，產生單獨跑全綠、一起跑就紅的假失敗，導致你去追一個不存在的問題。
2. **逐條核對 ticket 的 `Acceptance criteria`** —— 見下方判定規則。
3. **把核對結果寫回 ticket** —— 見下方「寫回 ticket」。
4. **回報** commit 清單、每個 commit 的測試與涵蓋的驗收條件、以及核對結果。
5. **詢問是否進行冷眼審查** —— 見下方。

### 驗收條件的判定規則

判定的是**實作有沒有做到**，不是**有沒有測試**。

| 判定 | 條件 |
| --- | --- |
| 達成 | 該行為已實作，並指出它落在哪裡（程式碼位置或測試皆可） |
| 部分達成 | 只做到一部分，明確說出缺哪一塊 |
| 未達成 | 沒做 |

- **不得因為「這條沒有對應測試」就判為未達成。** 測試覆蓋是 `to-acceptance-map` 的職責，且該處已有「不適用測試」分類承接本來就不預期有測試的項目。在收尾混用兩把尺，會產生大量假的未達成。
- 指出證據時，**程式碼位置與測試同等有效**。行為若明顯落在某個方法或畫面，指那裡即可。

### 寫回 ticket

**核對結果必須留在 ticket 檔案裡，不能只出現在對話中。** 對話會被清掉，ticket 是這張票唯一的長期紀錄；只留在 session 裡的核對，等於沒做過。

做兩件事：

**一、勾選達成的驗收條件。** 判定為「達成」的，把該條 `- [ ]` 改為 `- [x]`；部分達成與未達成維持 `- [ ]`。**只改 checkbox 狀態，條文一字不動。**

**二、在 ticket 末尾 append 一份帶證據的核對表。**

```md
## 驗收核對（YYYY-MM-DD）

| # | 判定 | 依據 |
| --- | --- | --- |
| 8 | 達成 | `DmsDeviceMovementService.Query()`；TestDmsDeviceMovementService.查詢僅納入確認狀態的工單 |
| 12 | 達成 | `Query()` 全程以 IQueryable 組條件，未先 ToList 再過濾 |
| 17 | 部分達成 | 下拉已實作，缺「退貨單」選項 |
| 19 | 未達成 | 權限攔截的整合測試未寫 |

未完成項目：#17、#19

本票 Test Consolidation：刪除 2 支僅為逼出 RED 的鷹架測試（行為由 `TestXxx.查詢僅納入確認狀態的工單` 守著）；3 條同質 case 併為 `TestXxx.各狀態的顯示文字` 一支參數化測試。
```

規則：

- **`#` 用驗收條件在該 ticket 內的出現順序**，與 `to-acceptance-map` 的 `<票號>-<項次>` 編號規則一致。
- **「依據」欄不得留空，也不得只寫「已實作」。** 要寫得出程式位置或測試名稱——**光打勾等於沒寫**，半年後回頭看一排 `[x]` 而不知道它靠什麼成立，這份紀錄就白留了。
- **只列有意義的內容，不逐條複製驗收條件原文** ——原文就在上面幾行，重抄一次是純膨脹。
- 重複執行時（例如補做未完成項目後再跑一次收尾）**就地更新同一份表**，不要 append 第二份。
- **本票有做 Test Consolidation 時，在表格後補一行摘要**（刪／併了什麼、該行為現在由誰守），依據是「邊做邊記」累積的內容。**一行帶過整張票，不逐 commit 流水帳**——逐筆紀錄 git history 已經有了，這裡要的只是讓半年後讀 ticket 的人看得出「測試變少是刻意收斂，不是漏測」。本票沒刪沒併就整行不寫，不要留一句「無」。

### 收尾**不做**什麼

以下一律不做，發現疑慮只記錄、不判定：

- **不判斷有沒有做多餘的事（scope creep）。**
- **不判斷實作是不是錯的。**
- **不評程式碼品質、重複、命名。**

理由：收尾由**寫出這段程式碼的同一個 session** 執行。它能可靠回答「我做了什麼」（回憶），但不能公正回答「我做得對不對」（判斷）——它剛剛才確信自己是對的。這三件事需要沒看過產生過程的冷眼，見下。

**一律在本 session 內完成，不得開 sub-agent。** 收尾若開 sub-agent，成本結構就等同 `/code-review`，卻沒有它的獨立性。

### 詢問冷眼審查

收尾回答「交付了什麼」，冷眼審查回答「交得對不對」。這是兩件事，收尾不替代它。回報結束時把選項給使用者，**不要自行決定**：

- **`/code-review`** —— 兩個冷啟動 sub-agent 讀 diff。實測 174,646 token，可用瘦身參數降低。
- **自己讀 `git diff <起點>...HEAD`** —— 零 token，花使用者的時間，而且使用者最懂自己專案的慣例。
- **不做** —— 逐 commit 已審查過的情況下，這是合理選項。

### 發現問題時不要就地修

收尾階段測試失敗、或有驗收條件未達成時：**不要靜默修掉再 commit**。先回報問題與影響，由使用者決定處理方式。使用者沒有看過的修改不該進 repo，那會破壞前面每個 commit 都經過確認的保證。

## 邊做邊記

每完成一個 commit，記錄本次寫出的測試以及它們涵蓋的 ticket 驗收條件編號。

- 只記**本次實際留下來**的測試（consolidation 之後的結果），不要把既有測試或已刪掉的鷹架測試算進來。
- 測試名稱寫到可直接搜尋的程度（檔名 + 測試方法名）。
- **對應關係允許多對多**：一支測試可以掛多條驗收條件，一條也可以列多支測試。不要為了讓表看起來整齊而拆測試或補測試。
- 沒有對應到任何驗收條件時（例如純重構、設定檔），寫「無」，不要硬湊。
- 驗收條件編號以該 ticket 內的出現順序為準。
- 本次有做 consolidation（刪除或合併測試）時，一併記下刪／併了什麼、該行為現在由誰守，供該 commit 的回報使用。

**這份記錄是線索，不是證明。** 它由實作者自己填寫，等同自我聲明；真正的驗證由 `to-acceptance-map` 在開發完畢後於獨立 session 執行。因此不需要為了「好看」而美化——沒寫測試就照實留空，那正是驗證階段要抓的東西。

**記錄位置由調用端 skill 指定。**
