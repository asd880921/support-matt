# 實作規範

`implement-stepwise` 與 `implement-oneshot` 共用。修改本檔會同時影響兩者。

## TDD

調用 Matt 的 **`/tdd`** skill，取得測試品質判準：好測試的定義、seam 概念、以及三個 anti-pattern（implementation-coupled、tautological、horizontal slicing）與 `tests.md`、`mocking.md` 的具體規則。這些內容不在此重複，一律以 `/tdd` 為準。

在其之上套用三條覆寫：

**覆寫 1 — seam 只確認一次。** `/tdd` 要求「寫任何測試前先寫下 seam 並與使用者確認，未確認的 seam 不得寫測試」。照字面執行會在每個 commit 前多一道詢問，與逐 commit 的節奏疊在一起造成雙重關卡。改為在流程的規劃／開場階段一次列出全部 seam 並取得確認，之後不再逐一重問。**調用端 skill 負責指定該確認發生在哪一步**；未經確認的 seam 仍然不得寫測試。

**確認過的 seam 可以修正，但不得默默擴張。** 發現原 seam 判斷錯誤、或它根本保護不到真正的行為與風險時：**會擴大測試範圍（新增 seam、多一批測試）就停下來說明並取得確認再寫**——`implement-oneshot` 沒有 commit 關卡，不停就等於默默增加 coverage；等價的位置修正（同一行為改測在更合適的 seam，測試量不增）只需回報。**不得為了遵守原計畫而在明知錯誤的 seam 上繼續堆測試**，那產出的是永遠守不住東西的測試，正是 Test Consolidation 要刪的那一類。

**覆寫 2 — 先看它失敗，且必須因為對的理由失敗。** `/tdd` 只說 "Red before green"。本規範要求：執行測試，確認它**因「功能尚未實作」而失敗**，而非因語法錯誤或環境問題而失敗。**此步驟不得跳過**——沒看過它失敗，就不知道它測的是不是對的東西。

**適用範圍是「新增或改變 observable behavior」的變更。** 是否走 TDD **不由 agent 自行判斷**：只要對外可觀察的行為有增減或改變，就一定走紅綠循環。純粹不改變行為的重構走另一條路徑，見下。

**兩條路徑：**

```text
新增或改變 observable behavior
  → RED → GREEN → REFACTOR

純 behavior-preserving refactor（行為完全不變）
  → 確認既有測試涵蓋該行為且為 GREEN → REFACTOR → 重跑，仍為 GREEN
```

- **既有 regression 測試已足以保護該行為時，不要求另外造一支 failing test。** 為了「一定要看到 RED」而替沒有新行為的重構硬生一支測試，那支測試從誕生第一天就沒有獨立的保護對象，正是 Test Consolidation 要刪的東西。
- **refactor 之前必須先跑相關的既有測試，確認是綠的。** 少了這一步，refactor 後冒出的紅燈分不清是這次弄壞的、還是本來就壞的。
- **既有覆蓋不足以保護要動的那段行為時，前置條件就不成立**：先補上守住**現行**行為的測試（它對現行程式碼應該是 GREEN，不是 RED），綠燈之後才動重構。
- **「行為有沒有變」以對外可觀察的結果為準**，不以程式碼改動幅度為準。改了一大片但輸入輸出、錯誤、副作用完全相同，是重構；只改一行卻讓某個輸入的結果不同，是行為變更。
- 判不準是哪一種時，**當作行為變更處理**，走紅綠循環。
- **這條路徑指的是「該 commit 的目的就是不改行為地整理結構」**（例如 ticket 本身是重構票）。實作中途順手重構既有程式碼，仍受**覆寫 3** 禁止——那不是走這條路徑，是不該做。

**覆寫 3 — 重構就地處理，不推給 review 階段。** `/tdd` 寫著「Refactoring is not part of the loop. It belongs to the review stage (see the `code-review` skill)」。但本套流程的 `code-review` 是選用的、可能不執行，照抄會讓重構無處可去。改為：在**剛寫出的程式碼**內、且測試保持綠燈時做最小整理。

- **不得改動本次以外的既有程式碼**（不順手重構、不改周邊命名、不調整格式或註解）。
- **預設不整理**，可直接省略此步。
- 若判斷需要較大範圍的重構，**不要就地進行**，依「暫停與回報」提出，由使用者決定。

### 例外

純設定檔、無邏輯的樣板或產生碼、純文件、一次性拋棄式變更，可不適用測試先行，但**須在回報中說明原因**。

## 測試層級

昂貴層（整合、UI／E2E，以及任何需要真實環境的型別）的每一支測試都在吃每次跑測試的時間；便宜層（單元）多幾支只是檔案長一點。**兩層的門檻是單向的**——以下規則一律只往下壓昂貴層，不反過來要求便宜層對稱減量。

### 入場規則

> **整合／UI 測試只用於單元測試無法真正驗證的部分；單元測試能完整覆蓋的行為，不在昂貴層重複建立。**

這條在**寫測試之前**就要套用，不是等到 consolidation 才拿出來決定該刪哪一支。補覆蓋缺口時尤其容易踩到：缺口通常照現象描述（「補非建單者直接呼叫端點被擋的斷言」），照字面實作就落在昂貴層，而那個行為在便宜層往往早就驗過了。

**照做，不要憑印象比對。** 每一支**打算寫在昂貴層**的測試，動手前先取它要斷言的**旗標／欄位／規則名**（例如 `CanEdit`、`WhenNotOriginator`、結案狀態），拿這個名字回**便宜層的測試類別搜尋**（方法名與斷言內容都搜）：

- **搜得到，且該行為的判斷本身屬便宜層**（見下方成本歸屬） → 改補在便宜層，昂貴層不新增。便宜層那支斷言不足時，補強它，不是到昂貴層另寫一支。
- **搜得到，但昂貴層另外驗到真實資料庫、HTTP 管線或瀏覽器 wiring** → 昂貴層留**一支**確認接線，其餘不寫。
- **搜不到** → 先問這個行為是不是本來就該由便宜層守；是就補在便宜層，不是才寫在昂貴層。

**seam 規劃階段就要逐支講出昂貴層測試的層級理由**，讓使用者在確認 seam 時看得到。那是修正層級最便宜的時點——測試寫完之後再改就是重寫。

### 成本歸屬

| 這件事 | 該由哪一層守 |
| --- | --- |
| 真實資料庫的交易、併發、實際查詢行為 | 整合 |
| HTTP 管線：驗證、授權、路由、模型繫結 | 整合，且同一種**只留一支參數化** |
| 瀏覽器上的 wiring 與真實使用者流程 | UI／E2E |
| ViewModel 的欄位、旗標、顯示文字 | **單元**——即使它最終呈現在畫面上 |
| 業務規則的分支與邊界值 | **單元** |

### 計量單位：case 數 × 環境成本

**昂貴層數的是 case 數（runner 實際執行的次數），不是測試方法數。** 一支參數化測試帶 23 個 `DataRow`，在 runner 眼中就是 23 次，執行時間與分開寫 23 支完全相同。

實跑證據：23 支昂貴層授權測試併成一支參數化之後，測試碼少了 170 行，**執行時間一秒未省**（整合測試 249 → 246，少掉的 3 次來自另一組 6 併 3——那組是真的刪掉 3 個 case）。

所以兩種成本要分開處置，不要拿其中一種的解法去解另一種：

| 成本 | 由什麼決定 | 有效的處置 |
| --- | --- | --- |
| 維護與閱讀成本 | 測試**方法**數 | 併成參數化 |
| 執行時間、以及每次跑測試在真實環境留下的資料 | **case 數 × 每個 case 的環境成本** | 刪掉不保護不同風險的 case |

- **併成參數化不減少 case 數**，不得拿「已經參數化了」當成昂貴層的成本已經處理過的說法。
- **昂貴層的 case 還有第二重成本**：每個會寫入真實資料庫的 case 都可能留下資料，之後每一次跑測試都被它拖慢。刪 case 是唯一擋得住這件事的動作。
- 便宜層的 case 幾乎不花時間也不留資料，以方法數計即可。

## Test Consolidation

TDD 過程會生出比最終該留的更多的測試——為了逼出 RED、為了確認某條分支走得到。那些測試的價值在**當下**，不等於有長期保存價值；全部留下來，測試套件會隨每張票膨脹，日後每次改動都要一併修一堆對不上任何風險的測試。

**時機：GREEN 與重構完成後、驗證與 commit 之前**，檢視**本次新增或修改的**自動化測試，決定哪些留、哪些併、哪些刪。**適用於全部層級**（單元、整合、UI／E2E，以及日後新增的任何自動化測試型別）。

```text
RED → GREEN → REFACTOR → TEST CONSOLIDATION → 驗證 → COMMIT
```

（純 behavior-preserving refactor 沒有 RED，其餘各站相同。）

### 執行清單

照順序做完這六步，細節看後面各節：

1. **列出本次新增或修改的測試。**
2. **對每一支，用它的命名尾綴／前綴搜尋整個測試類別，數出所屬家族的全員**（昂貴層數 case 數，家族裡的參數化測試帶 N 列就算 N；便宜層數方法數）→ 昂貴層達 3 個 case、便宜層達 8 支方法，就地併成參數化。
3. **本次往既有參數化測試加過 `DataRow` 時，逐列說出這一列保護什麼別列保護不到的東西**；說不出來就是同一段程式碼換輸入重跑，刪掉那一列。昂貴層單支累積達 6 列時，整支逐列複檢一次。
4. **本次新增的每一支昂貴層測試（整合、UI／E2E），逐支問「便宜層是不是已經在驗同一件事」**——取它斷言的旗標／欄位名回便宜層搜尋。是且沒多保護什麼 → 刪掉昂貴層那支；昂貴層的渲染確認至少保留一支。
5. **刪或併之前，逐項過護欄**：說得出該行為改由誰守嗎？斷言有沒有變弱？判不準嗎？三題有一題答不出來就留著。
6. **重跑受影響的測試，把刪／併了什麼寫進回報**，才進 commit。沒刪沒併也要說出留下的各守什麼。

**第 2、4 步都是「先搜尋再判斷」，不是「憑印象比對」。** 這兩步實測是整章唯一會真正減少測試的部分；跳過搜尋直接下結論，結論一律是「無」。

### 唯一判準

> **這支測試是不是保護了一個獨立且有長期價值的行為或風險？**

是 → 留。否 → 才考慮合併或刪除。其餘一切（測試數量、層級分佈、驗收條件條數）都不是判準。可處理的有五類：

- **重複的 observable behavior 覆蓋** —— 兩支驗同一件對外可觀察的事，只是寫法不同。
- **同質、可參數化的 cases** —— 只差輸入值、斷言結構相同。
- **純 implementation detail／mock 互動的測試** —— 驗「有沒有呼叫某方法幾次」而非行為結果；對應 `/tdd` 的 implementation-coupled anti-pattern。
- **只為驅動 TDD 而存在的鷹架測試** —— 行為已被更完整的測試涵蓋。
- **跨層級的重複覆蓋，且各層並未保護不同的風險** —— 見下方兩節。

### 同構家族

膨脹的主要形狀不是一個 commit 生出十支，而是**每個 commit 各生一支、生了十次**。每一支在當下都合理（它守的是這次新加的那個端點），十支疊起來卻是同一段程式碼被驗了十次——而**站在單一 commit 上永遠看不到這件事**：

```text
TestCreate_WithoutSendPermission_Returns403()
TestLookup_WithoutSendPermission_Returns403()
TestImportPost_WithoutSendPermission_Returns403()  …
```

所以視野不能只有「本次新增的測試」，還要看**它落進了哪個家族**：與同一測試類別中的既有測試**命名同型、arrange 與斷言結構相同、只差輸入值或目標**者，同屬一個家族。**先用共同的命名尾綴或前綴搜尋整個測試類別確認全員**，不要憑印象數——漏數會讓家族剛好停在門檻下。

| 家族所在層級 | 含本次在內的規模 | 處置 |
| --- | --- | --- |
| 昂貴層（整合、UI／E2E，以及任何需要真實環境的型別） | **3 個 case** | **必須**就地併成參數化，**並逐 case 問它保護的是不是別的 case 保護不到的東西**——不是的就刪掉那個 case，併方法只省維護成本，刪 case 才省執行時間 |
| 便宜層（單元） | 3–7 支方法 | **不強制**，順手就併——三五支分開寫，可讀性常勝過參數化 |
| 便宜層（單元） | **8 支方法以上** | 併成參數化。這規模的維護成本已追上昂貴層 |

- **昂貴層的規模以 case 數計**（見「計量單位」）：家族裡若已有一支參數化測試帶 4 列，家族就已經是 4 個 case，本次再加一支就是 5 個，不是 2 支。
- 這是「只動本次新增或修改的測試」的**唯一例外**：允許把既有的同型成員一起併進來，其餘既有測試仍不准動。
- **昂貴層家族只有 2 個 case 時不動**——分不出是模式還是巧合，太早併反而讓下一支不知道該加在哪。
- 併完**整個測試類別重跑**，確認每個 case 都還在、都是綠的；**斷言不得比原本弱**，做不到就維持原樣並在回報中說明。

### 已參數化的測試會繼續長

家族門檻只在「多支同型方法」這個形狀上觸發。收斂成一支參數化測試之後，同一段程式碼再多驗十種輸入，也只是那支測試多十列 `DataRow`——**方法數不再變動，門檻永遠不會再觸發，膨脹從此是隱形的**。收斂反而讓後續的膨脹更難被看見。

所以每次往既有的參數化測試加 `DataRow` 時：

- **逐列說得出這一列保護什麼別列保護不到的東西**（不同的規則分支、不同的邊界值、不同的錯誤訊息）。說不出來，它就是同一段程式碼換輸入重跑，不要加。
- **昂貴層單支測試的 `DataRow` 累積達 6 列**（便宜層 50 列）時，停下來把整支逐列複檢一次，把只是換輸入重跑的列刪掉。**刪的是列，不是方法**——這是唯一能真正減少執行時間的動作。
- **昂貴層刪列時，同一種檢查保留一支參數化、涵蓋具代表性的少數列即可**（例如各端點的 401／403 留一到兩列），規則本身的完整分支由便宜層守。
- 逐列複檢與刪列同樣受下方「護欄」節管：斷言不得因此變弱，說不出該行為改由誰守就不刪，判不準就留。
- **刪了哪幾列、留下的各保護什麼，要寫進該 commit 的回報**，與刪測試方法一樣不允許靜默進行。

### 跨測試層級的重複

同一個 observable behavior 被不同層級測到時，**不因為層級不同就自動全部保留**。依「測試層級」的成本歸屬表判斷：**昂貴層的每一支都要說得出「便宜層驗不到的是什麼」，說不出來就不留；反過來不成立，不要為了對稱去砍單元測試。**

入場規則沒攔住的，在這裡攔第二次——差別只在時點：入場規則在寫之前，這一節在寫完之後。

典型誤置：`CreateDetailModel_DraftWithoutSendPermission_HidesEdit`（單元）與 `Detail_DraftWithoutSendPermission_HidesEditEntry`（整合）驗的是同一個旗標。旗標怎麼算屬於單元層；昂貴層只需要**一支**確認「該頁真的依旗標渲染」。

### 護欄（防止刪過頭）

刪測試比留測試危險：多餘的測試只是慢，刪掉唯一的守門員是靜默的回歸缺口。

- **驗收條件與重要的 regression 覆蓋不得因 consolidation 而遺失。** 刪或併之前先確認該行為仍有其他測試守著；**說不出是哪一支，就不准刪**。
- **只動本次新增或修改的測試**，既有測試有疑慮時只回報不動手（唯一例外是上面的同構家族參數化，且僅限併入同型成員）。
- **合併不得降低斷言強度。** 為了併得漂亮而放寬斷言，等於刪掉覆蓋。
- **判不準就留。** 留錯的成本遠低於刪錯的成本。
- **刪或併了什麼必須在該 commit 的回報中講出來**（幾支、依據哪一條、該行為現在由誰守）。靜默刪測試不允許。
- consolidation 之後**必須重跑**受影響的測試確認仍是綠的，才進 commit。

### 不要留下 cleanup commit

consolidation 是該 commit 的一部分，發生在 commit **之前**。每個 implementation commit 直接包含這個行為最終值得永久保留的 production code 與測試，**不要另外產生 `test: remove redundant tests` 這類收尾 commit**——TDD 中途為取得回饋而生的暫時性測試，本來就不需要進 git history。

### 驗收條件與測試不是 1:1

**該由測試守的**驗收條件（以及規格的 `VC-xx`）必須有長期存在的自動化測試守著。哪些該由測試守在 seam 確認時就決定了，**不是每一條都算**——`to-acceptance-map` 另有「不適用測試」一格承接本來就不預期有測試的項目。在該有測試的那些條目上：一支測試可以覆蓋多條，一條也可以由多支共同保護，**不得為了追溯性而硬替每條生一支專屬測試**。要成立的是**覆蓋的可追溯性**（說得出每條由哪些測試守著），不是測試數量；「邊做邊記」記的就是這個對應關係，允許多對多。

### branch 層 cleanup 是例外，不是固定關卡

有些重複只有在整條 branch 收斂後才看得出來：跨多張 ticket、需求後續演進、後面的實作取代了前面較細粒度的保護。這些情況才在 feature／branch 完成後另外做一輪。

- **它是例外，不是每條 branch 必經的階段**，也不該固定產出一個 cleanup commit。沒東西可併就不做。
- 觸發來源通常是 `to-acceptance-map` 回報的「潛在重複覆蓋」（該 skill 只偵測、不動測試）。**只刪或併測試、不動 production code 時直接改即可，不需要為它跑任何 skill**；要同時動 production code 或範圍大到需要逐步把關時，才走 `implement-stepwise`（優先，刪測試需要關卡讓人看一眼）／`implement-oneshot`。兩種都算「純實作」，**不跑 `to-change-request`、不動規格文件**。
- **只要動了測試（刪、併、改），就必須重跑相關的驗證與覆蓋檢查**：受影響的測試專案全跑，並重跑 `to-acceptance-map` 確認沒有驗證條件因此失去覆蓋。

## 程式碼與註解

- **預設向既有程式碼看齊。** 動手前先看同目錄的既有檔案，沿用現行分層、命名慣例、錯誤處理方式與格式風格，不引入新風格、新抽象或新依賴。個人偏好一律讓位給專案現況。
  - 可偏離的情況僅限：既有寫法有明確缺陷（安全性、正確性、資源未釋放）、使用已棄用 API、既有風格本身不一致無單一慣例可循，或 ticket 已明訂不同做法。
  - **偏離時必須在回報中指出**「哪裡沒有沿用、依據哪一條理由、影響範圍」，讓使用者可當場否決。不得靜默偏離。
- **代碼層不寫需求文件編號**（`FR-xx`、`BR-xx`、`AC-xx`、`DC-xx` 等）。改為直接描述行為本身。ticket 與規格文件仍正常使用這些編號。
- **註解收斂到最少。** 只保留程式本身無法表達的約束或非顯而易見的推論，一個約束一行。刪除敘述性、提醒性、解釋本次改動理由的註解——那些屬於 commit message。測試斷言預設不加註解。

## Commit

使用 conventional commit 格式。

- 允許的 type 僅 `feat`、`fix`、`refactor`、`chore`、`test`。
- Commit type prefix 保持英文，描述以繁體中文撰寫。
- 若本次工作有已知的來源 issue 編號（例如經 `gitlab-issue-fetch` 取得的 GitLab issue），每則 commit message 都必須包含 `#<issue_number>`；純本地 ticket 無此編號時省略。
- 測試與其對應的實作屬於**同一個 commit**，不另拆。

## 收尾

一張 ticket 的全部 commit 完成後執行。**收尾是交接清單，不是稽核報告。**

### 步驟

1. **跑受影響範圍的測試** —— 本次變更所屬的測試專案／模組，不是完整測試套件。完整套件由 `to-acceptance-map` 在整條 branch 結束時跑一次，那裡才是它的位置；每張票都跑一次完整套件，在大型專案會耗掉大量時間而重複驗證同一批東西。

   **涉及多個測試專案時逐一執行，不要用 solution／workspace 層級的單一指令一次跑完。** 跨測試專案並行常因共用資料庫、連接埠、靜態狀態或測試替身而互相干擾，產生單獨跑全綠、一起跑就紅的假失敗，導致你去追一個不存在的問題。
2. **跨層重複檢查** —— 見下方。
3. **逐條核對 ticket 的 `Acceptance criteria`** —— 見下方判定規則。
4. **把核對結果寫回 ticket** —— 見下方「寫回 ticket」。
5. **回報** commit 清單、每個 commit 的測試與涵蓋的驗收條件、以及核對結果。
6. **詢問是否進行冷眼審查** —— 見下方。

### 跨層重複檢查

commit 前的 consolidation 有個看不到的死角：**同一個行為的單元測試與整合／UI 測試通常寫在不同的 commit 裡**（先寫 service 與它的單元測試，過幾個 commit 才寫端點與它的整合測試）。站在任何一個 commit 上，另一層都還不存在或已經是「既有測試」，所以跨層重複永遠不會被當場發現。

**收尾是這張票唯一兩層都寫完的時點**，所以在這裡做一次，範圍限定**本票新增的昂貴層測試**（整合、UI／E2E，以及日後任何需要真實環境的測試型別）：

逐支問一句——**便宜的那一層是不是已經在驗同一件事？**

- **是，而且昂貴層那支沒有多保護什麼** → 刪掉昂貴層那支。
- **是，但昂貴層另外驗到了真實資料庫、HTTP 管線或瀏覽器 wiring** → 兩支都留，並在回報中說出昂貴層那支多保護了什麼。
- **否** → 留著。
- 同一種昂貴層檢查出現 3 支以上（例如每個端點各一支 401／403）→ **併成一支參數化**，依「同構家族」處理。

規則：

- **只看本票新增的昂貴層測試**，不掃既有的、也不動單元測試——單元測試多幾支不是問題，這一步不是來砍它們的。
- 刪或併之後**重跑該測試專案**，不是只跑剩下的那幾支。
- **結果要寫進回報**：本票在昂貴層留下幾支、各自保護什麼便宜層測不到的東西；刪了哪幾支、原因是什麼。**一支都沒刪時也要講出留下的那些各保護什麼**——這一步的價值在於逼出那句話，不在於刪掉東西。
- 判不準就留，並在回報中點名，讓使用者決定。

### 驗收條件的判定規則

判定的是**實作有沒有做到**，不是**有沒有測試**。

| 判定 | 條件 |
| --- | --- |
| 達成 | 該行為已實作，並指出它落在哪裡（程式碼位置或測試皆可） |
| 部分達成 | 只做到一部分，明確說出缺哪一塊 |
| 未達成 | 沒做 |

- **不得因為「這條沒有對應測試」就判為未達成。** 測試覆蓋是 `to-acceptance-map` 的職責，且該處已有「不適用測試」分類承接本來就不預期有測試的項目。在收尾混用兩把尺，會產生大量假的未達成。
- 指出證據時，**程式碼位置與測試同等有效**。行為若明顯落在某個方法或畫面，指那裡即可。

### 寫回 ticket

**核對結果必須留在 ticket 檔案裡，不能只出現在對話中。** 對話會被清掉，ticket 是這張票唯一的長期紀錄；只留在 session 裡的核對，等於沒做過。

做兩件事：

**一、勾選達成的驗收條件。** 判定為「達成」的，把該條 `- [ ]` 改為 `- [x]`；部分達成與未達成維持 `- [ ]`。**只改 checkbox 狀態，條文一字不動。**

**二、在 ticket 末尾 append 一份帶證據的核對表。**

```md
## 驗收核對（YYYY-MM-DD）

| # | 判定 | 依據 |
| --- | --- | --- |
| 8 | 達成 | `DmsDeviceMovementService.Query()`；TestDmsDeviceMovementService.查詢僅納入確認狀態的工單 |
| 12 | 達成 | `Query()` 全程以 IQueryable 組條件，未先 ToList 再過濾 |
| 17 | 部分達成 | 下拉已實作，缺「退貨單」選項 |
| 19 | 未達成 | 權限攔截的整合測試未寫 |

未完成項目：#17、#19

本票 Test Consolidation：刪除 2 支僅為逼出 RED 的鷹架測試（行為由 `TestXxx.查詢僅納入確認狀態的工單` 守著）；3 條同質 case 併為 `TestXxx.各狀態的顯示文字` 一支參數化測試。
```

規則：

- **`#` 用驗收條件在該 ticket 內的出現順序**，與 `to-acceptance-map` 的 `<票號>-<項次>` 編號規則一致。
- **「依據」欄不得留空，也不得只寫「已實作」。** 要寫得出程式位置或測試名稱——**光打勾等於沒寫**，半年後回頭看一排 `[x]` 而不知道它靠什麼成立，這份紀錄就白留了。
- **只列有意義的內容，不逐條複製驗收條件原文** ——原文就在上面幾行，重抄一次是純膨脹。
- 重複執行時（例如補做未完成項目後再跑一次收尾）**就地更新同一份表**，不要 append 第二份。
- **本票有做 Test Consolidation 時，在表格後補一行摘要**（刪／併了什麼、該行為現在由誰守），依據是「邊做邊記」累積的內容。**一行帶過整張票，不逐 commit 流水帳**——逐筆紀錄 git history 已經有了，這裡要的只是讓半年後讀 ticket 的人看得出「測試變少是刻意收斂，不是漏測」。本票沒刪沒併就整行不寫，不要留一句「無」。

### 收尾**不做**什麼

以下一律不做，發現疑慮只記錄、不判定：

- **不判斷有沒有做多餘的事（scope creep）。**
- **不判斷實作是不是錯的。**
- **不評程式碼品質、重複、命名。**

理由：收尾由**寫出這段程式碼的同一個 session** 執行。它能可靠回答「我做了什麼」（回憶），但不能公正回答「我做得對不對」（判斷）——它剛剛才確信自己是對的。這三件事需要沒看過產生過程的冷眼，見下。

**一律在本 session 內完成，不得開 sub-agent。** 收尾若開 sub-agent，成本結構就等同 `/code-review`，卻沒有它的獨立性。

### 詢問冷眼審查

收尾回答「交付了什麼」，冷眼審查回答「交得對不對」。這是兩件事，收尾不替代它。回報結束時把選項給使用者，**不要自行決定**：

- **`/code-review`** —— 兩個冷啟動 sub-agent 讀 diff。實測 174,646 token，可用瘦身參數降低。
- **自己讀 `git diff <起點>...HEAD`** —— 零 token，花使用者的時間，而且使用者最懂自己專案的慣例。
- **不做** —— 逐 commit 已審查過的情況下，這是合理選項。

### 發現問題時不要就地修

收尾階段測試失敗、或有驗收條件未達成時：**不要靜默修掉再 commit**。先回報問題與影響，由使用者決定處理方式。使用者沒有看過的修改不該進 repo，那會破壞前面每個 commit 都經過確認的保證。

## 邊做邊記

每完成一個 commit，記錄本次寫出的測試以及它們涵蓋的 ticket 驗收條件編號。

- 只記**本次實際留下來**的測試（consolidation 之後的結果），不要把既有測試或已刪掉的鷹架測試算進來。
- 測試名稱寫到可直接搜尋的程度（檔名 + 測試方法名）。
- **對應關係允許多對多**：一支測試可以掛多條驗收條件，一條也可以列多支測試。不要為了讓表看起來整齊而拆測試或補測試。
- 沒有對應到任何驗收條件時（例如純重構、設定檔），寫「無」，不要硬湊。
- 驗收條件編號以該 ticket 內的出現順序為準。
- 本次有做 consolidation（刪除或合併測試）時，一併記下刪／併了什麼、該行為現在由誰守，供該 commit 的回報使用。

**這份記錄是線索，不是證明。** 它由實作者自己填寫，等同自我聲明；真正的驗證由 `to-acceptance-map` 在開發完畢後於獨立 session 執行。因此不需要為了「好看」而美化——沒寫測試就照實留空，那正是驗證階段要抓的東西。

**記錄位置由調用端 skill 指定。**
