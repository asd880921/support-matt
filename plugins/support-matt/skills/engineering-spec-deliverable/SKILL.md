# engineering-spec-deliverable

把 `to-engineering-spec` 產出的**工作版** `engineering-spec.md`，轉成一份**可獨立閱讀的交付版**，寫入 `<原檔名>_deliverable.md`。

## 工作流位置

本 skill 與 `to-engineering-spec` 一樣，服務的是 Matt 的流程：

```text
grill-with-docs → to-spec → [to-engineering-spec] → 人工確認 → to-tickets → implement → code-review → [to-engineering-spec 定稿]
                                                          ↘                                              ↘
                                                    [engineering-spec-deliverable] ←── 隨時可跑 ──────────┘
```

**它不是固定步驟。** 使用者想把規格貼上公司 GitLab Issue 時就跑一次；文件之後又改了，再跑一次覆蓋掉。工作版留在管線裡繼續被 `to-tickets` 與 `implement` 使用，交付版只給人看。

**只處理 `engineering-spec.md`。** 拿到其他型別的規格文件時停下來告知使用者，不要硬套——三項轉換都綁定這份文件的章節結構（三層約束程度、BR 引用 ADR、最後一章 handoff）。

## 為什麼需要轉換

工作版刻意帶著三樣東西。它們在管線裡都是必要的，貼上 Issue 後卻全部失效：

| 工作版有的 | 為什麼工作版需要它 | 貼上 Issue 後 |
| --- | --- | --- |
| `[spec.md](./spec.md)` 等本地相對連結 | 需求的權威在 Matt Spec，不複製才不會分岔 | 死連結。讀者點不開，也不知道被引用的內容是什麼 |
| ADR 編號引用（`docs/adr/0007-xxx.md`） | 決策理由的權威在 ADR，不複製 | 讀者只看到一個編號 |
| 最後一章「交給 to-tickets」 | `to-tickets` 靠它辨認三種約束程度 | 內部工作註記，人類審查者不需要，整章移除 |

**不要回頭去工作版把它們拿掉**——那會讓下游 Agent 失去引用與 handoff。正解是留著工作版，另外產一份交付版。

## 安全邊界

- **原始文件完全不異動。** 所有轉換只發生在新檔 `<原檔名>_deliverable.md`（與來源同目錄）。使用者可以繼續在工作版上修訂，再重新產一次交付版。
- **同名交付版已存在時直接覆蓋**（那正是「修訂後重產」的情境）；使用者另有指示時依其指示。
- **一次處理一份**，由使用者個別調用。不自行掃描目錄批次處理。
- **不改寫需求、不重新設計技術內容、不補缺漏的分析。** 遇到內容有問題（規則矛盾、缺少必要細節），**停下來告知使用者回 `to-engineering-spec` 修訂**，不要在交付版上就地修好——那會讓兩份文件分岔。
- 不呼叫 `gitlab-issue-write`、不呼叫 `gh issue` / `glab`、不建立或修改任何遠端 Issue。**產出本地檔案就停止**，由使用者自己貼上。
- 除非使用者明確要求自動化，不要寫或執行轉換腳本。

## 三項轉換

### 一、引用內嵌化

交付版的判準是：**讀者手上只有這一份文件，讀完不必去找別的東西。**

| 工作版 | 交付版 |
| --- | --- |
| `見 [spec.md](./spec.md) User Story 12` | `見需求規格 User Story 12：退回後申請人可修改並重送`（拿掉連結，保留摘要，補足夠的上下文） |
| `需求細節見 [spec.md](./spec.md)` | 換成一句實質說明；若原文只有這句話而無實質內容，改寫成該處真正需要交代的一句 |
| `相關 ADR：docs/adr/0007-inventory-lock.md` | 保留檔名作為追溯線索，**並把該 ADR 的決策與理由攤回它所服務的那條 BR 或設計決策的內文** |
| `> **設計決策**：…（理由：見 ADR-0007）` | `> **設計決策**：…（理由：<ADR-0007 的理由全文>）` |

規則：

- **連結一律移除，摘要一律保留並補足。** 工作版的引用本來就要求「編號 + 一句摘要」；交付版把那句摘要擴寫到「不看被引用的文件也讀得懂」為止。
- **ADR 的理由攤回內文。** 這是交付版唯一允許「複製」的地方——因為交付版不是單一事實來源體系的一部分，它是一份快照。
- **文件內部的編號引用（`BR-07`、`DC-03`、動作名稱、判斷式名稱）照原樣保留。** 那些指向的是同一份文件裡的章節，讀者找得到。
- 「文件資訊」表的 `Matt Spec` 一列：把相對連結換成需求文件的名稱與一句定位；已知公司 Issue 編號時改填該編號。

### 二、移除最後一章

把「交給 to-tickets」**整章刪除**——它從頭到尾都是講給下游 Agent 聽的。

- **不寫替代章節。** 不補一章「約束程度的解讀方式」或任何等價的說明表；`設計決策` / `實作方向` 的字面已經說明了強度，「非固定簽章」也標在程式碼區塊自己身上。
- **章內的內容不搬到別處。** 需要讓讀者知道的約束，本來就該由 `to-engineering-spec` 寫進正文，不是在交付版現場補。
- 刪完後正文最後一章是「驗證條件」，**位置不動**。其後只剩附錄（偏差與待處理、修訂紀錄）。
- 內文各處的 `> **設計決策**：` / `> **實作方向**：` 引用區塊**原樣保留**，一個都不動。

### 三、移除內部工作註記

只移除以下項目，其餘一字不動：

- `$to-tickets ...`、`$to-spec ...` 等指令行，以及任何「下一步請執行 …」的操作提示。
- 明確的 Agent 工作痕跡：`.scratch/` 路徑、`feature-slug`、skill 名稱、`文件狀態` 之外的流程狀態標記。
- **`文件狀態` 一列**：保留。它對審查者有意義（這份規格是定稿還是還在設計中），但值只留 `分析中 / 設計中 / 可拆 Ticket / 定稿` 與日期，`可拆 Ticket` 改寫為 `設計完成`。

## 必須原封不動保留的內容

以下任何一項在交付版消失，就是這次轉換失敗：

- 任何一條錯誤訊息原文。
- 任何一次狀態轉移，包含自環。
- 任何一個併發、交易或原子性約束。
- 任何一條權限、依賴條件與例外角色。
- 任何一個邊界值、預設值、格式限制、欄位必填性。
- **「驗證條件」章整章保留，逐條不得刪減、合併或改寫**，包含每條的前提、可觀察結果、依據編號與驗證方式。這一章條目多、句式重複、粒度細，**是全文件最容易被順手摘要掉的內容**——它同時是審查者判定交付是否成立的唯一依據，少一條就少一個驗收點。
- 任何一項設計決策的理由與被排除的替代方案。
- 「待釐清事項」章節——**仍有實質未釐清項目時整章保留**（審查者需要知道哪些還沒定），僅在整章為空或只有 `目前無待釐清事項`、`無`、`已全部釐清` 這類佔位內容時才整章移除。
- 「偏差與待處理」附錄（定稿模式產生）。這是文件最有價值的內容之一：它讓「規格與實作不一致」變成被看見的事。
- 「修訂紀錄」附錄——有實質內容時保留，空的或只有佔位列時移除。
- 所有 mermaid 圖、表格、程式識別符與既有用字遣詞。

**這份 skill 的職責是換一種呈現方式，不是收斂內容。** 覺得某段太冗長、某條 BR 該搬家，那是 `to-engineering-spec` 的事，回去那邊改。

## 工作流程

1. 確認來源檔路徑（通常 `.ai/.scratch/<feature-slug>/engineering-spec.md`）。使用者直接貼上內容時，跳過檔案處理，最後回傳轉換後的 Markdown。
2. **完整讀過來源文件**，不只掃描標題。三項轉換都需要理解內容才做得對，尤其是引用摘要的擴寫。
3. 需要攤回理由時，讀「文件資訊」列出的每一則 ADR。**ADR 讀不到（檔案不存在、路徑錯）時停下來問使用者**，不要編一個理由。
4. 把來源完整複製成 `<原檔名>_deliverable.md`，後續所有轉換只在這份副本上進行。
5. 依序執行三項轉換。
6. 若因移除章節造成中文章節序號跳號或不連續，依實際保留的同層 `##` 章節順序重編序號——只改序號，不改標題文字與章節順序。
7. 逐項驗證（見下）。
8. 停止。回報交付版路徑、做了哪些轉換、以及**仍存在的待釐清事項與偏差**（若有），提醒使用者這些會一起被貼上 Issue。

## 驗證

寫完後逐項確認：

- 全文沒有 `](./`、`](../` 這類本地相對連結；`docs/adr/` 只作為追溯線索出現，其理由已在內文。
- 沒有 `$to-tickets`、`$to-spec`、`.scratch/`，沒有 `to-tickets` / `implement` / `code-review` / `to-engineering-spec` 等 skill 名稱。
- 正文最後一章是「驗證條件」，位置沒有被移動；沒有多出任何解釋約束程度的新章節。
- **`VC-xx` 逐條計數，與來源檔完全相同**，且編號連續無缺號。這是本 skill 唯一能做精確計數的驗證，比抽樣強，成本是零——不要略過。
- 「待釐清事項」的去留符合規則；仍有項目時整章還在。
- 「偏差與待處理」若原本存在，仍在。
- 中文章節序號連續、無重號。
- 隨機抽 3 條錯誤訊息、2 個邊界值、2 條設計決策理由，比對來源檔——內容一字未改。
- **對照來源檔的行數**：扣掉最後一章的篇幅後，交付版應與來源**相當或略長**（理由攤回內文、摘要擴寫）。若明顯變短，代表誤刪了內容，回頭查。

## 輸出

- 有檔案路徑：寫入 `<原檔名>_deliverable.md`（與來源同目錄），回報新檔路徑。使用者另指定檔名或目錄時依其指示。
- 使用者貼上內容（無路徑）：直接回傳轉換後的 Markdown，不建檔。
- 兩種情況都**不自行調用其他 skill、不寫任何遠端 Issue**。
