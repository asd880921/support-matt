# to-acceptance-map

整條 branch 的 ticket 全部完成後，盤點**自動化測試對驗收項目的覆蓋情形**，產出一份可追溯的對應清單。

## 為什麼要獨立執行

`implement-stepwise` 在每個 commit 完成時會記錄「本次寫了哪些測試、涵蓋哪幾條驗收條件」。**那份記錄是實作者的自我聲明，不是證據。**

本 skill 的價值來自獨立性：在**乾淨的新 session** 執行，不帶開發過程的 context，逐項自行確認測試確實存在、且真的涵蓋該項目。

ticket 裡有兩處實作者留下的記錄——Commit checklist 的 `tests` 行，以及收尾寫回的「驗收核對」表——**兩者都只當搜尋線索使用**。依它們去定位測試很有效率，但**必須自行開啟測試確認內容**，不得直接採信。同理，**驗收條件的 checkbox 是否已被勾選，不影響本 skill 的判定**：勾選代表實作者認為做到了，與「有沒有測試守著」是兩回事。

記錄與實際不符時，以實際為準，並在報告中指出落差。

## 唯讀規範（最高優先）

- **只建立或覆寫 `acceptance-map.md` 一個檔案。**
- 對 ticket 檔案、`engineering-spec.md`、`spec.md`、功能程式碼、測試程式**一律唯讀**。
- **不補寫任何測試、不修改任何程式碼、不修改設計文件、不勾選任何 checklist。**
- 發現缺漏時只回報，由使用者決定後續處理。
- **唯讀指的是不修改檔案，不是不執行。** 本 skill 會執行測試（步驟 3），那是判定的必要依據；範圍由使用者選擇。

## 執行流程

### 1. 取得範圍

從使用者指定的 feature 目錄取得（路徑依 `.ai/docs/agents/issue-tracker.md` 的慣例，通常是 `.ai/.scratch/<feature>/`）：

- `issues/` 底下全部 ticket 檔案
- `engineering-spec.md`（若存在）

未指定時，依當前 git 分支名稱推斷對應的 feature 目錄；推斷不出來就停下來問，不要猜。

若仍有 ticket 的 Commit checklist 未全部勾完，**先回報並確認**是否仍要繼續盤點——對未完成的 branch 盤點，結果會大量出現「需補測試」而失去意義。

### 2. 匯集驗收項目

兩個來源都要納入：

- **各 ticket 的驗收條件** —— ticket 檔案中的 checkbox 項目。以 `<ticket 編號>-<項次>` 作為識別（例如 `01-08`）。
- **`engineering-spec.md` 的全域實作約束** —— DC 表格全部列，沿用其 `DC-xx` 編號。

**全域實作約束必須全部納入，包含從未被任何 ticket 吸收的項目。** 這正是本 skill 存在的理由之一：以否定式陳述表達的約束（「未使用 X」「未產生 Y」）在拆票時容易蒸發，因為它們演示不出來；feature 層級的盤點是它們唯一的回收點。

同理，**橫跨多張 ticket 的項目**（例如「查詢與匯出走同一個取資料的方法」）在任何單張 ticket 的收尾都驗不到，只有這裡驗得到。

### 3. 執行測試

#### 3.1 先問使用者要跑多大範圍

**不要自行決定，一律先問。** 有些專案跑完全部測試要很久，那個時間成本該由使用者決定值不值得：

```text
盤點前要跑哪個範圍的測試？
  1. 全部測試專案 —— 最完整，但可能耗時很久
  2. 只跑本次 branch 受影響的測試專案 —— 快，但未受影響的專案不會被驗證
  3. 不跑，直接用現況盤點 —— 最快，但無法確認測試是綠是紅，
     「已涵蓋」的判定會降級為「測試存在」而非「測試通過」

發現的測試專案：<列出偵測到的專案清單與各自大略規模>
```

選 3 時，在 `acceptance-map.md` 開頭明確標註「本次未執行測試，覆蓋判定僅依測試存在與斷言內容」。

#### 3.2 測試專案必須逐一執行，不得整個 solution 一次跑

**這是硬規則。** 跨測試專案並行執行時，常因共用資料庫、連接埠、靜態狀態或測試替身而互相干擾，產生**單獨跑全綠、一起跑就紅**的假失敗。實測案例：

| 專案 | 單獨執行 | 整個 solution 一次跑 |
| --- | --- | --- |
| UnitTest | 553 通過 / 4 略過 | **3 失敗** |
| IntegrationTests | 35 通過 | **21 失敗** |

拿這種假失敗去判定覆蓋，會把大量「已涵蓋」誤降為「覆蓋不足」，整份盤點就廢了。

因此：**先列出測試專案清單，再一個一個跑，分別記錄結果。** 不要用 solution 層級的單一指令一次跑完。

#### 3.3 失敗的處理

- **測試存在但是紅的，不得判為「已涵蓋」。** 判為「覆蓋不足」並在備註註明它目前失敗。
- **不要假設失敗都是本次 branch 造成的。** 專案可能本來就有既有失敗（例如 UI/E2E 測試因環境因素長期紅燈）。發現失敗時**列出來問使用者**哪些是既有的，既有失敗不影響該項目的覆蓋判定，只在備註標明。
- 本次 branch 明顯造成的失敗數量多到無法逐一歸屬時，**停下來回報**，請使用者先修好再盤點。

本步驟只**執行**測試，不修改任何測試或程式碼，不牴觸唯讀規範。

### 4. 逐項比對測試

對每一個驗收項目，找出涵蓋它的自動化測試——單元測試、整合測試、UI/E2E 測試皆計入。

探索方式：若專案已建立程式碼知識圖譜或等效索引工具（讀 `CLAUDE.md` / `AGENTS.md` 的宣告，或檢查可用的 MCP 工具判斷），**優先用它定位測試與被測目標**，再針對性讀取；本 skill 不指定使用哪一套。這是一次 feature 層級的全面盤點，靠 grep 加整檔閱讀會迅速累積大量無用 context。

判定四分類：

| 判定 | 條件 |
| --- | --- |
| **已涵蓋** | 存在測試，且其斷言確實驗證該項目所述的行為或約束 |
| **覆蓋不足** | 有相關測試，但只驗到部分條件、只測快樂路徑、或斷言不足以判定該項目成立 |
| **需補測試** | 沒有測試，**而且該由測試守** —— 這是真正的缺口 |
| **不適用測試** | 沒有測試，**而測試本來就不是這條的適當證據** —— 需人工或靜態檢查 |

### 為什麼要分開最後兩級

上游的驗收條件是以 Matt 的標準產生的，而 Matt 的 `/tdd` 明文寫著「**You can't test everything** —— 測試力氣要投在關鍵路徑與複雜邏輯，不是每一個邊界值」，且測試的單位是**議定的 seam**，不是驗收條目。因此**清單中本來就有相當比例的項目不預期有測試**，那是設計如此，不是缺陷。

把這兩者混為同一格，會讓報告出現大量誤報，使用者很快就會整份忽略——**一個常常誤報的驗證工具比沒有更糟**。

### 「不適用測試」的護欄（防止它變成垃圾桶）

- **必須逐項寫出理由**，不得只標分類不說明。
- **只有下列性質的項目可以判為「不適用測試」**：
  - 結構性約束（「四道判定全部在資料庫執行」「未使用含系統倉短路的授權判斷式」「三處共用同一個運算式」）——測試看不到實作走哪條路徑。
  - 純視覺或版面（欄位排列位置、樣式）。
  - 元條件（「單元測試涵蓋上述規則」這類講實作方式而非系統行為的項目）。
  - 需要真實外部環境才成立、專案未建置該層測試的項目。
- **使用者可觀察的行為一律不得判為「不適用測試」。** 錯誤訊息文字、必填驗證、資料是否出現在結果中、排序、分頁、預設值——這些都測得到，沒測就是「需補測試」。判斷困難時，**一律放進「需補測試」**，讓使用者自己決定要不要補。

### 其他判定原則

- **以斷言為準，不以測試名稱為準。** 名稱寫得像、但斷言沒驗到的，是「覆蓋不足」。
- **不把「程式碼看起來有實作」當成已涵蓋。** 本 skill 盤點的是測試覆蓋，不是實作完成度。
- 不要為了讓表格好看而勉強對應一個不相干的測試。

### 5. 寫出 `acceptance-map.md`

寫入 feature 目錄下的 `acceptance-map.md`（與 `issues/` 同層）。既有檔案直接覆寫——本 skill 可重複執行，每次都反映當下狀態。

```md
# 驗收覆蓋盤點：<feature>

- 分支：<branch-name>
- 盤點時間：<YYYY-MM-DD>
- 來源：issues/01..NN、engineering-spec.md 全域實作約束

## 摘要

| 判定 | 數量 |
| --- | --- |
| 已涵蓋 | N |
| 覆蓋不足 | N |
| **需補測試** | N |
| 不適用測試 | N |

**需要處理的只有「覆蓋不足」與「需補測試」兩欄。**

## 驗收條件（來自 ticket）

| 編號 | 驗收項目 | 判定 | 對應測試 | 備註 |
| --- | --- | --- | --- | --- |
| 01-08 | <驗收條件原文> | 已涵蓋 | `TestXxx.某測試方法` | |
| 01-09 | <驗收條件原文> | 覆蓋不足 | `TestXxx.某測試方法` | 只驗了快樂路徑，邊界值未測 |

## 全域實作約束（來自 engineering-spec.md）

| 編號 | 約束 | 判定 | 對應測試 | 備註 |
| --- | --- | --- | --- | --- |
| DC-02 | <約束原文> | 不適用測試 | — | 結構性約束：測試看不到查詢走 DB 還是記憶體，需靜態檢查 |
| DC-05 | <約束原文> | 需補測試 | — | 未被任何 ticket 吸收，但候選清單條件是可觀察行為 |

## 與 checklist 記錄的落差

| 位置 | checklist 記錄 | 實際 |
| --- | --- | --- |
| 01 commit 2 | `TestXxx.某測試` 涵蓋 #12 | 該測試存在，但斷言未涉及 #12 |

<沒有落差時寫「無落差」。>

## 待處理

- 依序列出「覆蓋不足」與「需補測試」的項目編號，供使用者決定補測試或判定為不適用。
- 「不適用測試」的項目另列一份，標明各自建議的檢查方式（人工檢視、靜態檢查、code review），不混在待處理裡。
```

### 6. 回報

**回報只呈現例外，不要把完整清單複述一遍。** 檔案本身保留全部項目（它是日後可查詢的追溯表），但貼給使用者的內容只有：

1. 摘要數字（四個判定各幾項）。
2. **「覆蓋不足」與「需補測試」的完整條列** —— 這是使用者真正要看的。
3. 「不適用測試」只給數量與一句歸類說明，不逐條列出；使用者要細節時再開檔案看。
4. 「與 checklist 記錄的落差」若有，全部列出。

一份 60 項的盤點，使用者需要讀的通常不到 10 項。把 50 項「已涵蓋」貼給他，只會讓他整份跳過。

最後明確告知：本 skill **未修改任何程式或文件**，補測試需由使用者決定後另行處理。

## 執行限制

- 盤點的是**測試覆蓋**，不是功能是否完成，也不是程式碼品質。發現實作缺陷時可在備註指出，但不擴大成 code review。
- 驗收項目本身有問題時（語意矛盾、無法判定真偽），照實記錄為「無法判定」並說明，**不要自行改寫項目**，也不要回頭修設計文件。
- 不與 `engineering-spec.md` 定稿模式競爭：定稿由 `to-engineering-spec` 負責，它會在 DC 表補「驗證結果」欄。本檔案是它的輸入之一，不是它的替代品。

## 下一步引導（純提示，不主動調用）

- **有需補測試或覆蓋不足** → 提示使用者可回到 `implement-stepwise`，將補測試視為新的 commit item 處理。
- **全部收斂** → 提示使用者可執行 `to-engineering-spec` 的定稿模式，依本檔案逐條標註全域實作約束的驗證結果；需交付時再以 `engineering-spec-deliverable` 產出交付版。
