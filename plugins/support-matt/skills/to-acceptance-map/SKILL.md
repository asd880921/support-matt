# to-acceptance-map

整條 branch 開發完畢後，盤點**自動化測試對驗證基準的覆蓋情形**，產出一份可追溯的對應清單。它與交付版規格是一組：規格說要成立什麼，本檔案說哪些有測試守著、哪些沒有、沒有的怎麼驗。

## 驗證基準只有一個來源

**規格文件的「驗證條件」（`VC-xx`）。ticket 不是驗證來源。**

本 skill 說的**規格文件**，預設是 `issue-doc.md`（`to-issue-doc`，狀態 `final`）；動角色權限、schema、跨模組交易的重案流程則是 `engineering-spec.md`（`to-engineering-spec`，狀態 `定稿`）。兩者的「驗證條件」章格式相同，本 skill 的處理方式完全一致——以下一律稱**規格文件**，只在需要區分時點名。

理由是**時態**。Matt workflow 是 append-only：開發中途有新需求或要調整，作法是再開一張 ticket 接續做完，而後開的票**可能砍掉或改寫前面票的功能**，舊票不會回頭更新。把各 ticket 的驗收條件平鋪匯集，等於拿一疊不同時間點的快照當現況，會同時產生三種錯：

- 已被砍掉的功能報成「需補測試」——測試跟著砍了，這是誤報。
- 已被砍掉的功能報成「已涵蓋」——**舊測試沒跟著刪，還是綠的**。這種假好消息最危險，它同時掩蓋了「這條不該存在」與「實作可能沒砍乾淨」。
- 互相矛盾的兩條條文並存，而表格沒有任何欄位能表達哪條才是現行事實。

規格文件是這條管線裡唯一會**就地修訂**的文件，收斂步驟（`to-issue-doc` 的 final／`to-engineering-spec` 的定稿）還會專門依實際交付校準驗證條件（新增 / 改寫 / 刪除）。以它為準，上述三種錯全部不會發生。

**ticket 仍然要讀，但只有一個用途，且不涉及判定：當搜尋線索。** commit checklist 的 `tests` 行與收尾的驗收核對表，是定位測試最快的路徑。

**不要拿 ticket 反向盤點規格**——「ticket 有而規格沒有」的項目不列、不提醒。ticket 的驗收條件在開發當下已逐張驗收過，把它們再攤回來對規格，等於用一疊舊快照重驗一輪，正是上面那三種錯的來源。規格漏收該由 `to-issue-doc` final（重案為 `to-engineering-spec` 定稿）收斂，不是這裡。

## 為什麼要獨立執行

`implement-stepwise` / `implement-oneshot` 在每個 commit 完成時會記錄「本次寫了哪些測試、涵蓋哪幾條驗收條件」。**那份記錄是實作者的自我聲明，不是證據。**

本 skill 的價值來自獨立性：在**乾淨的新 session** 執行，不帶開發過程的 context，逐項自行確認測試確實存在、且真的涵蓋該項目。

依 ticket 的記錄去定位測試很有效率，但**必須自行開啟測試確認斷言內容**，不得直接採信。同理，**ticket 的 checkbox 是否已被勾選，不影響本 skill 的判定**：勾選代表實作者認為做到了，與「有沒有測試守著」是兩回事。

記錄與實際不符時，以實際為準。

## 唯讀規範（最高優先）

- **只建立或覆寫 `acceptance-map.md` 一個檔案。**
- 對 ticket 檔案、規格文件、`spec.md`、功能程式碼、測試程式**一律唯讀**。
- **不補寫任何測試、不修改任何程式碼、不修改設計文件、不勾選任何 checklist。**
- **不刪除、不合併、不改寫任何測試**——包含步驟 4.1 列為可能已失效、以及步驟 4.2 列為潛在重複的那些。動不動由使用者決定，實際修改回到 `implement-stepwise` / `implement-oneshot`。本 skill 是獨立稽核者，一旦自己動手改測試，它報出來的結果就不再是獨立判定。
- 發現缺漏時只回報，由使用者決定後續處理。
- **唯讀指的是不修改檔案，不是不執行。** 本 skill 會執行測試（步驟 3），那是判定的必要依據；範圍由使用者選擇。

## 執行流程

### 1. 取得範圍

從使用者指定的 feature 目錄取得（路徑依 `.ai/docs/agents/issue-tracker.md` 的慣例，通常是 `.ai/.scratch/<feature>/`）：

- **規格文件**（`issue-doc.md`；重案流程為 `engineering-spec.md`）—— 驗證基準的唯一來源，**必要**。
- `issues/` 底下全部 ticket 檔案 —— 只作定位測試的搜尋線索。

未指定時，依當前 git 分支名稱推斷對應的 feature 目錄；推斷不出來就停下來問，不要猜。

**三道前置確認，都是停下來問，不自行決定：**

| 情況 | 為什麼要先問 |
| --- | --- |
| 規格文件不存在，或沒有「驗證條件」章 | 沒有驗證基準就沒有可盤點的對象。**不要退回去拿 ticket 的驗收條件充數**——那正是本 skill 刻意不做的事。請使用者先跑 `to-issue-doc`（重案為 `to-engineering-spec`） |
| 規格文件的 `文件狀態` 不是 `final`（重案為 `定稿`） | 收斂步驟才會依實際交付校準驗證條件（新增 / 改寫 / 刪除）。跳過它，盤點基準會停在開發前的版本，被砍掉的功能還在表上 |
| 仍有 ticket 的 Commit checklist 未全部勾完 | 對未完成的 branch 盤點，結果會大量出現「需補測試」而失去意義 |

### 2. 取得驗證基準

從規格文件的「驗證條件」章讀**那一張表**，**沿用其原始編號**（`VC-xx`）——編號是跨文件的追溯鍵，本 skill 不重新編號、不合併、不拆條。每條帶著規格給的「驗證方式」，那是判定的重要輸入（見步驟 4）。

**整張表都必須納入，包含從未被任何 ticket 吸收的項目。** 這是本 skill 存在的理由之一：以否定式陳述表達的約束（「未使用 X」「未產生 Y」）在拆票時容易蒸發，因為它們演示不出來；feature 層級的盤點是它們唯一的回收點。

同理，**橫跨多張 ticket 的項目**（例如「查詢與匯出走同一個取資料的方法」）在任何單張 ticket 的收尾都驗不到，只有這裡驗得到。

驗證條件本身粒度過粗、判不了真偽時（「系統應正確處理匯出」），**照實記錄為「無法判定」並說明**，不要自行改寫成一條你覺得它想講的條件——那會讓盤點結果失去追溯性。

### 3. 執行測試

#### 3.1 先問使用者要跑多大範圍

**不要自行決定，一律先問。** 有些專案跑完全部測試要很久，那個時間成本該由使用者決定值不值得：

```text
盤點前要跑哪個範圍的測試？
  1. 全部測試專案 —— 最完整，但可能耗時很久
  2. 只跑本次 branch 受影響的測試專案 —— 快，但未受影響的專案不會被驗證
  3. 不跑，直接用現況盤點 —— 最快，但無法確認測試是綠是紅，
     「已涵蓋」的判定會降級為「測試存在」而非「測試通過」

發現的測試專案：<列出偵測到的專案清單與各自大略規模>
```

選 3 時，在 `acceptance-map.md` 開頭明確標註「本次未執行測試，覆蓋判定僅依測試存在與斷言內容」。

#### 3.2 測試專案必須逐一執行，不得整個 solution 一次跑

**這是硬規則。** 跨測試專案並行執行時，常因共用資料庫、連接埠、靜態狀態或測試替身而互相干擾，產生**單獨跑全綠、一起跑就紅**的假失敗。實測案例：

| 專案 | 單獨執行 | 整個 solution 一次跑 |
| --- | --- | --- |
| UnitTest | 553 通過 / 4 略過 | **3 失敗** |
| IntegrationTests | 35 通過 | **21 失敗** |

拿這種假失敗去判定覆蓋，會把大量「已涵蓋」誤降為「覆蓋不足」，整份盤點就廢了。

因此：**先列出測試專案清單，再一個一個跑，分別記錄結果。** 不要用 solution 層級的單一指令一次跑完。

#### 3.3 失敗的處理

- **測試存在但是紅的，不得判為「已涵蓋」。** 判為「覆蓋不足」並在備註註明它目前失敗。
- **不要假設失敗都是本次 branch 造成的。** 專案可能本來就有既有失敗（例如 UI/E2E 測試因環境因素長期紅燈）。發現失敗時**列出來問使用者**哪些是既有的，既有失敗不影響該項目的覆蓋判定，只在備註標明。
- 本次 branch 明顯造成的失敗數量多到無法逐一歸屬時，**停下來回報**，請使用者先修好再盤點。

本步驟只**執行**測試，不修改任何測試或程式碼，不牴觸唯讀規範。

### 4. 逐項比對測試

對每一條驗證條件，找出涵蓋它的自動化測試——單元測試、整合測試、UI/E2E 測試皆計入。

探索方式：若專案已建立程式碼知識圖譜或等效索引工具（讀 `CLAUDE.md` / `AGENTS.md` 的宣告，或檢查可用的 MCP 工具判斷），**優先用它定位測試與被測目標**，再針對性讀取；本 skill 不指定使用哪一套。這是一次 feature 層級的全面盤點，靠 grep 加整檔閱讀會迅速累積大量無用 context。

判定四分類：

| 判定 | 條件 |
| --- | --- |
| **已涵蓋** | 存在測試，且其斷言確實驗證該項目所述的行為或約束 |
| **覆蓋不足** | 有相關測試，但只驗到部分條件、只測快樂路徑、或斷言不足以判定該項目成立 |
| **需補測試** | 沒有測試，**而且該由測試守** —— 這是真正的缺口 |
| **不適用測試** | 沒有測試，**而測試本來就不是這條的適當證據** —— 需人工或靜態檢查 |

### 為什麼要分開最後兩級

上游的驗證條件是以 Matt 的標準產生的，而 Matt 的 `/tdd` 明文寫著「**You can't test everything** —— 測試力氣要投在關鍵路徑與複雜邏輯，不是每一個邊界值」，且測試的單位是**議定的 seam**，不是驗收條目。因此**清單中本來就有相當比例的項目不預期有測試**，那是設計如此，不是缺陷。

把這兩者混為同一格，會讓報告出現大量誤報，使用者很快就會整份忽略——**一個常常誤報的驗證工具比沒有更糟**。

### 「不適用測試」的護欄（防止它變成垃圾桶）

- **規格的「驗證方式」欄優先於本 skill 的推測。** 該欄填 `自動化測試` 的項目，沒有測試就是「需補測試」，**不得判為「不適用測試」**——那是規格已經做過的判斷，本 skill 無權推翻。填 `人工檢視` / `靜態檢查` 的，才有資格進「不適用測試」，且仍要寫理由。
- **填 `靜態檢查` 的多是對實作路徑的約束**（「四道判定全部在資料庫執行」），落在「不適用測試」是正常結果，不是本 skill 偷懶。但**不要因為它填了 `靜態檢查` 就免驗**——仍要逐條跑下面的規則，確認它真的測不到。
- 規格文件沒有「驗證方式」欄時，回退到下面的自行判斷規則。
- **必須逐項寫出理由**，不得只標分類不說明。
- **只有下列性質的項目可以判為「不適用測試」**：
  - 結構性約束（「四道判定全部在資料庫執行」「未使用含系統倉短路的授權判斷式」「三處共用同一個運算式」）——測試看不到實作走哪條路徑。
  - 純視覺或版面（欄位排列位置、樣式）。
  - 元條件（「單元測試涵蓋上述規則」這類講實作方式而非系統行為的項目）。
  - 需要真實外部環境才成立、專案未建置該層測試的項目。
- **使用者可觀察的行為一律不得判為「不適用測試」。** 錯誤訊息文字、必填驗證、資料是否出現在結果中、排序、分頁、預設值——這些都測得到，沒測就是「需補測試」。判斷困難時，**一律放進「需補測試」**，讓使用者自己決定要不要補。

### 其他判定原則

- **以斷言為準，不以測試名稱為準。** 名稱寫得像、但斷言沒驗到的，是「覆蓋不足」。
- **不把「程式碼看起來有實作」當成已涵蓋。** 本 skill 盤點的是測試覆蓋，不是實作完成度。
- 不要為了讓表格好看而勉強對應一個不相干的測試。

### 4.1 可能已失效的測試（反向掃描）

前面四分類是「從驗證基準找測試」。這一步反過來：**從本次 branch 動過的測試找驗證基準**。

一個測試若對不上任何 `VC-xx`，而它測的是本 feature 範圍內的行為，就是**可能已失效**的候選——後開的 ticket 砍掉或改寫了某個行為，實作跟著改了，但測試沒同步，它現在守著一條規格已經不再要求的行為。

它為什麼只有在這裡驗得到：**它是綠的**。單張 ticket 的收尾看不到它（不在那張票的範圍內），CI 也不會抱怨（測試通過），四分類掃不到它（沒有任何驗證條件會指向它）。

- 用 `git diff` 對 branch 起點取得本次動過的測試檔，範圍限定在這些檔案與它們相鄰的既有測試，**不要全庫掃**。
- 判不準時**列出來問使用者**，不要自行認定它已失效——測試也可能守著規格沒寫、但確實需要的行為。
- 這是**回報項，不是判定**，措辭一律是「請確認」而非「應刪除」。本 skill 不刪任何測試，也不建議使用者非刪不可。

### 4.2 潛在重複覆蓋（只偵測，不動手）

測試的 consolidation 發生在 implement 的每個 commit 之前（見 `implementation-rules.md` 的「Test Consolidation」）。但有些重複只有在整條 branch 收斂後才看得出來——跨多張 ticket、需求後續演進、後面的實作取代了前面較細粒度的保護。**這一步是那些重複唯一的偵測點。**

在四分類完成後，對已判定「已涵蓋」的項目回頭看它的對應測試，標示三種候選：

| 候選類型 | 判斷依據 |
| --- | --- |
| **同層重複** | 同一個 `VC-xx` 由多支同層級測試守著，而各支的斷言驗的是同一件對外可觀察的事 |
| **可參數化** | 多支測試只有輸入值不同，斷言結構相同 |
| **跨層重複，看不出各自的獨立風險** | 同一個 observable behavior 被不同測試層級各驗一次，而說不出各層保護的是不同的風險 |

**兩條硬判準，不套用下面的「判不準就不列」**——它們的判準本身明確，沒有判不準的空間，逐條跑完才算跑過這一步：

1. **同一 `VC-xx` 對應 3 支以上測試** → 逐支寫出它保護什麼。**任何一支寫不出與其他支不同的保護對象，該支就列為候選。**
2. **同一測試類別中命名同型、斷言結構相同、只差輸入值或目標的測試，構成一個家族** → 依所在層級的門檻列為「可參數化」候選，不必再論證它們是否重複。這種家族是逐 commit 各長一支累積出來的，commit 前的收斂**在設計上看不到它**（每次只多一支，而那一支守的是新東西），**本步驟是它唯一的偵測點**。

   | 家族所在層級 | 支數 | 怎麼報 |
   | --- | --- | --- |
   | 昂貴層（整合、UI／E2E） | **3 支以上** | 逐筆列進表格 |
   | 便宜層（單元） | **8 支以上** | 逐筆列進表格 |
   | 便宜層（單元） | 3–7 支 | **不進表格**，只在章末壓成一行摘要（家族名稱＋支數） |

   **列家族前先實際搜尋全員**（用共同的命名尾綴或前綴搜尋整個測試類別），把總支數寫進報告。憑印象列會漏成員，也會讓剛好 3 支的家族整組被忽略。

   **一個家族在表格裡只佔一列**，成員全部寫在同一格（`<br>` 分隔），疑點欄只寫一次。把 10 支拆成 10 列、每列複製同一句話，是把一筆發現灌成一頁——使用者要讀的是「有幾個家族」，不是「有幾支測試」。

3. **同一個行為在便宜層驗資料、在昂貴層又驗它渲染或回傳出來** → 列候選。

   **怎麼找（照做，不要只比對印象）**：列出本次盤點到的**昂貴層測試中，斷言畫面元素、旗標或回傳欄位**的那些；對每一支，取它斷言的那個**旗標／欄位名**（例如 `CanEdit`、`HidesEdit`、`ShowsConfirmRepair`），拿這個名字**回便宜層的測試類別搜尋**（方法名與斷言內容都搜）。搜得到同名概念的測試 → 這一對就是跨層重複候選。

   **例外只有一個**：昂貴層保留**一支**證明「該頁真的照旗標渲染」，其餘同型的全部列為候選。

   這條刻意連搜尋動作一起寫死。前幾版只描述樣式（「說不出各層獨有的風險就列」「便宜層驗旗標、昂貴層又驗渲染」），實測連續三次都報 0——**光給樣式不會讓它去找，要給去哪找、拿什麼找**。

**兩條硬判準都先看昂貴層級（整合、UI／E2E）。** 便宜層多幾支測試只是檔案長一點，昂貴層每一支都在吃每次跑測試的時間——同樣是重複，昂貴層的那筆才值得使用者花時間讀。

**跨層重複要特別小心，它最容易誤報。** 各層說得出自己獨有的風險時（商業規則在單元、API／DB／framework 契約在整合、真實使用者流程與 wiring 在 UI／E2E），那是刻意的分工，**不列為候選**。只有「單純把同一件事再驗一次」才列。

護欄：

- **一支測試是某條 `VC-xx` 的唯一覆蓋時，永遠不列為候選。** 這一步找的是重複，不是找測試來刪。
- **判不準就不列。** 誤報一次，使用者下次就整章跳過；漏報只是少省一點維護成本。
- **措辭一律是「請確認」，不得寫「應刪除」「建議移除」。** 本 skill 沒有讀過開發過程，不知道那支測試當初為什麼在。
- 每一筆都要寫出**它為什麼可能重複**，以及**併掉之後該行為由誰守**。說不出後者就不要列。
- **候選為空只有在兩條硬判準都逐條跑過、且都不成立時才成立。** 沒跑過就寫空，是漏檢，不是好結果。真的跑完仍為空，代表 commit 前的 consolidation 有做到位——那時不要為了讓這章有內容而硬湊。

### 4.3 缺口要帶層級建議

「覆蓋不足」與「需補測試」會直接變成下一張補測試票的 seam 規劃。**只寫缺什麼、不寫該補在哪一層，補測試的人會照缺口的現象描述把測試補在昂貴層。** 實跑證據：五個缺口有三項被規劃在整合層（合計新增 7 個會寫入真實資料的 case），改補在服務層之後覆蓋一條不少、昂貴層零成長。

判斷所需的資訊本 skill 手上都有——步驟 4.2 判跨層重複用的就是同一份成本歸屬——所以在這裡一併給出。

對每一條判定為「覆蓋不足」或「需補測試」的項目，寫出**建議補在哪一層**與一句理由，依 `implementation-rules.md` 的「測試層級」成本歸屬：業務規則的分支與邊界值、ViewModel 的欄位與顯示文字屬**單元**；真實資料庫的交易與查詢行為、HTTP 管線的驗證／授權／路由／模型繫結屬**整合**；瀏覽器 wiring 與真實使用者流程屬 **UI／E2E**。

- **先回便宜層搜尋再下建議**：取該條驗證條件的旗標／欄位／規則名，搜便宜層的測試類別（方法名與斷言內容都搜）。搜得到同名概念的測試，缺口多半是那支的斷言不足，建議就是「補強該支斷言」，不是在昂貴層新增一支。
- **建議昂貴層時，必須同時寫出「便宜層驗不到的是什麼」**（真實資料庫、HTTP 管線、瀏覽器 wiring）。寫不出來就是便宜層。
- **這是建議，不是判定。** 使用者與 implement 端可以推翻它，但欄位不得留空——留空就退回成現象描述，缺口又會落回昂貴層。
- 判不準時照實寫「判不準」並說明兩層各自的理由，不要為了填滿欄位而猜。

### 6. 回報

**回報只呈現例外，不要把完整清單複述一遍。** 檔案本身保留全部項目（它是日後可查詢的追溯表），但貼給使用者的內容只有：

1. 摘要數字（四個判定各幾項）。
2. **「覆蓋不足」與「需補測試」的完整條列，各自帶上建議補在哪一層與理由** —— 這是使用者真正要看的，也是下一張補測試票直接拿去規劃 seam 的東西。
3. 「不適用測試」只給數量與一句歸類說明，不逐條列出；使用者要細節時再開檔案看。
4. **可能已失效的測試**若有，全部列出並說明疑點——由使用者判斷，不要下「應刪除」的結論。
5. **潛在重複覆蓋**若有，全部列出並說明疑點；一併說明它是選用的（要動才動，不動也不影響覆蓋），以及動了測試就必須重跑相關測試與本 skill。同樣不要下「應刪除」的結論。

一份 60 項的盤點，使用者需要讀的通常不到 10 項。把 50 項「已涵蓋」貼給他，只會讓他整份跳過。

最後明確告知：本 skill **未修改任何程式或文件**，補測試需由使用者決定後另行處理。

## 執行限制

- 盤點的是**測試覆蓋**，不是功能是否完成，也不是程式碼品質。發現實作缺陷時可在備註指出，但不擴大成 code review。
- 驗收項目本身有問題時（語意矛盾、粒度過粗、無法判定真偽），照實記錄為「無法判定」並說明，**不要自行改寫項目**，也不要回頭修設計文件。
- **不收斂驗證條件。** 依實際交付新增 / 改寫 / 刪除 `VC-xx`，是 `to-issue-doc` final（重案為 `to-engineering-spec` 定稿）的職責，發生在本 skill 之前。本 skill 只回報缺口，一個字都不改。
- 本檔案與規格文件是**兩份獨立的檔案**，各自產出、各自重跑，不互相內嵌。貼上 Issue 時一起貼。
