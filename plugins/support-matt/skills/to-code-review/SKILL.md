# to-code-review

Matt 的 `code-review` 的**上層入口**。它自己不取代任何審查能力：Matt 的兩軸（Standards / Spec）照跑，本 skill 負責三件 Matt 不管的事——**決定審什麼範圍**、**決定 finding 夠不夠格被寫出來**、**決定寫到哪裡**。

與個人版 `code-review-changes` 的差別只有一處：**開發文件不再向使用者索取**。當前分支若有對應的 feature 目錄，規格與 ticket 就在那裡，使用者只要說目標分支。

## 兩種模式

開場第一件事是判定模式，**不得跳過，也不得兩種混用**。

| | **A. 自家 branch** | **B. 代審他人 MR** |
| --- | --- | --- |
| 判定依據 | 當前分支有對應的 feature 目錄 | 沒有 |
| 使用者要提供 | **只有目標分支** | 目標分支 + 變更背景 |
| 審查背景來源 | feature 目錄下的規格與 ticket | 使用者提供的 Issue、文件或口頭說明 |
| 輸出位置 | feature 目錄下的 `REVIEW.md` | `.ai/code-review/<target>__<current>/REVIEW.md` |

### 模式判定

1. 讀 `.ai/docs/agents/issue-tracker.md` 取得 feature 目錄的位置慣例（通常是 `.ai/.scratch/<feature>/`）。找不到時改讀 `docs/agents/issue-tracker.md`；兩者皆無，直接視為模式 B。
2. 依當前 git 分支名稱推斷對應的 feature 目錄，確認它實際存在。
3. 目錄存在 → 模式 A。不存在 → 模式 B。

**推斷不出唯一對應（例如分支名對到多個目錄，或名稱差異大到只能用猜的）時，停下來問使用者是哪一個，不要猜，也不要因為猜不到就自己降級成模式 B。** 降級的代價是使用者被要求重打一份現成文件裡就有的背景。

## 必要輸入

### 模式 A

只有一項：**目標分支、base ref 或 commit 範圍**。

沒有時停下來問，**不得自行套用預設目標分支**——`main` 不一定是這條 branch 的分歧點。

審查背景由 feature 目錄自行取得，依序：

1. `engineering-spec.md` —— 有的話以它為主，它是這條 branch 唯一會就地修訂的文件。
2. `spec.md` —— 需求、範圍與行為基準。
3. `issues/` 底下的 ticket —— 本次變更實際交付了哪幾張票、各自的驗收條件。

三者都不存在（目錄在但是空的）時，**不要退回去要使用者補文件**，改為停下來確認：是否該走模式 B。

### 模式 B

兩項都要，缺任一項立即停止：

1. 目標分支、base ref 或 commit 範圍。
2. 本次審查訊息、Issue、需求背景、開發文件或驗收條件；**沒有額外文件時，也必須由使用者明確說明本次變更目的**。

停止時清楚列出缺少的項目請使用者補充，**不要先讀 diff、不要先審程式碼、不要建立 `REVIEW.md`**。沒有變更目的就開審，等於拿實作反推需求，會把「照需求做的」報成 finding。

## 與 Matt `code-review` 的關係

本 skill **完整調用** `mattpocock-skills:code-review`，把上面判定出來的固定點與規格來源交給它，兩軸照原樣跑完。

**不對它套用任何瘦身參數。** 本 skill 是合併前的最後一關，`implement-oneshot` 那套「Spec 軸改讀 ticket、縮小固定點」的省法在那裡成立（實作剛做完、驗收條件剛逐條核對過），在這裡不成立——這裡要看的正是整條 branch 累積下來、逐票核對看不到的東西。省 token 的位置不在這一關。

### Matt 的兩軸報告是輸入，不是輸出

**不得把 Matt 的報告原樣貼進 `REVIEW.md`。** 兩軸產出的是候選，本 skill 逐條過下面的證據門檻與明確排除之後，才決定哪些寫出來。

Standards 軸帶著一份 Fowler code smell baseline，其中 Mysterious Name、Speculative Generality、Middle Man 等大量落在本 skill 的**明確排除**（純命名、可讀性微調、非必要重構）。它們被列出來是 Matt 的設計，被濾掉是本 skill 的設計，兩者不衝突——`REVIEW.md` 的讀者是 MR 上的其他人，貼一條「這個名字不夠達意」進去只會稀釋真正的問題。

反過來也一樣：**兩軸沒提到的不代表沒問題**。權限、後端信任邊界、併發與資料一致性、N+1 不在 Matt 的兩軸守備範圍內，那是下面「補充審查重點」的工作，必須自行再走一輪。

## 核心原則

- 以 Matt 的 `code-review` 為主要審查能力；本 skill 只補充專案範圍、證據門檻與輸出規則，不要求為每個檢核類別硬找問題。
- 寧可省略低可信度或低影響評論，也不要輸出無法證實、與本次變更無關或沒有實際修正價值的 finding。
- 每個 finding 都必須能回答：如何觸發、會造成什麼影響、為何現有保護機制無法避免。
- 不因存在「更漂亮、更快、更抽象」的寫法就提出 finding；只有目前寫法會造成具體問題時才回報。

## 審查範圍

1. 使用使用者指定的目標分支、base ref、commit 範圍或 MR，不得自行套用預設目標分支。
2. 審查目前分支相對於目標分支的完整 MR diff，不限於最新 commit。
3. 參考相關 Issue、需求、開發文件及驗收條件，但不要擴大變更範圍。
4. 為確認實際影響，可追查必要的呼叫端、被呼叫端、模型、資料庫存取、權限與測試。
5. 只有符合下列任一條件時，才可回報 diff 外的程式碼問題：
   - 本次變更新增了到該問題的可達路徑。
   - 本次變更使既有問題更容易觸發或影響明顯擴大。
   - 本次變更依賴該既有行為，導致本次需求無法正確成立。
6. 單純在追查過程中看到的既有問題，不得列入 finding；必要時可完全不提。

## 補充審查重點

在 Matt 兩軸的檢查之外，聚焦檢查：

- **正確性與回歸**：錯誤條件、狀態轉換、邊界、例外、契約及既有流程。
- **需求完整性**：是否漏做文件或驗收條件明確要求的行為。
- **資安與權限**：身分、角色、資料歸屬、操作權限、注入及敏感資料。
- **後端信任邊界**：不可完全信任 request、route、query、form、hidden field 或 DTO 傳入的識別資料、狀態、數量、金額、層級及權限相關值。可由後端查詢或推導時，使用後端權威資料驗證、正規化並處理。
- **資料一致性與併發**：檢查合理的多請求、多使用者或多分頁操作是否可能造成遺失更新、重複建立、重複扣庫存、超扣、舊狀態覆蓋、部分成功或其他資料異常。只有能指出具體競爭流程與缺少的保護機制時才回報。
- **實質效能問題**：優先檢查 N+1、迴圈內資料庫或網路 I/O、同一資料的明顯重複查詢、無界限載入大量資料、可預期造成大量記憶體配置、阻塞重要流程、演算法複雜度在合理資料量下會快速惡化，以及可批次卻逐筆執行大量操作。
- **共用邏輯**：只有重複業務規則已造成或高機率造成行為分歧、修正遺漏或安全問題時才提出；不要只因程式碼外觀相似而要求抽取。
- **測試缺口**：只有本次變更新增或改變了重要行為，且缺少測試會使具體回歸難以被現有測試發現時才提出。不得只寫「建議補測試」。

不要只逐行閱讀 diff；沿資料流與呼叫關係確認候選問題是否已在其他位置處理。

## 明確排除

不得回報下列內容：

- 未受本次變更影響的既有問題。
- 純排版、純命名、個人偏好、可讀性微調或非必要重構。
- 奈秒級、常數級或無可觀測影響的微型效能最佳化。
- 沒有資料量、呼叫頻率或 I/O 證據支撐的效能猜測。
- 只有理論可能、但無合理觸發路徑的 Null、並行、資安或例外風險。
- 已由框架、型別系統、資料庫約束、上游驗證或現有保護機制可靠處理的情況。
- 為了填滿檢核清單而產生的評論。
- 無法指出實際錯誤結果的「可能有問題」「建議確認」「最好改成」類評論。

## Finding 證據門檻

提出 finding 前，依序確認：

1. **變更關聯**：問題由本次 diff 引入、改變或明顯放大。
2. **可達性**：存在合理輸入、狀態或操作流程可以觸發。
3. **實際影響**：可說明錯誤結果、資料異常、越權、明顯效能退化或需求不符。
4. **未被保護**：確認其他呼叫端、驗證、交易、限制或測試沒有已經處理。
5. **修正價值**：本次合併前處理具有實際價值，不只是理論上的完善。

任一項無法成立時，不要輸出 finding。**Matt 的兩軸報過的候選同樣要逐條走完這五關**，不因為它報過就免驗。

## 確認程度

- `已確認問題`：可由程式碼、執行結果或明確需求直接證明。
- `待確認風險`：已有具體程式碼路徑與實際影響，只差一項可明確驗證的環境、資料、設定或需求條件。

`待確認風險` 必須同時寫明：

- 已確認的程式碼事實。
- 唯一待確認的條件。
- 該條件成立時的具體影響。
- 可如何快速驗證。

若缺少多項前提、只能依賴猜測，或驗證後很可能不構成問題，不得列為 `待確認風險`。

## 嚴重程度

- `P0`：重大服務、資料或資安事故，必須阻擋。
- `P1`：一般情境可觸發的嚴重錯誤、越權或核心流程失效，應阻擋。
- `P2`：特定合理情境下的功能、回歸、實質效能、並行或維護問題，合併前應處理或確認。
- `P3`：影響較低，但與本次變更直接相關、證據明確、修正成本合理且有實際品質價值的小問題。

P3 可保留有價值的小細節，但仍必須符合完整證據門檻。不得把風格偏好、微型最佳化或不確定猜測包裝成 P3。

## Finding 內容要求

每個 finding 必須指出相關變更檔案與行號，並說明：

- 具體觸發情境。
- 目前行為。
- 預期行為。
- 實際影響。
- 現有保護為何無法避免。
- 聚焦的修正方向。

未實際執行測試時，不得宣稱測試通過。

## 輸出

有 findings 時，依模式決定寫入位置：

| 模式 | 路徑 |
| --- | --- |
| A. 自家 branch | 判定出來的 feature 目錄下的 `REVIEW.md`（與 `issues/` 同層） |
| B. 代審他人 MR | `.ai/code-review/<target-branch>__<current-branch>/REVIEW.md` |

模式 B 的目錄名先正規化：移除目標分支的 `origin/`，並將目標及目前分支名稱中的 `/` 改為 `-`。

既有檔案直接覆寫——本 skill 可對同一條 branch 重複執行，每次都反映當下狀態，不保留上一輪的內容當歷程。

findings 依 `P0` 至 `P3` 排序，使用以下格式：

```markdown
## [P0-P3] 簡短且具體的問題標題

* 問題類型：<類型>
* 確認程度：已確認問題 / 待確認風險
* 影響範圍：`相對路徑:行號或行號範圍`
* 問題說明：<觸發情境、目前行為、預期行為、現有保護為何無法避免，以及實際影響>
* 建議修正方向：<聚焦的修正方向；若為待確認風險，包含快速驗證方式>
```

`REVIEW.md` 只放可獨立貼至 MR comment 的 findings，不加入稱讚、審查過程、Matt 兩軸的原始報告、未變更內容摘要、被排除的候選問題或「未確認但可留意」清單。

沒有 findings 時不要建立檔案，回覆：`未發現 Code Review Finding。`

最終回覆同時列出：本次採用的模式與判定依據、findings 數量與最高等級、實際測試結果或未執行測試，以及有建立時的 `REVIEW.md` 路徑。

## 執行限制

- **不修改任何程式碼、測試或設計文件**，只建立或覆寫 `REVIEW.md`。發現問題一律回報，修不修由使用者決定。
- **不遞迴調用本 skill**，也不改由其他 code review skill 代替 Matt 的 `code-review`。
- 模式 A 讀 feature 目錄是為了取得審查背景，**不是去盤點測試覆蓋**——那是 `to-acceptance-map` 的工作，兩者不重疊。

## 在流程中的位置

```text
implement-stepwise / implement-oneshot 完成
    → [to-code-review]（本 skill，合併前最後一關）
    → to-engineering-spec 定稿 → to-acceptance-map → engineering-spec-deliverable

代審他人 MR：直接調用本 skill（模式 B），與上面的 pipeline 無關
```

## 下一步引導（純提示，不主動調用）

- **有 P0 / P1** → 提示先處理再合併；修正屬於實作，回 `implement-stepwise` 或 `implement-oneshot` 處理，本 skill 不動程式。
- **只有 P2 / P3** → 提示由使用者決定本次處理或另開 ticket。
- **修正後** → 提示重跑本 skill，`REVIEW.md` 會覆寫成當下狀態。
