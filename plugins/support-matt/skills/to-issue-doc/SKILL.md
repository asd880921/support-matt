# to-issue-doc

維護單一份 `issue-doc.md` —— 貼上公司**主 Issue** 的規格文件，拆票的 issue 放在它的 comments。

## 這支 skill 的取捨（先讀這段）

一份規格文件混了兩種東西，它們的最佳寫作時機相反：

| 內容 | 最佳時機 | 理由 |
| --- | --- | --- |
| 驗證條件 `VC-xx`、範圍邊界、關鍵決策 | **拆票前** | 它們是**約束**：拆票本身就是設計行為，落點與邊界沒先定版，決策會發生在拆票裡而沒有紀錄 |
| 系統分析、資料模型、介面與流程、實作落點 | **實作後** | 它們是**紀錄**：程式碼就是答案，事前寫是猜，事後抄才準 |

因此本 skill 把文件切成兩個時點寫，而不是一次寫完：**brief 只寫上排，final 才補下排**。這是它與 `to-engineering-spec` 的根本差異——那支要求在動工前把系統分析與技術設計一次寫到位，適合動角色權限、動 schema、跨模組交易邊界的重案；一般案子用本 skill。

## 工作流位置

```text
grill-with-docs → to-spec → [to-issue-doc brief] → to-tickets → implement(-oneshot/-stepwise)
                                    ↑                                          ↓
                    [to-issue-doc 修訂] ← to-change-request           全部 ticket 完成
                                                                               ↓
                      貼上主 Issue ← to-acceptance-map ← [to-issue-doc final]
```

**brief 在 `to-tickets` 之前，不是之後。** 兩個理由，都與「順手」無關：

- **拆票是設計行為。** 要把功能切成有相依順序、各自可獨立完成的切片，必須先決定落點：沿用哪些既有機制、資料寫入責任在誰、新邊界畫在哪。brief 放在拆票之後，不會讓這些決策不發生，只會讓它們**發生在拆票裡、沒有紀錄、沒有經過使用者確認**，而票是 `implement` 唯一實際吃的東西。
- **`VC-xx` 不能被票錨定。** `to-acceptance-map` 明訂驗證基準不得來自 ticket，且 feature 層級盤點的存在理由，正是回收那些任何單張票都看不到的條目（否定式約束、跨切片一致性）。看著票寫 VC，最可能的結果不是寫錯，而是變成「各票驗收條件的並集」——每條都合理、沒有任何症狀，卻剛好丟掉這張表唯一不可取代的部分。

沒有票在手時 `VC-xx` 照樣判得動，判的是條目性質不是切分方式，見「驗證條件」一節的四類判準。漏收由 `final` 的校準兜底。

**`final` 必須在 `to-acceptance-map` 之前跑。** `to-acceptance-map` 拿本文件的 `VC-xx` 當唯一驗證基準，而 `final` 的第一件事就是依實際交付校準那張表；順序反過來，盤點的是開發前的舊基準。

## 核心行為規範（最高優先）

- **一個 feature 一份 `issue-doc.md`，一律就地修訂。** 不產 `-v2`、不另存交付版副本、不建立第二份取代文件。
- **本文件的章節清單是資訊檢查表，不是 heading 檢查表。** 每個資訊面向都**必須被思考**，但思考完的結論可以是「值得獨立成章」「併入相鄰章節」「一句話帶過」「完全無資訊增量，不寫」。**不要用空章節或「本次無」證明自己檢查過**——檢查的痕跡寫在回報訊息裡，不寫進文件。反過來也成立：**省略 heading 不等於省略分析**，沒開「資料模型」章之前，schema／索引／關聯有沒有動仍然要查過。
- **文件的結構複雜度要與需求的資訊複雜度成正比。** 極簡不是目標，比例才是。單表 CRUD 不該長出跟跨模組交易改造一樣的目錄；反過來，真的有 migration、交易邊界、狀態機時，章節該展開就展開。
- **只有 `VC-xx` 那張表需要使用者逐條確認**，其餘章節攤出來讓使用者看一眼即可。確認關卡越多，這支 skill 就退化成它要取代的東西。
- **brief 不寫實作後才知道的事。** 介面簽章、欄位級 schema、方法落點一律留給 `final`。寫不出來就是還不該寫，不要用猜的填滿模板。
- **final 只寫既成事實。** 來源是程式碼、ticket 的驗收核對表與 `git diff`，不是 brief 的計畫。與 brief 不一致的地方**明確列出來讓使用者裁決**，不得靜默以 brief 為準覆蓋事實，也不得靜默以事實覆蓋 brief 而不提。
- **需求的權威永遠是 `spec.md`。** 本文件寫不下去是因為需求不明時，停下來請使用者改 `spec.md`（或走 `to-change-request`），不要在本文件裡自行發明需求。
- **不拆 ticket、不寫程式、不跑測試、不盤點測試覆蓋、不建立或修改任何遠端 Issue。**

## 不隨複雜度變動的部分

以下四樣是跨文件、跨 skill 的追溯基礎，**任何模式、任何規模都固定存在，不得因為「收斂」而合併或省略**：

1. **標題與文件狀態行** —— `文件狀態: brief | final (YYYY-MM-DD)`，模式判定與續作判定都吃它。
2. **`## 驗證條件` 章與 `VC-xx` 編號** —— 一章、一張表、一組編號。`to-acceptance-map` 唯一的驗證基準，章名不得改寫、不得拆成多張表、不得把條目散落到其他章節。
3. **`## 目標與範圍`** —— 範圍內／明確不做是讀審的人最先看、最會誤會的東西，再小的案子都要有。
4. **`## 修訂紀錄`** —— **有修訂才出現**，一旦出現就不刪、不合併。

其餘所有 heading 都是**候選章節**：由下面的展開判準決定它這次要不要成為獨立 heading。

## 檔案位置

`.ai/.scratch/<feature-slug>/issue-doc.md` —— 與 `spec.md`、`issues/` 同目錄。實際根目錄依 `.ai/docs/agents/issue-tracker.md`；找不到時改讀 `docs/agents/issue-tracker.md`。

## 三種模式

由文件狀態自動判定，使用者也可明確指定：

| 模式 | 何時 | 產出 |
| --- | --- | --- |
| **brief** | `issue-doc.md` 不存在 | 一頁 brief，頂部 `文件狀態: brief (YYYY-MM-DD)` |
| **修訂** | 文件存在且狀態為 `brief`，開發尚未結束 | 就地改，追加修訂紀錄 |
| **final** | 全部 ticket 完成（`to-change-request` 沒有待處理的追加票） | 校準 VC + 依既成事實補齊，狀態改為 `final (YYYY-MM-DD)` |

狀態已是 `final` 又被調用時，停下來確認：這是同一條 branch 的續作（確認後退回 `brief` 再修訂），還是該開新的 feature？**不要在 final 文件上靜默續改。**

## 前置讀取

1. `.ai/docs/agents/issue-tracker.md`（找不到改讀 `docs/agents/issue-tracker.md`）—— 檔案位置與慣例。兩者皆無則請使用者先跑 `setup-matt-preset`。
2. `.ai/docs/agents/domain.md` 指出的 `CONTEXT.md` 與 ADR —— 命名與既有決策的依據；檔案不存在時**靜默略過**。
3. `spec.md` —— 需求權威。**brief 模式必讀。**
4. `issues/` 下的 ticket（含驗收核對表）—— **final 模式必讀**；brief 模式時尚未拆票，不存在。

命名一律使用 `CONTEXT.md` 的領域詞彙；與既有 ADR 抵觸時明確指出，不默默覆蓋。

## brief 模式

在 `to-spec` 之後、`to-tickets` 之前執行。目標是**十分鐘寫完、讀審的人看得懂你要做什麼**，而且**拿得去拆票**。brief 不是縮小版的技術設計，別把它寫成 mini engineering spec。

下面五個是候選章節。`目標與範圍` 與 `驗證條件` 固定要有；另外三個**有內容才寫，沒有就整章不出現**——不要留「本次無」佔位。

```md
# <功能名稱>

文件狀態: brief (YYYY-MM-DD)

## 目標與範圍
本次要解決的問題 2-4 行。接著兩個清單：**範圍內**、**明確不做**。
「明確不做」比「範圍內」更值錢——它是讀審的人最會誤會的地方。

## 方案輪廓
打算怎麼做，讓沒讀過程式碼的人也判斷得出方向對不對：
主要參與的模組／服務、資料從哪來到哪去、既有機制沿用哪些、新增哪些。
5-10 行，或一張流程／對照表。
**不寫介面簽章、不寫欄位級 schema、不寫方法落點**——那些是 final 的事。

## 關鍵決策
一行一條，附一句取捨理由。3-5 條，通常來自 grill 的結論。
難以回復、影響超出本 feature 的，另外開 ADR 並在此指過去。
只有一條決策時，直接併進「方案輪廓」，不開獨立章。

## 驗證條件
見下方「驗證條件」一節。這是本文件唯一需要逐條確認的表。

## 風險與待釐清
**只放還沒解決的**：尚未拍板的問題、需要 owner 決定的事、上線後要追蹤的。
沒有 open 項目就整章不寫，不要留「無」。
```

寫完後把整份攤給使用者，**只針對 `VC-xx` 那張表請他逐條確認**；其餘章節請他掃一眼有無明顯錯誤。確認完成即停止，並在回報中給出可直接貼的下一步：

```text
$to-tickets 依 .ai/.scratch/<feature-slug>/spec.md 與 .ai/.scratch/<feature-slug>/issue-doc.md 拆票，並參照 .ai/docs/adr/ 與 .ai/CONTEXT.md
```

**`方案輪廓` 與 `關鍵決策` 就是拆票的輸入**，因此那一行要帶上本文件；`$to-tickets ...` 只出現在回報訊息，不寫進文件。

## 驗證條件（`VC-xx`）

**一章、一張表、一組編號，是整份文件的總驗收條件**，也是 `to-acceptance-map` 唯一的驗證基準。

寫這張表要連過四道關卡，順序不能換：**歸屬**（該不該進來）→ **強度**（有沒有超出依據）→ **可終結**（判不判得完）→ **量級**（是不是太多）。前兩道決定表裡有哪些條目，後兩道決定每條長什麼樣。**四道關卡的共同特徵是：沒過關的條目在本文件裡完全沒有症狀**——每條單看都合理、都可判斷真偽，要到 `to-acceptance-map` 才會變成一整排「覆蓋不足」。所以要在這裡逐條跑，不能靠讀起來順不順。

### 第一關：歸屬——該不該進來

> **這條若沒過，有沒有任何單一 Ticket 會發現？會，就不要寫進來。**

欄位必填、錯誤訊息原文、格式、預設值、選項連動、分頁筆數、排序方向——開票當下就驗掉了，寫進來不增加任何保護，只會讓這張表隨欄位數量無限膨脹。**這是本章最大的失控模式**，而且每一條單看都合理、都可判斷真偽，粒度檢查完全攔不住。

留下來的是**沒有任何單一切片看得到的東西**，就是下面這四類：

1. **跨切片的一致性** —— 同一取值在顯示、篩選、排序三處一致；查詢與匯出得到相同結果。
2. **整條規則的最終效果** —— 各票各做一段，合起來是否真的達成該業務規則要求的結果。
3. **權限的實際攔截** —— 不是畫面有沒有藏按鈕，是後端擋不擋得住。
4. **對實作路徑的要求** —— 但**只收已經寫進「關鍵決策」的那些**，見下一小節。

**這四類判得動不需要有票在手**——判的是條目的性質，不是切分方式；票在手上只會讓它更省力。反過來說，寫 brief 時看不到票是**好事**：否定式的約束（「未使用 X」「未產生 Y」）在票裡沒有影子，盯著票寫必然漏掉它們，而那正是這張表唯一不可取代的部分。

#### 第四類是最窄的一類，不是最方便的一類

第四類天生沒有可觀察的行為，`to-acceptance-map` 對它幾乎只判得出「不適用測試」或「覆蓋不足」。所以它的門檻要比其他三類更高，**兩個條件同時成立才收**：

1. **該約束本身已經寫進「關鍵決策」章**——VC 只負責寫「怎麼驗證那條決策成立」，不負責發明它。
2. **違反它會造成使用者觀察不到、但不可接受的後果**——例如資料外洩、既有機制被繞過。

**沒被寫成關鍵決策的實作要求一律不進本表**：隨手寫出來的 N+1、要不要 eager load、共用哪個 helper、繼承結構、方法名，那些是 coding standard 與 `to-code-review` 的事。寫進規格既擋不住也追不了，還會讓文件被下一次 refactor 弄成假的。這與 `to-engineering-spec` 的判準一致。

真的收進來的那幾條，也要寫成**可觀察的性質，不是目前的實作形狀**：

| 寫法 | 判定 | 理由 |
| --- | --- | --- |
| 列表與匯出在同一組篩選條件下結果一致，且不受分頁影響 | 寫成 VC | 可觀察，refactor 後仍該成立 |
| 列表與匯出必須共用同一個 `BuildQuery` 方法 | 不寫成 VC | 綁死方法名，那只是達成上一條的其中一種手段 |
| 沿用既有權限檢查機制，不自建第二套判定路徑（已列為關鍵決策） | 寫成 VC，`驗證方式` 填 `讀程式碼` | 決策已拍板，繞過的後果使用者看不到 |
| 清單載入不得對每列各發一次查詢 | 除非效能上界已是關鍵決策，否則不寫 | 一般情況屬 code review 的事 |
| 匯出模型必須繼承 `ExportData` | 不寫成 VC | 綁死繼承結構，換掉不影響任何可觀察行為 |

### 第二關：強度——不得超出「依據」欄

**過頭的條文是最難自己發現的失控**：每個字單看都對，但它要求的範圍比 `spec.md` 真正要求的大。它不會被歸屬判準攔下（性質確實是跨切片的），也不會被粒度檢查攔下（就是一句話），最後在盤點時變成永遠補不完的覆蓋不足。

三種典型的放大：

| 放大形式 | 例 | 收法 |
| --- | --- | --- |
| **未列舉的複數** | `spec.md` 只講了列表與匯出，VC 寫「同一取值在各處一致」 | 列明是哪幾處 |
| **補上的全稱量詞** | `spec.md` 講的是某個情境，VC 寫「任何情況下都不得…」 | 把情境寫回前提 |
| **順手升級的強度** | `spec.md` 說「預設不顯示」，VC 寫成「不得取得」 | 依 `spec.md` 的用詞，不自行加碼 |

檢查法：**把該條與 `依據` 欄指到的那句話並排，問「依據那句話沒說到的東西，這條有沒有多要求？」** 多要的部分二選一——回 `spec.md` 補成正式需求（走 `to-change-request`），或從 VC 拿掉。**不得留在表裡當隱形需求**：那是在用驗證條件擴充需求範圍，而本 skill 沒有這個權限。

### 第三關：可終結——要能被有限組斷言判完

`to-acceptance-map` 判「覆蓋不足」的定義是**只驗到部分條件**。所以一條 VC 只要含著開放式或複合式條件，它的結局幾乎固定是覆蓋不足——不是測試寫得不夠，是**條文本身沒有終點**。

寫完每條問一次：

> **要驗到什麼程度，這條才算驗完？答不出一個有限清單，就重寫。**

| 寫法 | 判定 |
| --- | --- |
| 停用的項目不出現在清單、搜尋結果與匯出檔三個入口 | 可終結——入口列明了，三個斷言就驗完 |
| 停用的項目不出現在任何取得資料的地方 | 不可終結——列明入口，或拆成各自一條 |
| 逾期單據自動結案，並通知關係人、寫入稽核紀錄 | 複合——三件事三條，或只留真正跨切片的那件 |

**同一條規則的多個等價類不各寫一條**——等價類的展開是測試程式的事，搬進表裡只是膨脹。

### 第四關：量級

`spec.md` 沒有編號的業務規則表可以當分母，所以先自己建一個：**在心裡（不寫進文件）列出本 feature 的業務規則清單**，以**約一條規則一條 VC** 為錨，再加上權限攔截與跨切片一致性各數條。一般功能 **6-10 條**。

**超過 12 條時，回頭重跑第一關，不要調降判準去遷就已經寫出來的條目。** 超量幾乎都是欄位級驗收混進來了，而它們每一條單看都合理——這就是為什麼要靠計數當觸發器，不能靠讀起來的感覺。

### 三條排除規則（寫入前逐條檢查，任一命中就不要放進來）

1. **`spec.md` 任何章節已經寫明的，不重複**——不限於驗收段落，Testing Decisions 與技術澄清也算。
2. **只是重述本文件其他章節的，刪**——「舊頁面已移除」屬於「目標與範圍」；「本次無 schema 變更」屬於技術落點。
3. **能被單一票完整擁有的，留在票裡**——這是第一關的另一種問法，寫完整張表後再掃一次，通常還會再掉幾條。

### 欄位

| 欄位 | 內容 |
| --- | --- |
| `VC-xx` | 編號。**跨文件的追溯鍵，一旦給出就不重編、不合併、不拆條** |
| 條件 | 一句話：明確前提 + 可觀察結果。需要三行才講得清楚，代表在重述需求或條件複合 |
| 依據 | 指回 `spec.md` 的 user story／業務規則，或本文件的決策。**指不回去的是新需求**，停下來請使用者先改 `spec.md`。第二關的強度校準吃這一欄 |
| 驗證方式 | 自動化測試／手動操作／查資料庫／讀程式碼，擇一。`to-acceptance-map` 的判定會吃這一欄 |

`驗證方式` 有護欄，因為 `to-acceptance-map` **不得推翻本欄**——填錯會讓真正的缺口被藏進「不適用測試」而沒有任何人發現：

- **使用者觀察得到的行為一律填 `自動化測試`。** 錯誤訊息、資料出不出現在結果中、排序、分頁、預設值都測得到。**判斷不了就填 `自動化測試`**，讓盤點時把它報成需補測試，由使用者裁決。
- 只有純視覺版面、需要真實外部環境而專案沒有建置那層測試、或約束的是實作路徑而非行為，才填其他三種，且要能一句話說出為什麼測不到。這三種**合計五條以內**；明顯更多時，多半是第一關沒跑乾淨。

## 修訂模式

開發中途改動時使用，通常由 `to-change-request` 委派，也可直接調用。

- **就地改**受影響的章節與 `VC-xx`：新增給新編號，改寫就地改，取消的**保留該列並標記「已取消（YYYY-MM-DD，原因）」**——編號不回收，否則追溯鍵會對不上先前貼出去的內容。
- 在文件末尾的「修訂紀錄」追加一列：日期、改了什麼、連帶改了 `spec.md` 的哪一段（若有）。
- 需求層級的改動（要不要做、做到什麼程度）**不在本 skill 處理**，`spec.md` 的權威不容繞過——請使用者走 `to-change-request`。
- 已完成的 ticket 一律不回頭修改。被推翻的行為靠新票收掉，現行事實靠本文件的 `VC-xx` 記錄。

## final 模式

整條 branch 的 ticket 全部完成後跑一次，**在 `to-acceptance-map` 之前**。六個步驟依序做完，**不要跳過第 2、3 步直接組版**。

### 1. 校準 `VC-xx`（先做這件事）

比對每條 `VC-xx` 與實際交付，逐條處理並在回報中明列：

- **仍成立** → 不動。
- **行為改了** → 就地改寫條文（編號不變）。
- **被後續決定取消** → 標記「已取消」，保留編號與原因。
- **實作做了、但當初漏收的跨切片要求** → 新增一條，給新編號。
- **行為沒變，但條文比實際交付寬、或條件複合** → 就地收斂成可終結的條文（編號不變）。brief 是在看不到實作的情況下寫的，寫寬是常態；**這一類在文件裡沒有任何症狀，只會在 `to-acceptance-map` 變成覆蓋不足**，所以要逐條主動跑「驗證條件」的第二關與第三關，不能只看行為有沒有改。

判斷依據是程式碼與 ticket 的驗收核對表，不是記憶。**這一步是 final 的重點**：`to-acceptance-map` 的整份盤點都建立在這張表上。

### 2. 掃過全部資訊面向（一個都不能跳）

讀程式碼、ticket 核對表與 `git diff`，對下面每一項做出結論。**這一步是分析，不是組版**——不要邊掃邊開 heading。

角色與權限 ／ 狀態與流轉 ／ 畫面與端點 ／ 業務規則 ／ 資料模型（表、欄位、索引、關聯、migration）／ 對外介面契約（API、事件、匯出格式）／ 關鍵流程與交易邊界 ／ 實作落點 ／ 交付事實 ／ 已知限制 ／ open 風險。

每項的結論只能是四種之一：**獨立成章** ／ **併入相鄰章節** ／ **一句話帶過** ／ **無資訊增量，不寫**。判準見第 3 步。

### 3. 判斷展開程度

先看整體：下列維度**命中越多，文件越該展開**。行數與 ticket 數量不是判準。

schema 變更或 migration ／ 交易邊界或併發控制 ／ 跨模組數量 ／ 外部整合 ／ API 或事件契約 ／ 權限矩陣的複雜度 ／ 真正的狀態機 ／ rollout 與回滾 ／ 難以回復的決策 ／ 向後相容 ／ 跨切片不變量的數量 ／ 需要長期維護者理解的非直覺落點。

- **命中 0-2 項（compact）** —— 典型是單表 CRUD、無 schema 變更、無交易與併發、權限沿用既有機制、enable/disable 兩態、頂多一條整合規則。目標是**少數高資訊密度的章節**：技術資訊併進最相關的章節，不各自開章。
- **命中 3 項以上（expanded）** —— `系統分析`、`資料模型`、`介面與流程`、`實作落點` 各自獨立成章是合理的，該寫多細就寫多細。

再逐面向套用展開判準：

| 資訊面向 | 獨立成章的條件 | 否則 |
| --- | --- | --- |
| **系統分析** | 多角色／權限矩陣、真正的狀態機（三態以上或有條件轉移）、多畫面或多入口、需要集中說明的一組 domain rules | 權限併進「業務規則」；enable／disable 兩態不開「狀態流程」；端點表已說清楚就不再寫一段敘述重講一次 |
| **資料模型** | 有 schema 變更、新增或改索引、新增關聯、migration 有風險、一致性／交易／併發與資料設計直接相關、既有 schema 是理解本功能不可缺的核心 | 「沿用既有 `Xxx`，本次無 schema 變更」一句話併進技術落點或方案摘要。既有 Entity 欄位是 source of truth，**不重抄欄位清單** |
| **介面與流程** | 跨服務、API／事件契約、非同步、交易邊界、外部整合、匯出／匯入的特殊契約、多步驟流程 | `Controller → Service → DB` 不值得開章。「畫面與端點」表已表達完整 CRUD 行為時，不寫第二份相同資訊 |
| **實作落點** | 有多個非直覺落點、新增了重要邊界或擴充點 | 只有 2-3 個自然落點時，寫成一小段併入相鄰章節 |
| **交付事實** | 實際交付與原方案有重大差異、有票被取消或替代、有 migration／rollout 需要追溯、團隊 workflow 明確需要 commit range 當索引 | 縮成 1-3 行或不寫。**逐票列 commit、測試條數、「N 項全數達成」屬於 PR description、release note、ticket 系統與 `acceptance-map.md`，不是本文件的內容** |

**「實作落點」是 code map，不是 repository inventory。** 只列接手維護的人真的需要知道的位置：非直覺的落點、新增的重要邊界、擴充點。不要預設列出每個 View、每個 partial、每個 ViewModel、icon 路徑、DI 註冊——那些用 IDE 搜尋兩秒就找得到，寫進來只是噪音。

### 4. 收斂 pass（組版前必做）

依序掃過五件事，每件事的處理結果都寫進回報訊息：

**a. 去重——每個事實只有一個權威位置。** 掃過全文的重要事實，各自判定它該住在哪：

| 資訊 | 權威位置 |
| --- | --- |
| 為什麼這樣取捨 | 關鍵決策／ADR |
| 系統最終必須怎麼表現 | 功能規格／業務規則 |
| 什麼做、什麼不做 | 目標與範圍 |
| 如何驗證跨切片的最終結果 | 驗證條件 `VC-xx` |
| 實作實際落在哪 | 技術落點／code map |
| 還沒解決的問題 | 風險與待釐清 |
| 已解決但值得留下的限制 | 已知限制（**不要再叫「待釐清」**） |

其他地方要提到同一件事，只做一句短引用或指向該章，**不重新完整解釋一遍**。典型的失控樣態是同一條整合規則在方案輪廓、系統分析、介面與流程、關鍵決策、VC 各講一次完整的 Why + What + How——正確做法是決策處講 Why、規格處講 What、VC 講怎麼驗。

**b. 薄章節合併。** 一個章節只有 1-3 個短 bullet、沒有獨立概念、又與前後章節強相關時，合併掉，不留獨立 heading。例：`資料模型: 本次無 schema 變更` 與 `實作落點: Controller / Service / ViewModel` 併成一章「技術落點」，兩句話講完。

**c. 已解決的事項搬家。** `風險與待釐清` 只放**還沒解決**的東西：仍可能改變實作或驗收、需要 owner 決定、上線後仍要追蹤。已經 resolved 的按性質搬走——永久的取捨 → 關鍵決策／ADR；已接受的測試缺口 → 已知限制；已定案的需求追加 → 功能規格 + 修訂紀錄；純歷史 → 修訂紀錄。搬完沒有 open 項目就**整章不出現**，不留「無」。

**d. implementation shape 降噪。** 方法名、繼承結構、partial view 清單、DI 註冊、icon 路徑、逐 commit 細節，除非是刻意保留的工程約束，否則不該成為長期規格的主體。能改寫成可觀察結果的就改寫（「共用同一個 `BuildQuery`」→「列表與匯出結果一致」）。

**e. 過期措辭。** brief 用的是未來式與計畫語氣（「打算」「預計」），final 是既成事實紀錄，把它們改成陳述句。

**收斂不等於抽象化。** 章節可以少，但實際交付的差異、契約、schema 變更、邊界仍然要寫進去——第 2 步查到的事實不會因為沒開 heading 就可以不寫。

### 5. 標出與 brief 的落差

`方案輪廓` 或 `關鍵決策` 與實際做法不同時，**列出來讓使用者裁決**是改文件、還是這確實是需要記錄的偏離。不得靜默對齊任一邊。

### 6. 輸出必須可直接貼上 Issue

final 完成的文件會被整份貼進 GitLab，因此：

- **不留本地相對連結**（`./spec.md`、`./issues/xx.md`）—— 讀者打不開。需要的內容內嵌成一兩句摘要。
- **不留 `$to-tickets ...` 之類的指令行、不留 TODO、不留內部工作註記。**
- **「風險與待釐清」若仍有未結項目，整章保留**，並在回報時提醒使用者那些會被一起貼出去。
- 不另外產生 `_deliverable.md` —— 本文件自己就是交付物。

### final 回報格式

回報訊息（不寫進文件）要包含：

1. `VC-xx` 校準結果：仍成立／改寫／收斂／取消／新增，逐條列；表末給出總條數，超過 12 條要說明為什麼留下。
2. 展開程度判定：compact 或 expanded，命中了哪幾個維度。
3. 第 2 步掃過的資訊面向，各自的結論（獨立成章／併入／一句話／不寫），**包含判定為「不寫」的那些及理由**——這是使用者確認你沒漏查的唯一依據。
4. 收斂 pass 五項的處理結果。
5. 與 brief 的落差清單，請使用者裁決。

## 適用門檻與退場

以下**兩項以上**為真時，本 skill 太輕，建議改用 `to-engineering-spec`（它有完整的系統分析與三級約束機制）：

1. 新增或調整角色與權限體系。
2. 涉及 schema 變更且牽動交易邊界或併發控制。
3. 需要改變既有架構假設，或跨三個以上模組的職責重劃。
4. 公司要求在動工前提交完整技術設計供審查。

反過來，改動小到「不動架構假設、不跨模組、無 schema 變更、VC 湊不滿 5 條」時，**直接告訴使用者本文件可以不寫**，走 `to-spec → to-tickets → implement` 即可，不要為了流程完整而生一份沒人讀的文件。

兩者之間還有第三種、也是最常見的情形：**文件要寫，但不需要展開全部章節。** 它不是另一種模式，不改文件狀態、不改檔名——由 final 第 3 步的展開判斷處理。

## 與其他 skill 的邊界

| 事實 | 權威 |
| --- | --- |
| 需求、範圍、行為 | `spec.md`（Matt `to-spec`） |
| 驗證基準 `VC-xx`、方案輪廓、關鍵決策 | **本文件** |
| 難以回復、影響超出本 feature 的決策理由 | ADR（`.ai/docs/adr/`） |
| 工作切片、逐票 commit 與驗收明細 | `issues/` 下的 ticket —— 不是需求或驗證的權威，也不需要摘進本文件 |
| 測試對 `VC-xx` 的覆蓋情形 | `acceptance-map.md`（`to-acceptance-map`） |
| 專案術語 | `.ai/CONTEXT.md` |

- **`to-tickets`** 讀 `spec.md` 與本文件的 brief 拆票（`方案輪廓`、`關鍵決策` 是切分的輸入）；本 skill 不自己拆、不調用它、不改 `issues/`。拆票過程若發現 brief 的方案輪廓站不住，回本 skill 修訂模式，不要在票裡默默改設計。
- **`to-acceptance-map`** 讀本文件的 `VC-xx`；本 skill 不做覆蓋盤點，也不把測試結果寫進本文件。
- **`to-code-review`** 與本文件無耦合。

## 下一步引導（純提示，不主動調用）

- **brief 完成** → 提示把 brief 貼上主 Issue 佔位，接著執行 `to-tickets` 拆票（那一行指令見「brief 模式」）。
- **修訂完成** → 回到 `to-change-request` 追加 ticket，或直接 `implement`。
- **final 完成** → 提示執行 `to-acceptance-map`，兩份檔案一起貼上主 Issue。
