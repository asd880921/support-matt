# 反問與待釐清事項

出現任何疑問或不明確之處時讀本文件。本 skill 對模糊需求採取**主動暫停並反問**，而非自行假設。

## 先確認「該不該問」

本 skill 位在 `grill-with-docs` 與 `to-spec` 之後。使用者已經被盤問過一輪了，**再問一次同樣的事情是浪費**，也會讓人懷疑前面那輪白做。

問之前先跑三個檢查：

1. **Matt Spec 或當前對話有沒有答案？** 有 → 引用它，不問。
2. **程式碼能不能回答？** 能 → 自己查，不問。ADR 與 `.ai/CONTEXT.md` 同理。
3. **我能不能合理判斷、並承擔被推翻的風險？** 能 → 做出決策，標 `> **設計決策**：` 附理由與替代方案，不問。

三個都否，且**缺少的東西會影響需求理解或重大設計**，才問。

**「能自行判斷」不等於「可以自己編」**：資料表欄位名稱可以自己取（設計決策），但「這個欄位到底要不要存歷史值」若牽動業務語意，就要問。

## 必須立即停下來提問的情況

出現以下任一情況時，**立即停止撰寫並向使用者提問**，取得明確回覆後才繼續：

- 需求語意有多種解讀，而不同解讀會產生不同的狀態機或不同的資料模型。
- 邊界不清晰：不確定某職責、組件、資料或流程是否屬於本次範圍。
- 角色、權限、業務規則、狀態流轉或預期行為無法從 Matt Spec、ADR 或程式碼確認。
- 任何會實質改變範圍或架構的判斷。
- 驗證條件寫到一半發現**某條指不回任何 user story、BR 或設計章節**——那是新需求，不是判準。**本 skill 不得藉由寫驗證條件擴充或縮減需求範圍**，停下來請使用者先改 Matt Spec。
- 資料來源、資料流或資料寫入責任不明。
- 錯誤處理、重試、冪等或一致性策略無法判斷。
- 設計段發現分析段已確認的內容有問題（不得自行推翻後繼續）。
- **Matt Spec 與本文件、ADR 或程式碼互相衝突**——見 SKILL.md 的「衝突處理」。

禁止以「先假設一個方向繼續做」或「這部分之後再說」的方式略過。

## 提問風格

- 一次提出一到三個重點問題，聚焦在會改變文件的關鍵點。
- 盡可能提供具體選項。
- 僅在 Matt Spec 或程式碼強烈暗示某一方向時，才標記建議答案。
- 簡短說明答案會如何影響文件——講清楚它會動到哪一章。
- 問衝突時，把雙方原文各引一句，讓使用者不必自己去翻。
- 待疑問解決、或經使用者同意記錄為待釐清事項後，才繼續起草。

## 「待釐清事項」的彙整

凡是曾被跳過、暫緩討論、或尚未達成共識的問題，一律完整彙整至「待釐清事項」章節，不得遺漏或省略。這包含：

- 經提問後，使用者選擇暫緩或跳過的問題。
- 提問後仍未達成共識、或回覆不足以定案的事項。
- 需由特定角色（需求方、PO、工程審查）後續回答的開放問題。
- 程式碼查找中發現、無法憑現有資訊裁決的落差或模糊點。
- **尚未裁決的文件衝突**——此時該列要註明衝突的另一方在哪（`spec.md` 的哪一段、哪一則 ADR）。

此章節**不得作為逃避設計責任的區塊**。只有在確實缺少必要資訊、且無法由 Matt Spec、現有程式碼或使用者補充合理推導時，才列入。

每個待釐清事項應描述清楚：問題是什麼、目前缺少什麼資訊、會影響哪個分析結果或設計判斷、建議向誰或透過什麼方式確認。

有未解問題時：每個問題一列，編號 `Q1`、`Q2`；以分析 / 設計角度描述影響；建議由誰或透過何種方式回答。

無未解問題時：保留章節，填入一列 `目前無待釐清事項 | 無 | 無`。

## 修訂處理方式

使用者回答「待釐清事項」中的問題時：

- 將確認的答案寫入**對應章節的權威位置**（依 `writing-rules.md` 的分工表），只寫一處。
- 從「待釐清事項」移除已回答的列。
- 若該答案原本是以 `> **設計決策**：` 暫定的判斷，且使用者確認了不同方向，更新該處決策內容並保留被推翻的方案於 `替代方案`。
- 若答案屬於需求、範圍或行為（要不要做、做到什麼程度），**它的家是 Matt Spec**——請使用者更新 `spec.md`，本文件只同步受影響的設計章節與 `VC-xx`。
- 若答案是**怎麼驗證它成立**（判準、邊界值、錯誤訊息文字），家是本文件的「驗證條件」章，直接寫進去。
- 若無問題剩餘，保留章節並以 `目前無待釐清事項` 列取代表格內容。
