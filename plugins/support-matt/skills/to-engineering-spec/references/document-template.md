# engineering-spec.md 模板

起草或修訂 `engineering-spec.md` 時使用本模板。

寫作規則（單一事實來源、三種膨脹、精簡準則）見 `writing-rules.md`；技術內容的三種約束程度見 `constraint-levels.md`。兩者都是本模板的前提，起草前必讀。

文件**不切成「SA」「SD」兩大章**。系統分析與系統設計是寫作者腦中的分層，不外顯成章節標籤——讀者拿到的是一份連貫的規格。

## Required Style

- 繁體中文，台灣軟體開發常用語。除標點符號外，所有特殊符號一律半形。
- 每個事實只在其權威章節定義一次；需求類事實引用 Matt Spec，不複製。
- 表格單格內容超過約 80 字時改用小節。
- 只有三種標記：`> **設計決策**：`、`> **實作方向**：`、「待釐清事項」的一列。不使用來源標記欄位。
- 不寫成 coding plan、commit 計畫或 Ticket 清單；不出現「此部分由下游設計」「留待後續補充」等轉嫁語句。
- 章節依實際情境選用；無關者依下方「章節去留」處置，不留只有標題或填「無」的空洞章節。
- 不寫讀者能自己推導出來的內容（`writing-rules.md` 第四章）；推導不明顯但重要的，收斂成一條驗證條件。
- 沒有 Agent 對話痕跡、沒有開發過程日誌、沒有內部工作註記（「修訂紀錄」一列一句除外）。
- 本模板產出的是**工作版**。要貼回公司 GitLab Issue 時，由 `engineering-spec-deliverable` 產出交付版，不在此就地改寫。

## 行數預算

每章標題旁的 `≤ N 行` 是**膨脹的警報器，不是刪除細節的授權**。

超出時的處置順序固定：先跑三種膨脹檢查（重複 / 越界 / 可推導，見 `writing-rules.md` 第〇章），把重複收斂成引用、把越界的內容搬家、把可推導的刪掉。**查完仍然超出，就照實寫超出**——`writing-rules.md` 第八章列的那些（錯誤訊息原文、狀態轉移、併發約束、邊界值、決策理由）一項都不准為了達標而消失。

為了壓行數而砍細節，是本 skill 最嚴重的違規：讀者少讀幾行，換來的是下游回頭問人。

## Section Guidance

只寫模板本身看不出來的判斷。**每一章的職責在模板的 blockquote 裡，不在這裡重述。**

- **文件資訊**：審查者的入口，也是最容易膨脹成第二份規格的地方。`本次改動` 只列對象不列理由，`審閱重點` 只指章節不重述決策——它們在正文都有家。`文件狀態` 反映流程進度（`分析中` → `設計中` → `可拆 Ticket` → `定稿`）；`Matt Spec` 列必填，它是需求權威的入口。
- **一、背景與目的**：**這裡最容易變成 Matt Spec 的換句話說**——寫完回頭檢查：有沒有一句話是 `spec.md` 已經說過的？
- **二、範圍與非範圍**：系統邊界，不是產品範圍。「不動 `OrderExport` 模組」是這裡的內容；「這一期不做行動版」是 Matt Spec 的內容。
- **三、角色與權限**：`依賴判斷` 是本章重點。授權需要「權限 × 資料歸屬 / 層級 / 狀態」的組合時，**為每個依賴條件取一個具名判斷式**（例如 `CanActAsOriginator`），在此定義一次，後續一律引用名稱——沒有具名判斷式，同一段依賴邏輯會在權限表、動作表、介面契約、驗證條件各重寫一次。判斷式刻意不含權限本身（保持正交）。`動作與權限對照` 跟第四章的動作對照表是同一張表的兩種型態，不是兩張表——家隨「有沒有狀態機」而定，任何情況下只存在一份。
- **四、狀態與流程**：**先確認這個功能有沒有狀態機。** 沒有（唯讀查詢、報表、設定頁）就不要硬套：一張「狀態轉移」欄整欄填「無」的表毫無資訊量，還會讓讀者以為漏寫。狀態圖畫**完整**轉移，不畫「主線」再另用表格補其餘——那會產生兩份不一致的狀態機描述。`動作對照表` 的 `副作用` 欄填**一句話 + BR 編號**，只填編號的格會逼讀者跳轉才知道這個動作做了什麼。
- **五、功能介面**：**這一章存在的理由是：沒有它，欄位表、必填、預設值、選單與按鈕位置會無處可去，只好擠進 BR。** 與八、介面契約的分界是「使用者看到什麼」vs「程式之間傳什麼」——同一個欄位兩章都提到時，語意的權威在本章，wire shape 的權威在介面契約。欄位語意、必填性、預設值是設計決策；版面位置、元件選型是實作方向。
- **六、業務規則與例外**：一條 BR 一個 h3 小節，**規則 / 判定 / 理由**三段。「理由」只回答「為什麼是這樣而不是那樣」，一到兩句——它是這章對審查者最有價值的一段，也是最常被寫成論文的一段。**寫每一條前先跑 `writing-rules.md` 的三問**，這一章是全文件最容易被灌入非規則內容的地方。`實作約束` 區塊吸收了「實作注意事項」章節的全部內容；本模板刻意沒有那個章節，不要自行加回來。
- **七、模組責任 / 八、介面契約**：責任邊界是設計決策，封裝落點與沿用模式是實作方向——一列一列分清楚，別整章同一個溫度。介面契約分頁面 / 資料兩類：頁面端點硬套 REST 契約只是製造空欄位，資料端點不寫欄位形狀則前端接不上。
- **九、資料與 Schema**：整章是設計決策。涉及 persisted data 時先讀 `data-design-checklist.md`。無 schema 變更時只留資料來源與查詢策略。
- **十、交易與併發**：這一章最容易復活成「實作注意事項」，寫每一列前都跑一次「能不能搬進 BR」的測試。
- **十三、驗證條件**：必為正文倒數第二章。**行為與實作約束同表，靠 `驗證方式` 欄區分，不拆兩章**——「觀察得到 vs 觀察不到」是怎麼檢查它的差異，那是欄位的事；拿它當章節邊界只會逼寫作者逐條裁決，而且放錯章沒有任何症狀。**安全與正確性的實作要求歸這裡**——「Server 端必須獨立驗權限，不可只靠隱藏按鈕」是驗證條件，不是 BR。這章的價值全部押在粒度上：可判斷真偽才有用，寫成需求摘要就白寫了。開發中新長出來的邊界值與錯誤訊息，定稿時要從 Ticket 收斂回這裡。
- **十四、交給 to-tickets**：必為正文最後一章，內容固定，照上面抄，不要每次重寫措辭——下游 Agent 靠這段的穩定性辨認約束程度。**`$to-tickets ...` 那一行指令不寫進文件**，它是給使用者的操作提示，只出現在回報訊息裡。

「章節依實際情境選用」不是模糊建議，是三種明確處置。**任何情況下都不留一個只有標題、內文寫「無」「N/A」「不適用」的章節或區塊。**

| 章節 / 區塊 | 無內容時 |
| --- | --- |
| 十二、待釐清事項 | **保留**，填一列 `目前無待釐清事項` |
| 十三、驗證條件 | **保留**。這章空掉代表需求沒有任何可判斷真偽的結果，那是分析沒做完，不是章節不適用——回頭補，不要填「無」 |
| 十四、交給 to-tickets | **保留**，內容固定 |
| 九、資料與 Schema | **保留標題**，寫一句「本次無 schema 變更」加上資料來源與查詢策略，省略前三節 |
| 十一、相容性與風險 | **保留標題**，寫一句「本次無破壞性變更」 |
| 四、狀態與流程 | 無狀態機且無分支流程 → **整章移除** |
| 五、功能介面 | 無畫面（批次、純 API、事件消費者）→ **整章移除** |
| 十、交易與併發 | 每一列都能搬進某條 BR → **整章移除** |

| BR 的「錯誤處理」/「實作約束」 | 該條規則沒有 → **整個區塊移除**，不留空標題 |

**「保留標題 + 一句話」與「整章移除」的差別**：讀者拿到一份開發規格，會預期它交代資料與相容性；那兩章的沉默會被讀成漏寫，所以明說一句。其餘章節不存在就是不適用，讀者不會去找。
