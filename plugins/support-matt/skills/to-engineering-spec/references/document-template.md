# engineering-spec.md 模板

起草或修訂 `engineering-spec.md` 時使用本模板。

寫作規則（單一事實來源、三種膨脹、精簡準則）見 `writing-rules.md`；技術內容的三種約束程度見 `constraint-levels.md`。兩者都是本模板的前提，起草前必讀。

文件**不切成「SA」「SD」兩大章**。系統分析與系統設計是寫作者腦中的分層，不外顯成章節標籤——讀者拿到的是一份連貫的規格。

## Required Style

- 繁體中文，台灣軟體開發常用語。除標點符號外，所有特殊符號一律半形。
- 每個事實只在其權威章節定義一次；需求類事實引用 Matt Spec，不複製。
- 表格單格內容超過約 80 字時改用小節。
- 只有三種標記：`> **設計決策**：`、`> **實作方向**：`、「待釐清事項」的一列。不使用來源標記欄位。
- **模板裡說明章節職責與寫法的 blockquote 是給寫作者的，不抄進產出文件。** 產出文件裡的 blockquote 只有四種：背景與目的的 `> **摘要**：`、角色與權限的權限模型、`> **設計決策**：`、`> **實作方向**：`。除此之外，產出文件不對讀者說明「這一章要寫什麼」——章名已經說了。
- **不寫給審查者的導讀。** 「本章最需要注意的是…」「請特別檢查…」這類句子，代表某個事實沒有被放進它該去的章節；把它放回去（風險放變更影響，取捨放該 BR 的「已知取捨」），不要在別處補一段提醒。
- 不寫成 coding plan、commit 計畫或 Ticket 清單；不出現「此部分由下游設計」「留待後續補充」等轉嫁語句。
- **章節標題不編號。** 追溯靠 heading 名稱與 `BR-xx` / `VC-xx`；章節會依需求增減，用序號當識別碼只會逼你為了不斷號而把該省的章補回來。
- 章節依實際情境選用：先跑下方「章節存在門檻」，再依「章節去留」處置。不留只有標題、填「無」，或整章只承載一句否定句的章節。
- 不寫讀者能自己推導出來的內容（`writing-rules.md` 第四章）；推導不明顯但重要的，收斂成一條驗證條件。
- 沒有 Agent 對話痕跡、沒有開發過程日誌、沒有內部工作註記（「修訂紀錄」一列一句除外）。
- 本模板產出的是**工作版**。要貼回公司 GitLab Issue 時，由 `engineering-spec-deliverable` 產出交付版，不在此就地改寫。

## 行數預算

每章標題旁的 `≤ N 行` 是**收斂的壓力，不是刪除細節的授權**。它預設你會達標——超出是例外，例外要先付出代價才拿得到。

超出時**先收斂，四步跑完仍不達標才放行**，順序固定：

1. **重複**（`writing-rules.md` 第〇章）——同一事實出現在多章時，留權威位置那一份，其餘改成帶摘要的引用。
2. **越界**——不符合本章職責的內容**搬到它該去的章節**。搬家不減少全文總行數，但這一章會回到預算內，而那一章本來就該收下它。
3. **可推導**（`writing-rules.md` 第四章）——讀過其他章節的工程師自己得出得來的話，刪掉；推導不明顯而代價高的，收斂成**一條**驗證條件。
4. **形式**——只有一項的條列改寫成句子；線性流程的 mermaid 改成文字；重述章節職責的開場白與結尾總結刪掉；表格單格超過約 80 字的改用小節。

**四步跑完仍然超出，就照實寫超出，不再壓縮。**

放行不是預設值：**四步都跑過才輪得到它**。超出幅度也在告訴你哪一步沒跑——只超一兩成通常是第 4 步，超過一倍通常是第 2 步（這一章已經變成垃圾桶了）。

不准用來達標的手段（`writing-rules.md` 第八章的完整清單）：刪掉任何一條錯誤訊息原文、任何一次狀態轉移、任何一個併發或交易約束、任何一條權限或依賴條件、任何一個邊界值或預設值、任何一項設計決策的理由。

為了壓行數而砍細節，是本 skill 最嚴重的違規：讀者少讀幾行，換來的是下游回頭問人。

## 章節存在門檻

**先把每個維度查完、想完，再決定它要不要成為 heading。** 這一節優先於下方 Markdown Structure 的章節列舉——那份列舉是**候選章節**，不是必產目錄。

每個維度只有四種結論：**獨立成章** ／ **併入相鄰章節** ／ **一句話帶過** ／ **不適用，不寫**。

| 章節 | 獨立成章的門檻 | 未達門檻時 |
| --- | --- | --- |
| **文件資訊** | 固定存在 | — |
| **背景與目的** | 固定存在，但要短。只回答「這個設計在系統裡解決什麼問題、為什麼需要一份工程規格」 | 「本次改動」表已交代 feature 形狀時，正文壓到一段 |
| **範圍與非範圍** | 有容易被誤解的相鄰模組、跨模組職責需要畫界、有名稱相近的既有功能要澄清 | 系統邊界本身就清楚時，只留真正會影響工程判斷的幾列，不為了完整而湊「不包含」 |
| **角色與權限** | 新增或修改權限模型、多角色矩陣、有具名依賴判斷式、資料歸屬 / 可見範圍、授權跨狀態或跨資料條件 | 所有端點沿用同一組既有權限、無額外依賴時，把「動作 → 權限」併進功能介面的動作表或相關 BR，一句話交代沿用哪組權限 |
| **狀態與流程** | 有狀態機、多分支流程、跨步驟編排、rollback / retry / 補償路徑，或不看流程就判斷不了正確性 | enable/disable 兩態或一般 CRUD 生命週期 → **整章不寫**，動作與權限對照移進角色與權限 |
| **功能介面** | 使用者介面本身有設計資訊：欄位連動成網、多入口、狀態造成 UI 行為差異、匯入匯出契約、搜尋 / 篩選 / 結果語意重要 | 純 API / 事件 / 批次 → 整章不寫。普通 CRUD 表單且欄位規則自然屬於 BR → 縮成一節「操作介面」，不硬撐四個 subsection |
| **業務規則與例外** | 固定存在，是文件的重心 | — |
| **模組責任** | 多模組、多 service / repository、寫入責任需要切分、有擴充點、動到共用元件 | 完全沿用既有架構、只是 `Controller → Service → Repository` → 不要把分層清單當設計；唯一值得記的落點寫進相關 BR 或一段「設計摘要」 |
| **介面契約** | 形狀是跨模組契約：對外 API、事件 / 訊息 schema、整合邊界、向後相容、另一個 consumer 依賴它 | 只是一般 MVC 頁面動作或 CRUD 端點 → 有端點**不等於**端點形狀是架構契約；路由與權限併進功能介面或動作表 |
| **資料與 Schema** | schema 變更、新表 / 欄位 / 索引 / 關聯、migration、seed / backfill、source of truth 設計、資料生命週期與保存期限、persistence ownership，或查詢 / 索引設計本身是核心風險 | 沿用單一既有表、無 schema 變更、無 migration、無新的資料 ownership 決策 → **不開章**，「沿用既有 `Xxx`，本次無 schema 變更」寫在文件資訊的 `Schema` 列、模組責任或相關 BR **其中一處**即可 |
| **資料存取與一致性** | 跨 BR 的交易邊界、併發模型、隔離等級、鎖順序、冪等、系統層級重試、大量查詢 / 索引策略、跨表一致性 | 一般單表 CRUD，且交易與唯一性都能在某條 BR 的「實作約束」講清楚 → 整章不寫 |
| **變更影響** | 有實質的相容性、rollout、migration 或下游影響 | 沒有 → **整章不寫**。不要留一句「本次無破壞性變更」當一章 |
| **待釐清事項** | 仍有未解問題 | 全部結清 → **整章不寫**，不留 `目前無待釐清事項` |
| **驗證條件** | 固定存在。空掉代表分析沒做完，回頭補 | — |
| **交給 to-tickets** | 固定存在（下游機器契約，理由見該章） | — |

**合併不是目標，比例才是。** 權限、schema、交易、契約真的各自複雜時，它們**本來就該各自成章**——本 skill 服務的正是那種需求。合併只針對薄章：只有 1-3 行、沒有獨立概念、又與相鄰章節強相關的那種。

## 否定資訊預算

工程規格很容易被這類句子撐大：本次無 schema 變更 / 無破壞性變更 / 無狀態機 / 無交易邊界 / 無待釐清事項 / 無外部整合 / 無 migration。

**不是所有「沒有」都值得寫。** 判準：

> **讀者有沒有可能合理誤判有這件事，而且誤判會影響設計、實作或審查？**

- **值得留**：「本次不建表，`DmsVendor` 由前置作業建置，本 feature 只讀寫既有主檔」——有人可能以為本次要負責建表，這句同時交代了 ownership 邊界。
- **不值得留**：「本次無破壞性變更」——沒人預期會有，這句只是填版面。

**真正的否定式設計決策不受本節限制**：不做 migration、不建歷史表、不提供刪除、不做重試、不允許跨租戶——那些有取捨、有替代方案，是設計的一部分。它們留在對應的 BR、`> **設計決策**：`、範圍邊界或 ADR，不因為長得像否定句就被刪掉。

## Markdown Structure

````text
# <功能名稱> 開發規格

## 文件資訊　`≤ 25 行`

| 項目 | 內容 |
| --- | --- |
| 所屬模組 / 系統 | <模組名稱> |
| Matt Spec | [spec.md](./spec.md)（需求、範圍與行為的權威；驗證條件見本文件的「驗證條件」章） |
| 相關 ADR | <.ai/docs/adr/0007-xxx.md，一行一則帶一句摘要；無則填「無」> |
| 公司 Issue | <GitLab Issue 連結或編號；無則省略此列> |
| 專案類型 | <既有專案 / 全新專案> |
| 文件狀態 | <分析中 / 設計中 / 可拆 Ticket / 定稿；附日期> |

**本次改動**

| 動作 | 對象 |
| --- | --- |
| 新增 | <模組 / 端點 / 頁面 / 選單項目> |
| 修改 | <既有權限兩項改名、品號詳細頁按鈕改導向> |
| 移除 | <舊子頁三個路由> |
| Schema | **無變更** / <新增 xx 表> |

<本表是審查者的入口：三十秒內知道這次動到哪裡。它與範圍與非範圍不重疊——本表是**動作視角**（新增什麼、改什麼、刪什麼），範圍章是**邊界視角**（哪些模組會被動到、哪些明確不動）。**只列對象不列理由**，理由在正文各章。>

## 背景與目的　`≤ 20 行`

> **摘要**：<一句話講這個功能做什麼。例：把庫存異動記錄抽為獨立功能，查詢對象由單一品號擴大為六類設備>

<1-2 段：這個功能為何存在、支援什麼使用情境、在系統中的核心職責是什麼。**不要重述上面的摘要**——摘要說過的那一句，正文不再講第二次。>

**不重寫 user stories。** 需求細節見 [spec.md](./spec.md)；此處只交代系統視角的定位。

**邊界定位**：<相關但不在本次範圍的功能、前後階段、後續模組，說明它們與本功能的關係。無則省略此段。>

## 範圍與非範圍　`≤ 20 行`

> 此章寫**系統邊界**——哪些模組會被動到、哪些明確不動、哪些資料不碰。產品層級的 Out of Scope 見 [spec.md](./spec.md)，不在此重複。

| 類型 | 項目 | 說明 |
| --- | --- | --- |
| 包含 | <模組 / 資料 / 流程> | <本次會動到什麼> |
| 部分包含 | <項目> | <講清楚哪一部分動、哪一部分不動> |
| 不包含 | <項目> | <為何排除、由誰承接> |

<「不包含」是全章對審查者最有價值的幾列——它擋掉來回確認，也擋掉範圍蔓延。**名稱相近但無關的既有功能寫在這裡澄清**。>

## 角色與權限　`≤ 30 行`

> **全部沿用既有權限、且無依賴條件時整章不寫**（見「章節存在門檻」）——那句「所有端點沿用既有 `XxxPermission`」放進功能介面的動作表或相關 BR 就夠了。本章的價值在權限模型本身有東西可說：新增或修改的權限、多角色矩陣、具名依賴判斷式、資料歸屬與可見範圍。
>
> 權限模型：<一至數句說明權限如何分組、範圍 / 依賴邏輯如何運作。依專案實際採用的權限機制描述，不寫死特定名詞。>

### 權限清單

| 權限 | 涵蓋動作 | 說明 |
| --- | --- | --- |
| <權限鍵或權限名稱> | <涵蓋哪些動作> | <說明> |

### 依賴判斷

<當「有權限」還不足以放行、另需資料歸屬 / 層級 / 狀態等依賴條件時使用；無此類依賴則整節省略。>

**為每個依賴條件取一個具名判斷式並在此定義一次**，後續章節一律引用名稱，不重述判斷內容：

| 判斷式 | 定義 | 適用動作 |
| --- | --- | --- |
| `<判斷式名稱>` | <精確定義：需要滿足什麼條件> | <引用動作名稱（有狀態機時在「狀態與流程」的動作對照表，無狀態機時在下方的動作與權限對照）> |

**例外**：<豁免上述依賴的角色或身分，以及豁免的邊界。無則省略。>

### 動作與權限對照

<**只有無狀態機的功能才有本節**；有狀態機時，本表帶著「狀態轉移」欄放在「狀態與流程」的動作對照表，此處整節省略。兩處不並存。>

本表是**動作與其權限、依賴、副作用的唯一權威**。其他章節引用動作名稱，不重述權限。

| 動作 | 權限 | 依賴 | 副作用 |
| --- | --- | --- | --- |
| <動作> | <權限鍵> | <引用上方判斷式名稱，無則 —> | <一句摘要 + BR 編號，如「見 BR-03：僅回傳所屬單位資料」；不可只填編號> |

## 狀態與流程　`≤ 40 行`

> **無狀態機的功能：** 不要保留一張「狀態轉移」欄全填「無」的表。動作與權限的對照移到角色與權限的「動作與權限對照」節，本章只保留仍有分支判斷的流程；連那個也沒有時，**整章省略**。

## 功能介面　`≤ 60 行`

> **無畫面（批次、純 API、事件消費者）整章不寫。** 普通 CRUD 表單、欄位規則自然屬於 BR 時，縮成一節「操作介面」，不硬撐下面四個 subsection。
>
> 本章是**使用者看到什麼**的唯一權威：畫面上有哪些欄位、必填什麼、預設什麼、選項怎麼連動、從哪裡進來。程式之間傳什麼是介面契約的事；欄位的儲存型別與長度是資料與 Schema 的事。
>
> 屬於分析段——這些內容人可以直接審，不需要看 codebase。
>
> **無畫面的功能（批次、純 API、事件消費者）整章省略**，不要留空標題。

**填 `靜態檢查` 的那些是拆票前就要遵守的實作約束**（橫跨數條 BR 的一致性要求、約束實作路徑而非行為的要求、跨模組收斂要求），不是等驗收才看的事——強制力由「設計決策」標記承載，不因為與行為條目同表而降級。它們通常在五條以內。

<定稿模式追加一欄「驗證結果」（通過 / 未驗證 / 不適用）。開發中新增、改寫或移除的條目在此就地收斂——改寫的直接改那一條，不新增第二條並存；移除的刪掉並在修訂紀錄記一列。>
````

## Section Guidance

只寫模板本身看不出來的判斷。**每一章的職責在模板的 blockquote 裡，不在這裡重述。**

- **文件資訊**：審查者的入口，也是最容易膨脹成第二份規格的地方。`本次改動` 只列對象不列理由——理由在正文都有家。**不要加「審閱重點」這類導讀**：值得被挑戰的決策，本來就該在變更影響或該 BR 的「已知取捨」被看見；要靠開頭補一段提醒才看得到，代表那兩個位置沒寫好。`文件狀態` 反映流程進度（`分析中` → `設計中` → `可拆 Ticket` → `定稿`）；`Matt Spec` 列必填。
- **背景與目的**：**這裡最容易變成 Matt Spec 的換句話說**——寫完回頭檢查：有沒有一句話是 `spec.md` 已經說過的？
- **範圍與非範圍**：系統邊界，不是產品範圍。「不動 `OrderExport` 模組」是這裡的內容；「這一期不做行動版」是 Matt Spec 的內容。
- **角色與權限**：`依賴判斷` 是本章重點。授權需要「權限 × 資料歸屬 / 層級 / 狀態」的組合時，**為每個依賴條件取一個具名判斷式**（例如 `CanActAsOriginator`），在此定義一次，後續一律引用名稱——沒有具名判斷式，同一段依賴邏輯會在權限表、動作表、介面契約、驗證條件各重寫一次。判斷式刻意不含權限本身（保持正交）。`動作與權限對照` 跟「狀態與流程」的動作對照表是同一張表的兩種型態，不是兩張表——家隨「有沒有狀態機」而定，任何情況下只存在一份。
- **狀態與流程**：**先確認這個功能有沒有狀態機。** 沒有（唯讀查詢、報表、設定頁）就不要硬套：一張「狀態轉移」欄整欄填「無」的表毫無資訊量，還會讓讀者以為漏寫。狀態圖畫**完整**轉移，不畫「主線」再另用表格補其餘——那會產生兩份不一致的狀態機描述。`動作對照表` 的 `副作用` 欄填**一句話 + BR 編號**，只填編號的格會逼讀者跳轉才知道這個動作做了什麼。
- **功能介面**：**這一章存在的理由是：沒有它，欄位表、必填、預設值、選單與按鈕位置會無處可去，只好擠進 BR。** 與介面契約的分界是「使用者看到什麼」vs「程式之間傳什麼」——同一個欄位兩章都提到時，語意的權威在本章，wire shape 的權威在介面契約。欄位語意、必填性、預設值是設計決策；版面位置、元件選型是實作方向。
- **業務規則與例外**：一條 BR 一個 h3 小節，**規則 / 判定 / 理由**三段。「理由」只回答「為什麼是這樣而不是那樣」，一到兩句——它是這章對審查者最有價值的一段，也是最常被寫成論文的一段。**寫每一條前先跑 `writing-rules.md` 的三問**，這一章是全文件最容易被灌入非規則內容的地方。`實作約束` 區塊吸收了「實作注意事項」章節的全部內容；本模板刻意沒有那個章節，不要自行加回來。
- **模組責任 / 介面契約**：責任邊界是設計決策，封裝落點與沿用模式是實作方向——一列一列分清楚，別整章同一個溫度。介面契約分頁面 / 資料兩類：頁面端點硬套 REST 契約只是製造空欄位，資料端點不寫欄位形狀則前端接不上。
- **資料與 Schema**：整章是設計決策。涉及 persisted data 時先讀 `data-design-checklist.md`。**無 schema 變更、無 migration、沿用單一既有表時整章不寫**——那句「沿用既有 `Xxx`」放進文件資訊的 `Schema` 列、模組責任或相關 BR 其中一處；只有在資料來源本身是設計資訊（多來源、衍生值、權威歸屬有爭議）時，才為它保留章節。
- **資料存取與一致性**：這一章最容易復活成「實作注意事項」，寫每一列前都跑一次「能不能搬進 BR」的測試。**唯讀功能不要把這章寫成兩句「無交易、無併發控制」**——那等於整章在說自己不適用；唯讀功能真正的內容在讀取一致性、資料量上界與索引使用，章名可改為「資料讀取與一致性」。**但也不要往下滑進程式寫法**：這章的界線是「規格能決定的事」，資料量上界與索引策略是，取幾次資料庫不是。
- **驗證條件**：必為正文倒數第二章。**行為與實作約束同表，靠 `驗證方式` 欄區分，不拆兩章**——「觀察得到 vs 觀察不到」是怎麼檢查它的差異，那是欄位的事；拿它當章節邊界只會逼寫作者逐條裁決，而且放錯章沒有任何症狀。**安全與正確性的實作要求歸這裡**——「Server 端必須獨立驗權限，不可只靠隱藏按鈕」是驗證條件，不是 BR。這章的價值全部押在粒度上：可判斷真偽才有用，寫成需求摘要就白寫了。開發中新長出來的邊界值與錯誤訊息，定稿時要從 Ticket 收斂回這裡。
- **交給 to-tickets**：必為正文最後一章，內容固定，照上面抄，不要每次重寫措辭——它是下游 Agent 唯一能得知三種約束程度與驗證基準位置的地方，也是交付版唯一整章刪掉的一章。**不要把 feature 專屬內容寫進來，也不要在這裡重述整套 workflow。****`$to-tickets ...` 那一行指令不寫進文件**，它是給使用者的操作提示，只出現在回報訊息裡。

## 章節去留

「章節依實際情境選用」不是模糊建議。**任何情況下都不留只有標題、內文寫「無」「N/A」「不適用」的章節或區塊，也不留整章只承載一句否定句的章節。**

| 章節 / 區塊 | 無實質內容時 |
| --- | --- |
| 文件資訊 / 背景與目的 / 業務規則與例外 | **固定保留**（背景與目的可壓到一段） |
| 驗證條件 | **固定保留**。這章空掉代表需求沒有任何可判斷真偽的結果，那是分析沒做完，不是章節不適用——回頭補，不要填「無」 |
| 交給 to-tickets | **固定保留**，內容固定（下游機器契約） |
| 待釐清事項 | 全部結清 → **整章移除**，不留 `目前無待釐清事項` |
| 資料與 Schema | 未達「章節存在門檻」→ **整章移除**；那句「沿用既有 `Xxx`，本次無 schema 變更」放進文件資訊的 `Schema` 列、模組責任或相關 BR **其中一處** |
| 變更影響 | 無實質相容性 / rollout / migration / 下游影響 → **整章移除**；不留「本次無破壞性變更」 |
| 狀態與流程 | 無狀態機且無分支流程 → **整章移除** |
| 功能介面 | 無畫面（批次、純 API、事件消費者）→ **整章移除**；普通 CRUD 表單 → 縮成一節「操作介面」 |
| 角色與權限 | 全部沿用既有權限且無依賴條件 → **整章移除**，動作與權限對照併進功能介面或相關 BR |
| 介面契約 | 沒有跨模組契約（只是一般頁面 / CRUD 端點）→ **整章移除**，路由與權限併進功能介面或動作表 |
| 模組責任 | 完全沿用既有分層、無 ownership 切分與擴充點 → **整章移除**，唯一值得記的落點併進相關 BR |
| 資料存取與一致性 | 每一列都能搬進某條 BR → **整章移除** |
| 角色與權限的「依賴判斷」/「例外」 | 無此類條件 → **整節移除** |
| 介面契約的「頁面端點」/「資料端點」 | 專案沒有那一類 → **整節移除** |
| 模組責任的「主要互動」 | 組件少或關係顯而易見 → **整節移除** |
| BR 的「錯誤處理」/「實作約束」 | 該條規則沒有 → **整個區塊移除**，不留空標題 |

**章節標題不編號，所以移除章節不需要重編任何東西**，也不會出現斷號。跨章引用一律用 heading 名稱與 `BR-xx` / `VC-xx`。

**移除 heading 不等於移除資訊。** 併進別章的內容照樣要完整——併過去之後，那一處就是它唯一的權威位置。查過但不適用的維度才是真的不寫。

## 各模式的章節分佈

| 階段 | 產出章節 | 文件狀態 |
| --- | --- | --- |
| 建立 · 分析段 | 文件資訊（`本次改動` 的 Schema 列可暫填待確認）、背景與目的、業務規則與例外（BR 的 `實作約束` 留空），加上通過門檻的分析章節（範圍與非範圍、角色與權限、狀態與流程、功能介面）、待釐清事項（若有） | `分析中` |
| 建立 · 設計段 | 回填 BR 的 `實作約束`、加上通過門檻的設計章節（模組責任、介面契約、資料與 Schema、資料存取與一致性、變更影響）、驗證條件、交給 to-tickets | `設計中` → `可拆 Ticket` |
| 修訂 | 就地改權威位置那一處；追加「修訂紀錄」一列。行為有變時**同步改掉對應的 `VC-xx`**，不新增第二條並存。改動使某章只剩一兩句時，依「章節去留」併掉 | 維持 `可拆 Ticket` |
