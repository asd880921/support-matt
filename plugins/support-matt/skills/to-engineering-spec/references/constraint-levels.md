# 約束程度：設計決策 / 實作方向 / 實作示意

寫任何技術內容前先讀本文件。這是本 skill 與 Matt `implement` 之間的介面。

## 為什麼需要三層

正式規格若把每個施工細節都寫死，下游 Agent 拿著半年前的設計硬幹，會做出比它自己判斷更差的東西；若什麼都不寫死，資料表名、API contract、交易邊界就會在四個 Ticket 裡長出四種版本。

所以文件要能回答讀者一個問題：**「這段我可以改嗎？」**

三個答案，三種程度：

| 程度 | 這段我可以改嗎 | 偏離的處理 |
| --- | --- | --- |
| **設計決策** | 不行 | 回 `to-engineering-spec` 修訂模式，改了文件才能改程式 |
| **實作方向** | 可以，但要說 | 在 Ticket 或 PR 記錄原因；`code-review` 會核對 |
| **實作示意** | 本來就不是約束 | 不需處理 |

## 設計決策（已確認，必須遵守）

**判準**：改了它，別人寫的程式會接不上，或已完成的 Ticket 要重做。

典型內容：

- 資料表與欄位名稱、型別、必填性、索引
- API contract（method + path、request / response 欄位、狀態碼）
- 公開介面與跨模組簽章
- 交易邊界（哪些寫入必須同一筆交易）
- 併發控制方式（樂觀 / 悲觀、CAS 條件、重試策略）
- 模組責任邊界（誰負責寫這張表、誰不准直接碰）
- 必須共用的核心元件（不得各自複製一份）
- 已確認的類別或介面名稱
- 狀態機的合法轉移集合
- 錯誤訊息原文
- 畫面欄位的語意、必填性與預設值

**標記法**：

大多數情況**不需要標記**——「資料與 Schema」整章、「介面契約」整章、動作對照表，本身就是設計決策，靠章節性質即可辨認。

只在下列兩種情況顯式標記：

1. 這個判斷是本次**主動做出、有替代方案被排除**的，理由值得留下。
2. 它出現在一個以「實作方向」為主的章節裡，需要跟周圍區隔。

```markdown
> **設計決策**：庫存扣減採 `UPDATE ... WHERE Quantity >= @Qty` 的單語句原子扣量，依 affected rows 判斷成敗（理由：SQL Server 下可避免先讀後寫的競態，且不需升級隔離等級；替代方案：`SERIALIZABLE` 交易——被排除，該表在尖峰時段的鎖等待會外溢到報表查詢）。
```

`理由` 必填。`替代方案` 有才寫；沒有真的被排除的方案就不要編一個。

## 實作方向（原則上遵循，可提出調整）

**判準**：改了它，只有寫這段程式的人受影響；別人的介面、資料與行為都不變。

典型內容：

- 建議封裝在哪一層
- 預計調整哪些模組、哪些既有元件可沿用
- 建議的資料流與呼叫順序
- 方法責任的切法
- 測試切入點（在哪個 seam 測）
- 建議的既有實作模式（「照 `OrderCancelService` 那套寫」）
- 畫面的版面位置、元件選型、欄寬

**標記法**：

```markdown
> **實作方向**：庫存異動封裝在 `InventoryWriter`，由 `TransferApprovalService` 呼叫，不讓 Controller 直接碰 Repository（依 codebase 發現更合適的落點時可調整，請於 Ticket 或 PR 說明原因）。
```

括號那句可以省略——`> **實作方向**：` 這個標記本身就已定義了「可調整但要說」。整章都是實作方向時，在章節開頭寫一次 blockquote 說明即可，不必每列都掛。

**測試切入點屬於實作方向，不是設計決策**，除非 Matt Spec 的 Testing Decisions 已經把 seam 定死——那時它的權威在 Matt Spec，本文件引用即可，不重寫。

## 實作示意（僅協助閱讀）

**判準**：它存在的唯一理由是「用散文講會很囉嗦」。

典型內容：

- 方法簽章示意
- SQL 或 pseudo code
- 類別關係範例
- 可能的命名候選

**標記法**：程式碼區塊正上方一行斜體註記，不可省略。

```markdown
*實作示意（非固定簽章）*

\`\`\`csharp
Task<Result<TransferId>> ApproveAsync(TransferId id, UserId approver, CancellationToken ct);
\`\`\`
```

**寫實作示意前先問一句：這段能不能用一句話講完？** 能，就用散文，別放程式碼——每一段沒有必要的 pseudo code 都在增加下游把它當契約抄進去的機率。

**例外**：若某個型別 shape、狀態機或 schema **本身就是設計決策**（改了會接不上），它就不是示意。把它放進設計決策，標記寫成 `> **設計決策**：`，程式碼區塊上方不掛「非固定簽章」的註記，並在該處明說「此形狀為契約」。

## 分界練習

同一個功能的四句話，四種程度：

| 內容 | 程度 | 為什麼 |
| --- | --- | --- |
| `DmsTransferOrder.ApprovedBy` 為 `nvarchar(50) NOT NULL` | 設計決策 | 別人的 INSERT 會壞 |
| 審核與庫存異動必須在同一筆交易 | 設計決策 | 改了會產生資料不一致 |
| 建議把交易邊界開在 `TransferApprovalService.ApproveAsync` | 實作方向 | 開在哪個方法不影響外部行為，只要邊界成立 |
| `ApproveAsync(TransferId, UserId, CancellationToken)` | 實作示意 | 參數順序與 `CancellationToken` 有無不影響任何人 |

**最常見的錯誤是把第三列寫成設計決策。** 「交易邊界必須涵蓋 A 與 B」是約束，「開在哪個方法」是施工。前者鎖住、後者放開，才是這三層存在的意義。

第二常見的錯誤是**整份文件沒有任何實作方向**——那代表所有技術內容都被寫成了硬約束，下游 Agent 只能照抄，`implement` 的判斷力完全浪費掉。設計段完成後自檢一次：這份文件裡有幾條實作方向？答案是零的話，回去看有哪些「設計決策」其實只是施工偏好。

## 給下游的一致性

三種程度的意義在 handoff 章節（見 `document-template.md`）向 `to-tickets` 完整交代一次，`code-review` 的 Spec axis 也依它判斷：

- 違反**設計決策** → 是缺陷，退回修正或回本 skill 修訂文件。
- 偏離**實作方向**且有記錄原因 → 不是缺陷；把該處更新進文件（定稿模式處理）。
- 偏離**實作方向**且沒有記錄 → 是缺陷（靜默偏離）。
- 沒照**實作示意** → 不是缺陷，不要報。
