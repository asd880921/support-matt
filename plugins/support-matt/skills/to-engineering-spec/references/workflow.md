# 三種模式與確認關卡

開始任何寫入前先讀本文件。本 skill 產出**一份** `engineering-spec.md`，三種模式共用同一份文件。

## 模式判定

先看使用者有沒有明講（`建立` / `修訂` / `定稿`，或 `create` / `revise` / `finalize`）。有就照講的做，不要自己推翻。

沒明講時依文件狀態判定：

| 觀察到的狀態 | 模式 |
| --- | --- |
| `.scratch/<feature-slug>/engineering-spec.md` 不存在 | 建立（分析段） |
| 文件存在，`文件狀態` = `分析中`，使用者帶著確認或修正回來 | 建立（設計段） |
| 文件存在且已到 `可拆 Ticket` 以上，開發尚未結束 | 修訂 |
| 開發與 code review 已完成，使用者要求核對／收尾／交件 | 定稿 |

**判定不明確時直接問，一句話就好。** 猜錯的代價很大：把「修訂」做成「建立」會蓋掉已確認的設計；把「定稿」做成「修訂」會讓實作偏差被靜默寫成正式設計。

## 建立模式

### 為什麼分析段與設計段之間要停

需求（做什麼、誰能做、狀態怎麼流轉）與設計（程式落點、資料落點、實作約束）的**修正成本差很多**。系統分析走偏而沒被攔下，後面所有設計細節都白做。

這個關卡是**審查節奏，不是文件分層**。文件全程只有一份、章節連續、不標記哪段是誰產的。讀者拿到的是一份完整規格，看不出它分兩次寫成。

**它與 Matt 的 grilling 不重複。** grilling 確認的是「要不要做、做什麼」；這個關卡確認的是「我把它理解成這樣的角色、狀態與規則，對不對」——同一份需求換成系統視角後，經常會冒出 Matt Spec 沒討論到的狀態轉移與例外分支。

### 切點

| 段 | 產出 | 文件狀態 |
| --- | --- | --- |
| **分析段** | 文件資訊（含一句話、本次改動、審閱重點）、一 背景與目的、二 範圍與非範圍、三 角色與權限、四 狀態與流程、五 功能介面、六 業務規則與例外（**`實作約束` 區塊留空**）、待釐清事項 | `分析中` |
| **設計段** | 回填各 BR 的 `實作約束`、七 模組責任、八 介面契約、九 資料與 Schema、十 交易與併發、十一 相容性與風險、十二 待釐清事項（重編）、十三 驗證條件、十四 交給 to-tickets | `設計中` → `可拆 Ticket` |

切點落在「規則本文 vs 規則的實作約束」之間。規則說「庫存不足時擋下並回這句訊息」屬於分析，人可以審；「用 `UPDATE ... WHERE Quantity >= @n` 的原子扣量、依 affected rows 判斷」屬於設計，要看過 codebase 才寫得出來。前者定案，後者才有依據。

### 分析段流程

1. 讀 Matt Spec 全文（通常 `.scratch/<feature-slug>/spec.md`）、當前對話、`CONTEXT.md`、`docs/adr/` 中相關的 ADR。確認 `feature-slug` 與 `docs/agents/issue-tracker.md` 的 tracker 設定。
2. 依 SKILL.md 的「適用門檻」判斷值不值得產出。三者以上皆否時停下來告知使用者可走 Matt 原生流程。
3. 判斷既有專案 / 全新專案。既有專案讀 `codebase-discovery.md` 查找現況——**分析段也要查找**，因為現有的角色、狀態、規則與術語會直接改變分析的寫法。術語一律對齊 `CONTEXT.md`。
4. 讀 `writing-rules.md`、`constraint-levels.md`、`document-template.md`，寫出分析段章節。
5. 過程中出現疑問，依 `clarification-and-open-questions.md` 立即停下來問；被暫緩的問題全數進「待釐清事項」。已在 grilling 或 Matt Spec 確認的事不重問。
6. **跑一次「送出前自檢」**（見下方共用的「送出前自檢」章節），發現的問題就地修掉。
7. 寫入 `engineering-spec.md`，`文件狀態` 填 `分析中`。
8. 在 Matt Spec 頂部補上一行指標（若尚未存在）：`> Engineering spec: [engineering-spec.md](./engineering-spec.md)`。這是唯一允許對 Matt Spec 做的改動。
9. **停止**。回報檔案路徑、摘要、待釐清事項狀態，明確告知使用者：確認後回來執行設計段。不自動接續。

### 設計段流程

1. 讀現有 `engineering-spec.md` 全文與使用者的確認 / 修正意見。
2. 使用者若對分析段內容有修正，**先改分析章節，再展開設計**。不要帶著舊理解做設計。
3. 既有專案：依 `codebase-discovery.md` 針對設計面查找（既有模組、命名慣例、資料結構、併發與權限檢查方式、可沿用的實作模式）。
4. 涉及 persisted data 時讀 `data-design-checklist.md`，做出明確的資料設計決策。
5. 依 `constraint-levels.md` 把每一項技術內容放進正確的約束程度。**這是設計段最容易做錯的一步**：把所有東西都寫成設計決策會鎖死 Matt 的自由度，全寫成實作方向則等於沒有約束。
6. 回填各 BR 的 `實作約束`；補上模組責任、介面契約、資料與 Schema、交易與併發、相容性與風險；待釐清事項重編號；新增驗證條件與 handoff 章節。
7. **跑一次「送出前自檢」**（見下方共用的「送出前自檢」章節），含追加項；發現的問題就地修掉。
8. 就地更新同一份 `engineering-spec.md`，不另開新檔。`文件狀態` 更新為 `設計中` 或 `可拆 Ticket`。
9. 停止。回報摘要、待釐清事項狀態，並輸出可直接貼上的 `to-tickets` 呼叫。

### 防呆

- **分析段不寫設計**。不寫模組責任、介面契約、Schema、交易邊界。忍不住想寫，代表你在跳過確認關卡。**但「五、功能介面」屬於分析段**——畫面上有哪些欄位、必填什麼、預設什麼、從哪裡進來，人可以直接審，不需要看 codebase；把它推遲到設計段等於讓確認關卡漏掉最容易被誤解的一塊。
- **設計段不重做分析**。分析段已確認的範圍、規則、狀態機是 contract。發現它有問題時，停下來問使用者，不要自行推翻後繼續。
- **不因分兩段而重複**。設計章節與分析章節之間一樣受單一事實來源約束——`實作約束` 引用它所屬的 BR，不重述規則；介面契約引用動作名稱，不重述權限。
- **使用者要求一次做完時**，仍照兩段順序寫（分析章節先定稿再展開設計），但可不停下來等確認；此時明確告知使用者跳過了確認關卡。
- **不硬套狀態機**。功能沒有狀態轉移時（唯讀查詢、報表、設定頁），第四章的狀態圖與動作對照表不是「填無」而是不存在；動作與權限的對照移進三、角色與權限。見 `writing-rules.md` 反模式 6。
- **一次只處理一個 feature**。

## 送出前自檢

**四種情境都要跑：分析段、設計段、修訂、定稿。** 寫完、**停止之前**跑一次，發現的問題就地修掉。

這份文件的第一讀者是要實作它的工程師——他讀不下去，下游拿到的就是一份沒人真正看過的規格。

共通：

1. **重複**——挑 3 個事實（一條規則、一個權限條件、一個欄位），各查一次它出現在幾個章節。超過一處、且不是帶摘要的引用，收斂到權威位置。
2. **越界**——每一章抽 3 條內容跑歸屬測試（`writing-rules.md` 第〇章）。不符合章節職責的**搬家**，不是刪除。
3. **可推導**——每條 BR 問一次：讀過其他章節的工程師，能不能自己得出這句話？能就刪掉，或收斂成一條驗證條件（`writing-rules.md` 第四章）。
4. **措辭**——同一個限定語（「僅限所屬單位」這類）寫了三次以上嗎？給它一個名字，或上收成表格上方的一句前提。同一個概念全文有沒有混用兩三種說法？有沒有把集合跟它的元素並列？
5. **空章節**——有沒有只剩標題、內文是「無」「N/A」「不適用」的章節或區塊？依 `document-template.md` 的「章節去留」處置。
6. **體積**——BR 數量對照 `writing-rules.md` 的規模參考，明顯偏多時回頭對每條跑一次三問。各章對照 `document-template.md` 標註的行數預算；超出的章節逐一跑該文件「行數預算」的四步收斂，**四步跑完仍超出才照實寫超出，且不為了達標砍細節**。
7. **單邊遺漏**——**掃一次 Matt Spec 的 Implementation Decisions / technical clarifications 這類區塊**，逐條判斷它是需求層級事實還是設計事實。是設計事實，就確認本文件有章節承載它；沒有就是漏了。處置見 SKILL.md 的「單邊遺漏」。

設計段、修訂、定稿追加：

8. **約束程度**——這份文件有幾條「實作方向」？零的話回去重新分級（`constraint-levels.md`）。
9. **驗證條件的體積**——有沒有一條超過一句？超過代表它在重述 BR。填 `靜態檢查` 的超過十條，代表三條排除規則沒被執行。
10. **驗證條件的粒度**——抽 3 條問：不看文件其他章節，能不能直接判定它成立或不成立？答不出來就是粒度上浮了，補上前提與可觀察結果。再確認每條的「依據」都指得回 user story、BR 或設計章節，指不回去的是夾帶的新需求。
11. **驗證方式**——有沒有觀察得到的行為被填成 `人工檢視` 或 `靜態檢查`？錯誤訊息、必填、排序、分頁、預設值、權限被拒都測得到，一律填 `自動化測試`。

第 7 項最容易被略過，因為**它是唯一一項「文件本身沒有任何徵兆」的檢查**。前六項都能從文件內部看出症狀；單邊遺漏在本文件裡完全沒有痕跡——那條事實只是不在這裡而已。必須主動去 Matt Spec 對一遍才查得到。

自檢結果不寫進文件，也不寫進回報訊息——它是寫作紀律，不是產出物。

## 修訂模式

開發中發現需求、規則、設計或模組分解需要改變時使用。

### 流程

1. 讀現有 `engineering-spec.md` 全文、最新 Matt Spec、相關 ADR，以及 `.scratch/<feature-slug>/issues/` 的現況（哪些 Ticket 已發布、哪些已完成）。
2. **判斷這件事該不該進正式規格**：

   | 情況 | 處理 |
   | --- | --- |
   | 改到需求、範圍或行為（要不要做、做到什麼程度） | 屬於 Matt Spec。停下來說明，請使用者改 Matt Spec；本文件只同步受影響的設計章節與 `VC-xx` |
   | 改到系統分析、設計決策或實作約束 | 本文件就地修訂 |
   | 改到怎麼驗證需求成立（判準、邊界值、錯誤訊息文字） | 本文件的「驗證條件」章就地修訂——**改掉原本那條 `VC-xx`，不新增第二條並存**；行為被移除時刪掉該條 |
   | 重大、難以回復、有真實取捨的決策理由 | 補一則 ADR，本文件引用它，不複製理由全文 |
   | 只是局部實作細節，不影響已確認的設計決策 | **明說「不需修訂正式規格」並停手**。不要為了留紀錄而膨脹文件 |

3. 找出該事實的**唯一權威位置**，只改那一處。若改完覺得別處也要跟著改，代表那裡違規重述了——把它改成引用，而不是同步更新兩份。
4. 標記的升降級要跟著改：一項「實作方向」被確認為必須遵守 → 升為「設計決策」；一項「設計決策」被推翻 → 改寫該處決策內容並保留被推翻的理由（`替代方案` 欄），不刪掉歷史判斷。
5. 更新「修訂紀錄」一列（日期、改了什麼、為什麼）。這是文件裡**唯一**允許出現的過程性內容，一次修訂一列、一列一句。
6. **跑一次「送出前自檢」**。修訂特別容易踩第 7 項：這次改動若是因為 Matt Spec 更新而來，新增的設計事實很可能還躺在 `spec.md` 沒被接過來。
7. 回報「修訂影響」：
   - 受影響的 Matt Spec 段落（列出，但不代改）。
   - 受影響的 ADR（需要新增或更新哪一則）。
   - 受影響的已發布 Tickets（列出編號與影響），**不直接修改已發布 Ticket**，除非使用者明確要求。
8. 停止並回報。

### 防呆

- **不因程式碼已經這樣實作，就把偏差合理化成正式設計。** 實作先跑掉了，正確做法是問使用者「接受這個實作、還是把程式改回設計」，而不是把文件改成跟程式一樣。
- **不建立第二份取代文件。** 沒有 `-v2`、沒有 `engineering-spec-new.md`、沒有另存副本。
- **不刪掉已完成 Ticket 依據的設計決策。** 那條決策已經是交付的一部分；要改的話標明從何時起改變。

## 定稿模式

開發與 code review 完成後，核對並定稿同一份文件。

### 輸入

最新 Matt Spec、現有 `engineering-spec.md`、相關 ADR、最終 git diff、最終程式碼、測試與驗收結果、`.scratch/<feature-slug>/issues/` 的完成狀態。

### 流程

1. **三方比對**。逐項對照，一項一列：

   | 欄 | 內容 |
   | --- | --- |
   | 預期需求 | Matt Spec 說要什麼 |
   | 確認設計 | 本文件的設計決策 / 實作方向 |
   | 實際實作 | git diff 與最終程式碼實際做了什麼 |

2. **分類結果**：

   | 結果 | 處理 |
   | --- | --- |
   | 三者一致 | 不動。文件已描述實際交付結果 |
   | 不一致，但有正式修訂依據（修訂紀錄 / ADR / 使用者確認） | 同步回文件，讓文件描述實際結果 |
   | 不一致，且**沒有**修訂紀錄 | 列為**偏差**，寫進「偏差與待處理」章節。**不得直接覆寫原設計** |
   | 「實作方向」被下游合理調整並記錄了原因 | 更新該處內容，並保留調整原因一句 |
   | 「實作方向」被靜默偏離 | 也是偏差。標出來 |

3. **偏差要有結論才移除**。使用者確認接受該實作結果後，才修訂對應章節、把該偏差列刪掉；使用者要求改程式的，偏差列保留並註明「待修正」，文件不改。
4. **清掉已失效的預計做法**。定稿文件描述的是實際交付結果，不是當初的計畫。「預計調整 X 模組」若最後沒動，刪掉；動的是 Y，寫 Y。
5. **保留設計決策理由，不保留過程日誌**。「為什麼選悲觀鎖」要留；「第 3 個 Ticket 卡了兩天因為測試環境」不要。修訂紀錄保留，但收斂成一列一句。
6. 「驗證條件」逐條標註驗證結果（通過 / 未驗證 / 不適用），未通過者進「偏差與待處理」。
7. **從 Ticket 收斂「驗證條件」**。掃過本 branch 全部 Ticket，三種情況分別處理：開發中新長出來的可觀察行為（邊界值、錯誤訊息原文）→ 補一條 `VC-xx`；後開的票推翻或改寫了先前行為 → **就地改掉那條，不新增第二條並存**；功能被移除 → 刪掉該條並在修訂紀錄記一列。**Ticket 本身不回頭修改**，它是切片當下的快照，收斂只發生在本文件。

   這一步漏掉，下游 `to-acceptance-map` 會拿一份過期的驗收基準去盤點，把已經砍掉的功能報成「需補測試」、把改過的規則報成「覆蓋不足」。
8. **跑一次「送出前自檢」**。定稿是最後一次補上單邊遺漏的機會——開發過程中補進 `spec.md` 的技術澄清，很可能從未進到本文件。
9. `文件狀態` 更新為 `定稿`（附日期）。
10. 停止。列出仍存在的偏差（若有），並告知使用者：要貼回公司 GitLab Issue 時，用 `engineering-spec-deliverable` 產出交付版 `engineering-spec_deliverable.md`，本文件不動；要附上自動化測試的覆蓋情形，用 `to-acceptance-map` 產出 `acceptance-map.md`。

### 防呆

- **定稿不是橡皮圖章**。若三方比對只花了兩分鐘、沒讀 git diff，那不是定稿，是簽名。
- **偏差不是失敗**。它是這份文件最有價值的產出之一：它讓「規格與實作不一致」變成一件被看見、被決策的事，而不是被程式碼默默改寫的事。
- **不把 Matt Spec 的 user stories 抄進來當交付證明**。「驗證條件」章寫的是怎麼驗證它成立，不是需求本身的換句話說；每條都要指得回 user story 或 BR。
- **不把測試結果寫進本文件**。哪條驗證條件有沒有自動化測試守著，是 `to-acceptance-map` 的 `acceptance-map.md` 的事，兩份各自獨立。
