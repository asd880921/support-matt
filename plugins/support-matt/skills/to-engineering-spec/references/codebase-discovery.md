# 程式碼查找（既有專案）

對既有專案查找相關現有程式碼時讀本文件。全新專案略過，直接進入設計。

查找與文件撰寫同時進行，不分成兩個階段。

**先讀 `.ai/CONTEXT.md`**（或 `.ai/CONTEXT-MAP.md` 指到的那一份）。文件用字一律對齊它——它標了 `_Avoid_` 的字不要用，也不要自創同義詞。同樣先掃一遍 `.ai/docs/adr/`：本次要動的區域若已有 ADR，設計必須遵守它，或明確提出要推翻它並補新的 ADR。

## 兩段各查什麼

### 分析段

目的是讓分析結果與系統現況對齊。查找：

- 目前由哪些組件承載相關職責，以及責任邊界在哪。
- 現有流程、狀態、入口與串接方式。
- 現有角色、權限、所有權與審批行為。
- 現有業務規則、驗證與例外處理。
- 可複用的既有能力，或與 Matt Spec 行為的落差。
- **專案現有術語**——對照 `.ai/CONTEXT.md`，發現未收錄的重要術語時提出補進去（由 `domain-modeling` 負責寫，不自己改）。
- 對外整合點與依賴（概念層級）。

分析段**不**擷取：資料表欄位、API 合約、route 命名、逐方法實作細節。那些是設計段的事。

### 設計段

目的是讓設計落在正確的程式與資料位置。查找：

- 既有 API、controller、service、repository、model、job、event、queue、config。
- Route、command、event handler、排程任務的進入點與負責元件。
- 既有命名慣例、資料結構、DTO / ViewModel、request / response 型別、SQL 與資料表。
- 既有錯誤處理、retry、驗證、concurrency 與邊界情況處理方式。
- 既有權限檢查、ownership、資料可見範圍、稽核 / logging 機制。
- 既有測試、fixture、seed、feature flag、migration 與相容性處理。
- **既有的測試 seam**——Matt Spec 的 Testing Decisions 偏好沿用既有 seam；查到現成的就引用它，不要提議新開一個。
- 上下游依賴與外部整合設定。

## 擷取原則

- **把觀察轉化為設計影響，而非列出檔案。** 「`InventoryWriter` 目前只動待安裝桶，需擴充為跨狀態桶成對加減」是設計影響；「有一個檔案叫 `InventoryWriter.cs`」不是。
- 只在有助於工程審查時，才列出精確的路徑、類別、方法、資料表或 enum 名稱。
- **不要僅憑命名相似就認定為同一事物。** 存在多個候選元件時，檢查足夠上下文以確認最可能的負責方，或把此模糊點記入「待釐清事項」。
- 指出應以哪個現有模組作為實作模式，並說明為何適合沿用——這通常是**實作方向**（`> **實作方向**：`），不是設計決策。
- 把缺乏實作支撐的情況記錄為設計缺口或風險（「十一、變更影響」）。
- **不臆造**資料庫欄位、API 合約、權限或業務規則。所有陳述須有 Matt Spec、對話或程式碼依據。
- 影響實作信心的測試覆蓋缺口值得記錄。

## 程式碼與 Matt Spec 不一致時

依 SKILL.md 的「衝突處理」**停下來向使用者確認**，不得自行判定以哪一方為準。程式碼現況可能揭示 Matt Spec 未涵蓋或已過時的限制——這類落差由使用者裁決，不可在文件中悄悄以某一方覆蓋另一方。

**特別是定稿模式**：程式碼已經這樣寫，不等於設計就該改成這樣。那是偏差，不是既成事實。

## 呈現方式

查找結果不另闢章節堆放，而是**融入它該去的地方**：

| 查到什麼 | 寫進哪一章 | 哪一段 |
| --- | --- | --- |
| 現有權限機制 | 三、角色與權限 | 分析段 |
| 現有狀態與流程 | 四、狀態與流程 | 分析段 |
| 現有畫面欄位與入口 | 五、功能介面 | 分析段 |
| 現有規則與驗證 | 六、業務規則與例外 | 分析段 |
| 現有職責與模組 | 七、模組責任 | 設計段 |
| 現有 API 與型別 | 八、介面契約 | 設計段 |
| 現有資料表與欄位 | 九、資料與 Schema | 設計段 |
| 現有併發與交易處理 | 十、資料存取與一致性 或所屬 BR 的實作約束 | 設計段 |
| 既有整合點的相容性風險 | 十一、變更影響 | 設計段 |

不要產出「程式碼查找結果」這種章節——它會變成與正文重複的第二份描述，違反 `writing-rules.md` 的單一事實來源。
