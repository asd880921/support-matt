# 寫作規則

起草或修訂 `engineering-spec.md` 前必讀。本文件是 `document-template.md` 的前提：模板規定**放什麼**，本文件規定**怎麼寫才不膨脹**。

**這份文件的第一讀者是人——實作這個功能的工程師。** 他要能從頭讀到尾、讀完知道該怎麼開工。下游 Agent 是第二讀者，而它們吃得下的重複，人讀不下去；反過來，一份工程師願意讀完的文件，Agent 一定也用得了。兩者衝突時，以人為準。

規格文件難讀的成因，幾乎不是「細節太多」，而是同一件事被講了很多次、或講了根本不必講的話。細節是讀者要的，重複與贅語才是負擔。因此本 skill 的產出目標不是「短」，而是**同水準的資訊量 + 每句話都在說新東西**。收斂的手段是刪除重複與贅語，不是刪除細節——為了縮短而砍掉一條錯誤訊息、一個併發條件或一次狀態轉移，是嚴重違規。

## 〇、膨脹怎麼衡量（先讀這條，否則會把改對的當成改壞的）

**膨脹的單位不是行數。**

最招牌的改動——業務規則從表格列升格為小節（反模式 2）——**必然使行數上升**：同一段 1,600 字元的規則，塞在表格裡是 1 行，攤成小節是約 40 行。資訊量沒變、可讀性大幅改善，但行數多了 39 行。**行數上升是這個改動成功的副產品，不是失敗的徵兆。**

壓行數最快的手段，正好是砍錯誤訊息、砍併發條件、砍設計理由——也就是本文第八章明訂絕不能砍的東西。

膨脹有三種，症狀不同、查法不同、修法也不同：

| 型態 | 症狀 | 怎麼查 | 怎麼修 |
| --- | --- | --- | --- |
| **重複** | 同一事實出現 N 次 | 數次數 | 留權威位置那一份，其餘改成帶摘要的引用 |
| **越界** | 事實出現在錯的章節 | 逐章跑歸屬測試 | **搬家**，不是刪除 |
| **可推導** | 內容是別處已寫內容的必然結果 | 跑推導測試（本文第四章） | 刪掉，或收斂成一條驗證條件 |

**後兩種躲得過第一種的檢查。** 越界與可推導的內容每一條都只出現一次，數次數會全數放行。典型失控長這樣——一個唯讀查詢頁產出 20 條 BR：查詢條件表、結果欄位表、選單位置、按鈕位置各佔一條（越界），另有數條只是把權限章與模組責任章的結論再講一遍（可推導）。沒有任何重複，但只有 6 條是真的業務規則。

### 歸屬測試（查越界）

寫完或修訂完一章後，對該章抽 3 條內容，各問一次：

1. **這一章的職責是什麼？** 一句話講不出來，代表這一章已經變成垃圾桶了。
2. **這條符合那個職責嗎？**
3. 不符合的話，**它的家在哪？**

最需要跑這個測試的是六、業務規則與例外——它是全文件唯一一個「什麼都塞得進去」的章節，因為任何約束都能被寫成「約束 + 違反時的處理」。搭配本文第三章的三問使用。

### 常見誤放對照表

| 誤放的內容 | 最常被放進 | 正確的家 |
| --- | --- | --- |
| 查詢條件、結果欄位、必填、預設值、格式 | 六、業務規則 | 五、功能介面 |
| 選單位置、按鈕位置、進入條件 | 六、業務規則 | 五、功能介面的「入口與導向」 |
| 「本次不做 X」「X 由另一期處理」 | 六、業務規則 | 二、範圍與非範圍 |
| 某個動作需要哪個權限 | 六、業務規則 / 八、介面契約 | 動作對照表（有狀態機在四，無則在三） |
| 依賴條件的判斷內容 | 散落各章 | 三、依賴判斷的具名判斷式 |
| 欄位的 SQL 型別、長度、索引 | 五、功能介面 / 六、業務規則 | 九、資料與 Schema |
| request / response 欄位 | 六、業務規則 | 八、介面契約 |
| 程式落點、共用哪個方法 | 六、業務規則 | 七、模組責任 |
| 安全實作要求（不可只靠前端擋） | 六、業務規則 | 十三、驗證條件 |
| **單條**規則的交易邊界 | 十、交易與併發 | 該 BR 的「實作約束」 |
| **跨規則**的併發模型 | 某一條 BR | 十、交易與併發 |
| 功能為何存在的產品理由 | 一、背景與目的 | Matt Spec，本文件只引用 |

### 越界的處置一律是搬家

這一節與「八、什麼絕不能砍」不衝突：那一章管的是**內容不能消失**，這一節管的是**內容要放對地方**。

上面那個 20 條 BR 的例子，正解是收到 6 條、文件從 480 行降到 317 行，而**沒有任何一條錯誤訊息、任何一個邊界值、任何一項決策理由消失**——砍掉的 14 條全部是搬到功能介面章與範圍章，不是刪掉的。

**修訂時發現越界，不要就地重寫成引用。** 引用是「重複」的解法；越界的解法是把整段內容原封不動移到它該去的章節，再視需要於原處留一個帶摘要的引用（或什麼都不留）。

## 一、跨文件的單一事實來源（先於文件內部）

寫任何一句話之前，先問：**這個事實的權威是哪一份文件？**

| 事實類型 | 權威文件 | 本文件怎麼寫 |
| --- | --- | --- |
| 需求、範圍、行為、user stories | Matt Spec (`./spec.md`) | 引用 + 一句摘要 |
| 專案術語定義 | `CONTEXT.md` | 直接用它的字，不重新定義 |
| 重大決策的理由 | ADR (`docs/adr/`) | 引用編號 + 一句摘要 |
| 系統分析、設計決策、實作約束 | **本文件** | 在此定義一次 |
| 驗證條件（怎麼驗證需求成立） | **本文件**的「驗證條件」章 | 在此定義一次，每條指回 user story、BR 或設計章節編號 |
| 工作切片 | Tickets | 完全不寫；本文件不列 Ticket |

完整權威順序與衝突處理見 `matt-workflow-integration.md`。

**最常見的違規**：把 Matt Spec 的 user stories 換句話說抄進「一、背景與目的」，於是需求有了兩份互相競爭的版本。正確做法是一句話帶過功能是什麼，然後 `見 [spec.md](./spec.md)`。

## 二、文件內部的單一事實來源

**每個事實只有一個章節能定義它。其他章節只能引用編號或名稱，不得重述內容。**

| 事實類型 | 唯一權威位置 | 其他章節怎麼寫 |
| --- | --- | --- |
| 狀態轉移（誰、從什麼狀態到什麼狀態） | 四、動作對照表 | 引用動作名稱 |
| 動作所需權限、依賴與副作用 | 有狀態機 → 四、動作對照表；無狀態機 → 三、動作與權限對照 | 引用動作名稱 |
| 授權依賴條件的定義 | 三、依賴判斷（具名判斷式） | 引用判斷式名稱 |
| 畫面欄位規格（必填、預設、格式、選項連動） | 五、功能介面 | 引用欄位名稱 |
| 入口位置與導向（選單、按鈕、進入條件） | 五、功能介面的「入口與導向」 | 引用入口名稱 |
| 欄位驗證的錯誤訊息原文 | 五、功能介面的「條件驗證與錯誤訊息」 | 引用欄位名稱 |
| 業務規則本文 | 六、對應 BR 小節 | 引用 BR 編號 |
| 業務規則的錯誤訊息原文 | 六、對應 BR 小節的「錯誤處理」 | 引用 BR 編號 |
| 單條規則的交易邊界、原子性、檢查順序 | 六、對應 BR 小節的「實作約束」 | 引用 BR 編號 |
| 系統層級的併發模型（隔離等級、重試、鎖順序） | 十、交易與併發 | 引用該節 |
| 程式落點（模組、類別、方法、路由） | 七、模組責任 / 八、介面契約 | 引用模組或介面名稱 |
| 資料表結構與儲存型別 | 九、資料與 Schema | 引用資料表或欄位名稱 |
| 設計決策與其理由 | 該決策所屬章節的 `> **設計決策**：` | 引用該章節 |

**十章與 BR「實作約束」的分界**：**單條規則**的交易邊界寫在該 BR（「審核與庫存異動同一筆交易，見 BR-07」）；**跨規則、系統層級**的併發模型寫在第十章（「本模組一律樂觀鎖 + 最多重試 1 次，隔離等級維持 READ COMMITTED」）。判準：這句話只服務一條規則，還是所有規則都要遵守？

**這不是把舊模板的「實作注意事項」章節換個名字裝回來**——那一章的每一列都是別章的重述（反模式 3）。第十章只寫「別章沒有、也放不進任何單一 BR」的東西。寫進第十章的每一列，都要能通過一個測試：把它搬進某條 BR 會不會更合適？會，就搬過去。

### 具名概念與前提上收

單一事實來源不只管「事實」，也管**措辭**。同一個限定語在文件裡反覆出現，讀者每讀一次都要重新確認它是不是同一件事：

- 「僅限登入者所屬單位」出現在權限章、動作對照表、三條 BR、介面契約與驗證條件，六處措辭各有微差——讀者無從判斷是同一條還是六條。
- 「未刪除且啟用中」出現在每一條查詢類 BR。

兩種修法，擇一：

1. **給它一個名字。** 授權依賴用具名判斷式（`CanViewOwnUnit`）；資料範圍或狀態集合用具名概念（`可查詢設備 = 未刪除且啟用中`）。在其權威章節定義一次，其餘一律只寫名字。
2. **上收成前提。** 一張表的每一列都帶同一個限定語時，那個限定語屬於表格上方的一句前提，不屬於每一列。

**判準：同一個限定語寫到第三次就停下來**，給名字或上收。第三次通常也是三種措辭開始分岔的地方。

## 三、這條該不該是 BR

第六章的 BR **只放業務規則**，範圍不大於「商業政策」的經典定義。這一條不設防，欄位驗證、畫面配置與範圍聲明會整批被吸進第六章——因為它們也長成「約束 + 違反時的處理」的樣子。

三問，**全部為「是」才是 BR**：

1. **這條約束由業務決定嗎？** business 有可能做出不同的決定——而不是「畫面就長這樣」「框架就這樣」「邏輯上本來就不可能」。
2. **違反它的後果不只是畫面提示嗎？** 會產生錯誤資料、越權、稽核缺口、金流或庫存錯誤，或讓下游流程走錯。
3. **換一個入口進來（API、批次、匯入、後台），這條還成立嗎？**

任一問為「否」，它就不是 BR——**把它搬到正確的章節，不是刪掉它**。

| 例子 | 判斷 | 去處 |
| --- | --- | --- |
| 查詢結果僅顯示登入者所屬單位的設備 | 是 / 是 / 是 | BR |
| 已報廢的設備不出現在候選清單 | 是 / 是 / 是 | BR |
| 起日不得晚於迄日 | 第 1 問否：業務沒得選 | 功能介面的錯誤訊息表 |
| 查詢條件預設近三個月 | 第 3 問否：換入口就不成立 | 功能介面 |
| 結果欄位包含設備編號、名稱、狀態 | 第 1、3 問否 | 功能介面 |
| 本期不做行動版 | 全否，這是範圍不是規則 | 二、範圍與非範圍 |

**錯誤訊息原文只有一個家，但那個家不一定是 BR。** 訊息原文寫在它所約束的事實所在的章節——業務規則的訊息寫在該 BR 的「錯誤處理」，欄位驗證的訊息寫在功能介面章的錯誤訊息表。同一則訊息不得同時出現在兩處。

### 規模參考

| 功能型態 | BR 參考量 |
| --- | --- |
| 唯讀查詢／報表 | 3-8 |
| 單一表單 CRUD，無狀態機 | 5-10 |
| 有狀態機的單據流程（多角色、庫存或金流） | 12-20 |
| 跨模組、多狀態機 | 20+，但先評估是否該拆成多份文件 |

這是量級參考，不是上限。超出時回頭對每條 BR 跑一次三問，**不是刪到達標**。最常見的四種溢出：

- 欄位規格、畫面配置、入口位置被寫成 BR（→ 功能介面）。
- 範圍聲明被寫成 BR（→ 二、範圍與非範圍）。
- 程式落點與安全實作要求被寫成 BR（→ 七、模組責任 / 十三、驗證條件；見本文第四章）。
- **同一條規則的多個例外被拆成多條 BR。** 例外屬於它所屬規則的小節，不另立編號。

## 四、不寫可推導的內容

前三章管的是「這個事實該寫在哪」。這一章管的是**這句話該不該存在**。

> **推導測試**：一個讀過本文件其他章節的工程師，能不能自己得出這句話？能，它就不該佔一行。

規格文件最頑固的膨脹來自這裡，因為每一句單獨看都正確、也都只出現一次——前面所有檢查都攔不住。

### 三種典型

**一、繼承式規則被逐條展開。**

一條規則若定義為「與 X 相同，除了 Y」，就寫 X 的名字與 Y 這個例外，不要把 X 的內容逐條列出來。那份清單會在 X 改動時默默過期，是最難發現的單一事實來源違規——**它長得像引用，其實是複製**。

| | 寫法 |
| --- | --- |
| ❌ | 匯出沿用畫面查詢：欄位一致、套用 BR-01、套用 BR-02、套用條件驗證、資料範圍一致、權限一致，但不受分頁影響 |
| ✅ | 匯出與畫面查詢使用相同的條件、欄位、排序、資料範圍與權限，差別只有不套用分頁 |

✅ 那句不只短，涵蓋範圍還更大：之後新增的查詢類 BR 一體適用，而清單式寫法只涵蓋當初列出來的那幾條。

**二、把別章的結論在 BR 裡再講一遍。**

「未授權時不顯示匯出按鈕」已經在五、功能介面的入口與導向寫過；「查詢與匯出共用同一個方法」已經在七、模組責任寫過。**BR 只寫業務效果**——這條規則要達成什麼、違反時怎麼處理。落點是模組責任的事，畫面行為是功能介面的事。

**三、把「不可以偷懶」寫成規則。**

「不可只靠隱藏按鈕擋權限，Server 端必須再驗一次」不是業務規則——業務不可能做出別的決定（本文第三章第 1 問）。它是**驗證條件**，家在十三、驗證條件，一條一句（`驗證方式` 填 `自動化測試`——直接呼叫 API 就驗得到）：

```markdown
| VC-04 | 匯出端點在 Server 端獨立驗證權限，隱藏按鈕不作為唯一防線 | 三、角色與權限 | 自動化測試 |
```

### 什麼時候可推導的內容仍要留

推導測試的目的不是把文件寫薄，是讓它能一路讀下去。三種例外：

- **推導不明顯，而且推錯的代價高** → 收斂成**一條**驗證條件，一句話，不在 BR 裡展開。
- **推導要跨三章以上** → 在最相關的一處寫一句帶摘要的引用（見本文第五章），不重述內容。
- **它是被主動排除的替代方案** → 屬於 `> **設計決策**：` 的「替代方案」欄，不是可推導內容，照留。

## 五、引用一律帶摘要

「不得重述內容」禁的是**把規則本文抄第二遍**，不是禁止交代這條引用在講什麼。**每個引用都必須帶一句最短摘要**，摘要與編號同時出現：

| | 寫法 |
| --- | --- |
| ❌ 裸引用 | `見 BR-06；更新審核人 / 審核時間` |
| ❌ 裸引用 | `序號設備限制見 BR-07。` |
| ❌ 裸引用 | `詳見 spec.md。` |
| ✅ 編號 + 摘要 | `見 BR-06：先驗設備狀態，通過才依差額異動庫存並寫回來源單據；更新審核人 / 審核時間` |
| ✅ 編號 + 摘要 | `序號設備僅能填 0 或 1（BR-07）` |
| ✅ 連結 + 摘要 | `退回後申請人可修改並重送，見 [spec.md](./spec.md) User Story 12` |

**判準——「刪掉編號測試」**：把 `（BR-xx）` 或連結整個拿掉，該句話仍須完整成立、讀者仍知道會發生什麼。若拿掉後句子塌了（剩「見 BR-06」「限制見 BR-07」這種），代表編號正在承擔語意，違規。

摘要要短到不可能與權威表述分岔——一句話、只講「會發生什麼」，不含條件分支、不含錯誤訊息原文、不含實作細節。**摘要不是縮小版的原文**；一旦摘要開始逐條列舉，它就變成本文第四章的「繼承式規則被逐條展開」。

**修訂時同樣適用**：只改權威位置那一處。若改完發現別處也要跟著改，代表那裡本來就違規重述了——把它改成引用，而不是同步更新兩份。

## 六、反模式

### 反模式 1：一條規則散落十處

一條「起單方依賴」規則在權限模型 blockquote、權限清單表、動作對照表、模組責任、介面契約兩列、實作注意事項兩列、驗證條件各寫一次。十處措辭略有差異，讀者無從判斷哪份權威，只好十份都讀。

**正解**：在三、依賴判斷定義 `CanActAsOriginator` 一次；動作對照表的「依賴」欄填 `CanActAsOriginator`；其餘章節完全不提。

### 反模式 2：表格單格塞 400 字

一條 BR 塞進表格單格 1,648 字元，混雜驗證規則、六種錯誤訊息、SQL CAS 條件與四個跨 BR 引用。表格無法分段、需要橫向捲動，是最不適合承載長論述的容器。

**正解**：BR 是小節不是表格列。規則本文分段寫，錯誤訊息用子表格，實作約束獨立區塊。

### 反模式 3：「實作注意事項」章節

一個 16 列的「實作注意事項」章節，**每一列都是別章的重述**——併發控制重述 BR-14、CAS 重述 BR-10、交易邊界重述 BR-18、權限可見性重述 BR-16/20/21。整章零新增資訊。

**正解**：單條規則的實作約束寫在它所屬的 BR 小節。系統層級的併發模型才進第十章，且每一列都要通過「搬進某條 BR 會不會更合適」的測試。

### 反模式 4：把 Matt Spec 抄一遍

「一、背景與目的」寫成 Problem Statement 的換句話說，「二、範圍與非範圍」把 Out of Scope 逐條重打，「十三、驗證條件」把 user stories 換句話說再寫一遍。三章零新增資訊，而且從此有兩份會分岔的需求描述。

**正解**：功能是什麼一句話 + 連結；範圍章只寫**系統邊界**（哪個模組不動、哪張表不碰）；驗證條件只寫 user story 表達不出的判準與設計正確性。

驗證條件是這條反模式最容易犯的一章，因為它**本來就該對著 user story 寫**。分界在於它有沒有增加可判定性：

| user story | ❌ 抄一遍 | ✅ 增加可判定性 |
| --- | --- | --- |
| 審核者可退回申請單 | 審核者能夠退回申請單 | 對 `待審核` 的單按「退回」且退回原因為空 → 擋下並顯示「請填寫退回原因」，狀態維持 `待審核` |

右欄是 `spec.md` 沒有、也不該有的東西（那是判準，不是需求）。左欄則是換句話說，刪掉。

### 反模式 5：狀態機三份描述

同時有「主線 mermaid 圖」（只畫 4 個轉移）、「合法狀態轉移表」（13 個轉移）、「動作 → 狀態轉移對照表」（14 列）。三份互有出入。

**正解**：一張完整 mermaid 狀態圖 + 一張動作對照表。

### 反模式 6：唯讀功能硬套狀態機

一個唯讀查詢頁照樣畫了狀態圖、照樣列出動作對照表，而「狀態轉移」一欄從頭到尾填「無」。整欄零資訊，還讓讀者懷疑是不是漏寫。

**正解**：動作對照表真正在集中的是「哪個動作要哪個權限、依賴哪個判斷式、有什麼副作用」——這件事所有功能都有，狀態轉移才是狀態機功能才有的那一欄。無狀態機時把表降級為「動作與權限對照」移進三、角色與權限（拿掉狀態轉移欄，不是填「無」），「四、狀態與流程」的狀態圖與本表一併省略；若還有帶分支判斷的流程就只留流程圖，沒有則整章省略。**同一張表任何情況下只存在一份，不因搬家而在兩章各留一份。**

### 反模式 7：來源標記欄

每張表都有一個「來源」欄，7 種標記，但 90% 的列都是 `PRD-confirmed`——一整欄的雜訊，換來的資訊只有「這句話是需求還是我猜的」，而它還需要一整節「來源標記說明」解釋自己。

**正解**：只保留 `> **設計決策**：`、`> **實作方向**：` 與「待釐清事項」章節。前兩者告訴讀者「能不能改」，第三個告訴讀者「還沒定」——都影響決策，其餘不影響。

### 反模式 8：所有技術內容都是硬約束

整份設計章節沒有一條「實作方向」，方法簽章、變數命名、資料流全被寫成必須遵守。下游 `implement` 只能照抄，發現更好的落點也不敢動。

**正解**：見 `constraint-levels.md`。設計段完成後數一次：這份文件裡有幾條實作方向？零的話回去重新分級。

### 反模式 9：BR 把別章的結論再講一遍

一條「匯出」BR 的核心只有一句「與畫面查詢相同，但不套用分頁」，卻寫了八點：欄位一致、不受分頁、套用 BR-01、套用 BR-02、套用條件驗證、未授權不顯示按鈕、查詢與匯出共用方法、Server 端要再驗權限。

其中按鈕顯示條件在五、功能介面寫過，共用方法在七、模組責任寫過，Server 端驗權限是驗證條件，其餘全是「與畫面查詢相同」這句話的展開。**八點裡有七點是可推導的，而且每一點都只出現一次**——重複檢查完全攔不住。

**正解**：BR 只留業務效果那一句。落點回模組責任，畫面行為回功能介面，安全檢核回驗證條件，繼承關係寫成「與 X 相同，除了 Y」。見本文第四章。

### 反模式 10：為了對稱而補內容

五條 BR 裡四條有「實作約束」，第五條沒有，於是硬寫一句「依一般做法實作即可」。一張表某一列沒有值，於是填「無」「N/A」「不適用」。一個章節這次用不到，於是留著標題寫「本次無此需求」。

**正解**：沒有就整個區塊省略，不留空標題。哪些章節無內容時要留、哪些要整章移除，見 `document-template.md` 的「章節去留」。

## 七、精簡準則

- **表格單格上限約 80 字**。超過就改用小節。
- **一條規則講完就停**。BR 不需要開場白、不需要重述功能背景、不需要結尾總結。第一句就是規則本身。
- **一條驗證條件一句話**。需要三行才講得清楚，代表在重述 BR。收斂成驗證條件前先確認它**不是**「已在 `spec.md` 寫過」或「只是重述本文件其他章節」——那兩種情況直接刪，不要換個地方再說一次。
- **不把一句話拆成條列**。條列用在真的有多個並列項目時；只有一項的條列改寫成句子。
- **不重述章節職責**。「本章說明本功能的業務規則」與章節標題同義，刪掉。
- **mermaid 只在有分支判斷時畫**。線性流程用文字，畫成流程圖只是把一句話拉成十行。
- **不畫兩張圖講同一件事**。狀態圖與流程圖的職責要切乾淨。
- **章節不為套模板而生**。無關的省略，不留空標題與佔位內容（反模式 10）。
- **不寫轉嫁語句**。「此部分由下游設計」「留待後續補充」——不屬於本文件就直接不寫；屬於本文件但還沒確認，就進待釐清事項。
- **不寫過程日誌**。「第一版設計是 A，後來討論改成 B」不進正文；需要留痕就在「修訂紀錄」一列一句。

## 八、什麼絕不能砍

收斂只砍重複、越界與可推導，不砍以下任何一項：

- 任何一條錯誤訊息原文。
- 任何一次狀態轉移，包含看似不重要的自環（例如「取消 → 維持原狀態」）。
- 任何一個併發、交易或原子性約束。
- 任何一條權限或依賴條件，包含例外角色。
- 任何一個邊界值、預設值、格式限制。
- 任何一項設計決策的理由。
- 任何一條待釐清事項。
- 任何一條定稿模式標記出來的偏差。

**判準**：如果刪掉它，下游 `to-tickets` / `implement` 或工程師就得回頭問人，那它就是細節，必須留。如果刪掉它，讀者只是少讀一次已經知道的東西，那它就是重複、越界或可推導，必須處理掉。

**「文件看起來有點長」不是砍任何一項的理由。** 真要砍，砍的對象只能是那三種膨脹，而它們是查出來的（本文第〇章），不是憑感覺看行數。若查完發現每個事實都只出現一次、都在對的章節、都不是別處的必然結果，那這份文件就是它該有的長度，不再壓縮。

## 九、語言

- 繁體中文，台灣軟體開發常用語。
- 除標點符號外，所有特殊符號（`/`、`+`、`-`、`...` 等）一律使用半形。
- 術語對齊 `CONTEXT.md`；`CONTEXT.md` 標了 `_Avoid_` 的字不要用。
- **同一個概念全文用同一個詞**。「可視範圍」「可見範圍」「資料範圍」混用，讀者會以為是三件事。挑一個，其餘全部改掉。
- **不把集合與它的元素並列**。「四道納入判定與可視範圍全部在資料庫執行」——可視範圍就是那四道的第四道，並列讀起來像五件事。改成「四道納入判定（工單類型、工單狀態、生效數量、可視範圍）全部在資料庫執行」。
- 避免生硬 AI 用詞：不寫「賦能」「打通」「閉環」「顆粒度」「進行一個…的動作」「值得注意的是」。該說「審核者按下核准後，庫存立刻扣掉」就這樣說。
- 不用第二人稱對讀者說話（「你需要注意」），這是規格不是教學。
